00 · The short answer

Two durable ledgers. One disposable process.

The Svelte interface does not talk to Claude, Codex, or Agy directly. It calls Tauri commands. Rust owns the session, records every normalized event in the SQLite database on the machine that owns the session, launches an ACP adapter only when work begins, and streams ordered updates back to Svelte.

The easiest accurate mental model is this:

The provider keeps the model’s real conversation context in its own native session. Assembly keeps a second, durable, normalized account of the conversation in sessions.db so the UI can restart, page backward, restore drafts, and audit what happened. The ACP adapter is a translator process between them. When a turn is finished and nothing is still running, Rust disconnects that translator to reclaim memory, but it keeps both durable records and the provider’s native session ID.

01 · Source authority

What changed from the stale guide.

The old explanation was accurate for old main: PTY-owned agents, provider JSONL tail polling, an unwired Rust spike, and no conversation database. Those are no longer the main structured-conversation architecture in this worktree.

Current worktree

ACP is wired

Rust launches trusted adapter manifests, negotiates capabilities, creates or resumes native sessions, prompts over ACP, handles agent requests, and normalizes updates.

Current worktree

History is database-backed

sessions.db is the durable Assembly journal. Svelte loads bounded windows from SQLite and can page backward. Provider JSONL is now an import/fallback source, not the only UI source.

Current worktree

Images are typed ACP content

Structured prompts send text and base64 image blocks when the provider advertises image support. Paths are appended only in the raw terminal fallback.

Current worktree

Markdown is real and safe

The frontend tokenizes GitHub-flavored Markdown with marked, converts it to typed blocks, and renders escaped Svelte nodes. It does not inject generated HTML.

Remote boundary

The owning machine owns the session

Normalized session and ensure records name either local or remote. Omitted values remain local for compatibility. The new-session composer asks whether work runs locally or remotely. Its remote setup accepts any user-selected SSH destination and saves only that destination, the remote Assembly source checkout, and the default working directory in the Mac's SQLite settings. Rust deploys and updates the loopback-only service through SSH, reads its token into memory, owns the SSH tunnel through window shutdown, and routes remote conversation, draft, and workspace commands over one authenticated WebSocket. That machine's sessions.db, provider session, checkout, credentials, and runtime are authoritative; the Mac does not mirror them into local SQLite.

Do not blend branches mentally. Older plans may still describe interim designs. For “what runs,” the code in this worktree wins, and this page is the only description of it that is kept current. It calls out external and proposed parts instead of presenting them as shipped.

02 · Vocabulary

Protocol, adapter, agent, session.

These words name different layers. Keeping them separate makes the whole system much easier to reason about.

ACP
Agent Client Protocol. A JSON-RPC contract for initialization, sessions, prompts, streaming updates, cancellation, permissions, user input, configuration, and capabilities. It is the language on the wire, not the model.
ACP client
Assembly’s Rust code. It spawns an adapter, writes requests to stdin, reads stdout, answers requests from the adapter, and maps provider-specific updates into one app vocabulary.
ACP adapter
A provider-specific child process. It accepts standard ACP on one side and translates to Codex app-server, the Claude Code adapter, or Agy stream JSON on the other.
Coding agent
The underlying program that performs the actual model and tool work: Codex, Claude Code, or Antigravity/Agy. It may have its own native protocol and transcript storage.
Tauri
The desktop boundary. Svelte invokes named Rust commands in-process; Rust emits named events back to the webview. There is no HTTP server between this UI and its backend.
Sidecar
A child process launched and supervised by the desktop app. Here, it is usually the ACP adapter and sometimes a native provider process beneath it.

03 · Topology

Who talks to whom.

The normal structured path crosses four boundaries. Only the middle boundary—between Rust and the adapter—is ACP.

Svelte webviewComponents, stores, reducer, composer, safe Markdown renderer.
Tauri commands + eventsTyped in-process IPC. No localhost REST API.
Rust runtime managerIdentity, writer lease, SQLite, activation, normalization, recovery.
ACP sidecar over stdioOne JSON-RPC object per line on stdin/stdout.
Native coding agentCodex app-server, Claude Code adapter internals, or agy stream JSON.
Boundary 1

Svelte ↔ Rust

Svelte calls commands such as ensure, send, respond to approval, read snapshot, load older, save draft, and manage attachments. Committed agent events cross the root ordered agent-conversation-event Channel; low-volume events still use named Tauri events.

Some of what crosses here is not ours. Tauri’s own plugins register commands on this same boundary, and the Files panel calls three of them directly rather than through a command of ours: plugin-fs to make, rename and watch, plugin-opener to show a path in the Finder, and plugin-clipboard-manager to copy one. plugin-dialog and plugin-notification were already registered and are called from elsewhere. Each plugin is registered in the builder and each carries its own permission in src-tauri/capabilities/default.json.

Boundary 2

Rust ↔ adapter

ACP JSON-RPC 2.0 over newline-delimited stdin/stdout. Requests have numeric IDs; notifications do not; responses resolve pending one-shot channels.

Boundary 3

Adapter ↔ provider

Provider-specific. Codex bridge speaks app-server JSON-RPC. Agy adapter invokes stream JSON. Claude behavior lives in the installed external adapter.

The Workflow Engine reuses this same runtime and store. Startup gives it a clone of the ACP manager and the manager’s existing Arc<SessionStore>. Workflows are orchestration above the ACP manager, not a second hidden way of talking to agents or a second database connection.

16 · Proposed work

Building Assembly-owned compaction safely.

The journal now gives you enough durable source material to summarize a conversation. It does not by itself let Assembly replace the context inside an existing provider-native session.

Not implemented

There is currently no Rust summarizer service, no “fast tier” backend setting, no compaction artifact or boundary in SQLite, and no evidenced standard ACP method that mutates a session’s context. The contextCompaction event that exists records a compaction the provider performed (its own auto-compaction or /compact); it is a marker in the journal, not a compaction engine.

The minimum safe design

  1. Choose a stable durable boundary.

    Capture through_sequence for one ownedId. Never summarize “whatever happens to be loaded in Svelte.”

  2. Select source material in one backend SQL query.

    Read completed human/assistant content and required tool/file outcomes through that boundary. Exclude streaming deltas and superseded state.

  3. Hash the normalized source.

    A source hash plus boundary makes retries idempotent and proves exactly what the summary represents.

  4. Call a separate one-shot summarizer.

    The Rust backend sends a bounded document to the explicitly configured lower-latency/lower-cost model tier. This should not borrow the active conversation’s writer lease or silently alter it while a turn is running.

  5. Persist the result before applying it.

    Store summary text, boundary, source hash, model/tier, status, token accounting, and timestamps. Preserve the original event journal.

  6. Apply through an explicit provider strategy.

    If the adapter advertises a real provider compaction command, invoke it under the structured writer lease. Otherwise create or fork a new native session seeded with the summary plus the uncompacted tail. Do not pretend that writing a summary row changed the old provider context.

  7. Record the context transition.

    Append the durable contextCompaction event that already marks provider compactions, extended with the summary and the new native-session boundary, so the UI can explain what changed without hiding old messages.

  8. Resume ordinary prompting.

    Only after the compaction state and provider transition are durable should the writer lease return to normal use.

Smallest useful durable schema

A dedicated row makes resumable work, retries, failure recovery, and “which summary was applied?” easy to query. The visible transition should still be an ordinary canonical event so timeline replay remains complete.

Guardrail

Never compact live work

Require the same quiescence checks as suspension: no active prompt/turn, approval, input, handoff, live tool, or background work. Compaction is another writer.

Guardrail

Never delete the journal

Compaction changes future model context; it should not erase the user-visible, auditable history that produced the summary.

Guardrail

Do not assume ACP support

Capabilities or provider command discovery must decide whether in-place provider compaction is possible. Otherwise use an explicit new/forked native session.

Guardrail

Measure the actual context

Trigger from provider telemetry when available; use conservative byte/token estimates when it is not. Message count alone is not a context-window measurement.

What the user should see

A compacted session should retain scrollback and show a small, inspectable timeline marker: what range was summarized, which model produced it, whether the provider accepted it in-place or a new native session was created, and where the full original history remains. Failure should leave the old session untouched and retryable.

Recommended implementation order: first add SQL-derived counts and a context-health DTO; then persist summary artifacts; then add the one-shot backend summarizer; only then implement one provider application strategy with an explicit capability check. That sequence keeps the risky provider-context mutation separate from the useful accounting foundation.

Two services, one shape

One request, one answer, no memory

OpenAI is asked through the Responses API (instructions, input, max_output_tokens); Anthropic through the Messages API (system, messages, max_tokens, and the anthropic-version header). Each vendor module phrases one request and reads one answer; a single transport sends it, with a twenty-second ceiling and one retry only when the call never left the machine. A timeout is not retried, and neither is a refusal. Nothing streams and nothing is remembered between calls, so a job is exactly as expensive as the text handed to it.

The app asks too

A session names itself after its first turn

A new session is named after the first line the person typed, which is rarely what it turns out to be about. The moment its first turn finishes, the runtime manager hands the helper that prompt and the reply to it — a thousand characters of each — and writes the short name that comes back over the provisional one, marking the row title_source = helper and telling the rail so the row changes where it stands. Nothing waits on the call: the send has already finished, a helper with no key stored does nothing at all, and any other failure leaves the prompt name alone. A name the person typed themselves is never touched, and neither is one the helper has already written, so this happens once per session.

Counted like everything else

Helper calls show up in Usage

Every call that succeeds writes one row to the usage store through record_helper_call: the vendor as the provider, the model id, the input and output token counts, source kind helper and source key helper/<job>. That is the same table the indexed agent transcripts land in, so the Usage popover counts helper spend without knowing the helper exists, and no schema change was needed to carry it.
