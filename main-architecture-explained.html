00 · The short answer

Two durable ledgers. One disposable process.

The Svelte interface does not talk to Claude, Codex, or Agy directly. It calls Tauri commands. Rust owns the session, records every normalized event in the SQLite database on the machine that owns the session, launches an ACP adapter only when work begins, and streams ordered updates back to Svelte.

The easiest accurate mental model is this:

The provider keeps the model’s real conversation context in its own native session. Assembly keeps a second, durable, normalized account of the conversation in sessions.db so the UI can restart, page backward, restore drafts, and audit what happened. The ACP adapter is a translator process between them. When a turn is finished and nothing is still running, Rust disconnects that translator to reclaim memory, but it keeps both durable records and the provider’s native session ID.

What exists now

A real ACP client

agent_conversation/messaging.rs starts one Axum endpoint at 127.0.0.1 on an ephemeral port per backend process. ACP session creation, loading and resuming pass an assembly HTTP MCP server with a session-bound Authorization bearer header only when initialize advertises mcpCapabilities.http. The credential crosses ACP over its input pipe. The Claude launcher replaces its HTTP Authorization value with an environment-variable reference before the Agent SDK constructs CLI arguments, keeping the value in the per-query child environment. The Codex adapter sends its HTTP headers through the app-server input pipe as thread configuration; its CLI arguments contain no MCP credentials. No MCP client subprocess is needed. Tokens stay in backend memory, survive runtime suspension and are revoked on owned-session deletion. The endpoint answers MCP initialize and tools/list. Each credential binds weakly to its owning SQLite store; list_sessions reads the backend-local SQL directory and send_message resolves an exact unique name, then stores a queued message. The board_update tool writes a Build board card through the same backend-local store: helpers are refused, the marked main orchestrator may update any card, and other sessions may update only cards they created. A call with question or answer records, answers or reopens a question in board_questions instead, under the same ownership rule, and replies with its number. Only the bearer header determines the caller; arguments cannot impersonate another session.

session_directory projects local root sessions, excluding cached remote rows and provider child records. Duplicate titles gain their full owned ID as a suffix; task-key/step names remain reserved, so collisions return an error. A title never makes an orchestrator: the owner marks one session from its rail menu (set_main_orchestrator), stored as the app_settings row orchestrator.main on that session's machine, and the view's orchestrator column reads it. Latest owned-session orchestration events supply run, step and task-key metadata from workflowPayload.run.inputSnapshot.task.key. The migrated workflow_messages table stores sender and target owned IDs, sender display name, optional group/run metadata and receipts. Delivery reads one oldest queued row with WHERE to_owned_id=? AND receipt='queued' ORDER BY created_at_ms,id LIMIT 1 using the target/receipt/time/id index. Group membership serves status/timeline metadata only. Delivery uses the sender display name and records delivered only after the provider accepts the message. A busy helper receives its own parent's and sibling helpers' queued messages through the provider's existing steering capability; other senders wait until it is idle. Helpers with the same stored parent can address each other by name or handle. Each sibling message also queues one copy to their parent, labelled with both parties; copies wait while the parent is busy. One SQL count caps each direction of a helper pair at twenty messages; the count, original and copy share a write transaction. Busy-helper selection happens in SQL, so an older unrelated message does not block the parent. Refused steering leaves the message queued, including when the turn has just ended. The owner's composer uses that same steering path directly. Historical expired receipts remain readable.

02 · Vocabulary

Protocol, adapter, agent, session.

These words name different layers. Keeping them separate makes the whole system much easier to reason about.

ACP
Agent Client Protocol. A JSON-RPC contract for initialization, sessions, prompts, streaming updates, cancellation, permissions, user input, configuration, and capabilities. It is the language on the wire, not the model.
ACP client
Assembly’s Rust code. It spawns an adapter, writes requests to stdin, reads stdout, answers requests from the adapter, and maps provider-specific updates into one app vocabulary.
ACP adapter
A provider-specific child process. It accepts standard ACP on one side and translates to Codex app-server, the Claude Code adapter, or Agy stream JSON on the other.
Coding agent
The underlying program that performs the actual model and tool work: Codex, Claude Code, or Antigravity/Agy. It may have its own native protocol and transcript storage.
Tauri
The desktop boundary. Svelte invokes named Rust commands in-process; Rust emits named events back to the webview. There is no HTTP server between this UI and its backend.
Sidecar
A child process launched and supervised by the desktop app. Here, it is usually the ACP adapter and sometimes a native provider process beneath it.

03 · Topology

Who talks to whom.

The normal structured path crosses four boundaries. Only the middle boundary—between Rust and the adapter—is ACP.

Svelte webviewComponents, stores, reducer, composer, safe Markdown renderer.
Tauri commands + eventsTyped in-process IPC. No localhost REST API.
Rust runtime managerIdentity, writer lease, SQLite, activation, normalization, recovery.
ACP sidecar over stdioOne JSON-RPC object per line on stdin/stdout.
Native coding agentCodex app-server, Claude Code adapter internals, or agy stream JSON.
Boundary 1

Svelte ↔ Rust

Svelte calls commands such as ensure, send, respond to approval, read snapshot, load older, save draft, and manage attachments. Committed agent events cross the root ordered agent-conversation-event Channel; low-volume events still use named Tauri events.

Some of what crosses here is not ours. Tauri’s own plugins register commands on this same boundary, and the Files panel calls three of them directly rather than through a command of ours: plugin-fs to make, rename and watch, plugin-opener to show a path in the Finder, and plugin-clipboard-manager to copy one. Raster image preview uses the app-owned read_source_image command so its bounded bytes cross IPC as a raw response rather than an expanded JSON array. plugin-dialog and plugin-notification were already registered and are called from elsewhere. Each plugin is registered in the builder and each carries its own permission in src-tauri/capabilities/default.json.

Boundary 2

Rust ↔ adapter

ACP JSON-RPC 2.0 over newline-delimited stdin/stdout. Requests have numeric IDs; notifications do not; responses resolve pending one-shot channels.

Boundary 3

Adapter ↔ provider

Provider-specific. Codex bridge speaks app-server JSON-RPC. Agy adapter invokes stream JSON. Claude behavior lives in the installed external adapter.

The Workflow Engine reuses this same runtime and store. Startup gives it a clone of the ACP manager and the manager’s existing Arc<SessionStore>. Workflows are orchestration above the ACP manager, not a second hidden way of talking to agents or a second database connection.

04 · Provider adapters

One protocol, three translations.

The Rust provider registry does not hardcode “run a model.” It holds trusted executable manifests, validates them, and constructs the same AcpRuntimeAdapter interface for each provider.

Signed provider adapter

Codex

Manifest ID: codex-acp — the daily provider release compiles the latest published official npm adapter into a standalone runtime, pairs it with a launcher, and records hashes in the signed platform feed. A clean desktop release downloads it only when Codex is selected for installation.

Development: dev-app.sh uses the prepared release payload and matching hash. A verified installed provider update takes priority over this bootstrap payload, including after relaunch.

The current adapter reports a legacy composite models projection and also publishes the controls it actually accepts as configOptions: base model ids under model and thinking depth under reasoning_effort. Assembly gives those mutable options precedence, maps the effort id into its reasoning field, and changes either value through session/set_config_option; it does not put a composite model id into the base-model control.

Claude

Manifest ID: claude-agent-acp — the daily provider release updates the official npm adapter to its newest version and compiles it, unpatched, inside Assembly's launcher scripts/claudeAcpLauncher.ts (a release that breaks the launcher's imports fails the run, so nothing is published) and its Claude Agent SDK into a standalone runtime, pairs it with a launcher, and records hashes in the signed platform feed. CLAUDE_CODE_EXECUTABLE in its environment is honoured, and an inherited MAX_THINKING_TOKENS is scrubbed so the adapter’s own effort option is the only way effort is set.

Development: the same prepared adapter payload is used, with inherited nested-Claude markers cleared. Installed updates take priority over bootstrap payloads.

Its implementation is external to this repository. Assembly treats it as an ACP agent and learns its session, image, command, and interaction capabilities during initialize. session/new answers with modes and configOptions (mode, model, effort, agent) rather than a models list; the client remembers the offered option ids and changes model or effort with session/set_config_option, whose reply carries the whole option set back. The adapter has no session/set_model. Model display names from ACP configOptions remain paired with their wire IDs in the conversation config and menus; aliases such as opus display the provider’s current Opus 5.5 name without changing the value sent to the adapter. A new session takes whatever the adapter reports; the model and effort chosen for the conversation are then asked of it, and the reply names what the session is actually on — a request the adapter resolves to something else is shown resolved, not as typed. Effort is no longer fixed when the process starts, so it can change at any point in a conversation; the “Effort is set when the session starts” refusal is reserved for an adapter that reports no effort option at all.

Sign-in, the same for every provider

An adapter error with ACP's authentication-required code (-32000), or Claude 0.93's -32603 carrying data.details "Authentication required", means the user must sign in. If starting the session fails that way, providers/authentication.rs starts one temporary, unpooled attempt with the first method the adapter advertised in initialize that needs nothing from Assembly (no terminal or _meta requirement): Antigravity oauth-personal, Codex chat-gpt. The adapter opens its own browser sign-in under a five-minute deadline outside the session lifecycle lock; success retries activation once before the original prompt. Stop and session close cancel by Assembly session id and generation, a pending attempt blocks provider restart, and the client detaches on every outcome. When the adapter offers no such method (Claude), when the error arrives on a prompt, or when the backend runs as the headless remote server (--assembly-server, where nobody could see the browser), the user is told plainly to sign in with that provider's CLI where the session runs and send again.

How a new adapter version reaches local and remote sessions

  1. GitHub Actions publishes a signed provider feed each day.

    The workflow runs at 08:23 UTC, updates the Codex and Claude ACP npm packages to their newest published versions, and resolves Antigravity through the official ACP registry. bun compiles the stock Claude adapter that resolves together with Assembly's launcher, scripts/claudeAcpLauncher.ts, which runs the adapter as a library: it answers the prompt at the turn's result while background sub-agents run, sends sessionState and backgroundTaskCount (from the raw background_tasks_changed messages it opts into through the documented claudeCode.emitRawSDKMessages session meta) as session_info_update, tags root updates outside an active prompt with outOfTurn, stops background tasks on cancel, keeps the effective context window (an autoCompactWindow override included) when a result reports the model's full capacity, and drops ExitPlanMode's clear-context choice outside a prompt. When an upstream release breaks the launcher's imports, the build fails and the run publishes nothing, so Codex is held back too until the launcher is fixed. It builds platform assets for Apple Silicon Mac, Intel Mac, and Linux x86-64. The signed manifest lists all three providers, but an installation downloads only the chosen provider’s files. For both, the source package pin (Claude 0.90.0) is what development builds use, not the feed’s version ceiling.

  2. Assembly checks and offers, then waits for a choice.

    The local Settings host checks once when mounted. A ready remote connection checks its own provider status in Connections; the new-session picker checks the selected machine and offers Install for a missing provider. Settings shows installed and available versions with separate Install or Update buttons. There is no global update flyout, badge, banner, idle poll, or silent adapter installation.

  3. The machine running the session owns the files.

    Local Rust downloads the selected Mac assets. For remote work, the desktop sends a named provider command through the existing WebSocket and the backend downloads the Linux assets directly to the remote machine. The remote protocol carries request-scoped byte progress back to the same UI control. Both paths verify the signed manifest and file hashes, stage only the selected provider, retain other verified installed providers, then atomically switch the active pointer. A failed or interrupted transfer keeps the prior active selection. Restart Assembly or the remote server explicitly to load the new adapter. Active provider work blocks a remote install and a local restart. A remote restart instead warns for ten seconds, naming the busy sessions on that machine, then ends them: the server stops its adapters through AgentRuntimeManager::shutdown before exiting, and RestartProvidersButton.svelte re-checks once the connection returns.

Claude and Codex launchers need their respective claude and codex CLIs on the machine that runs the session. Adapter updates do not install, version-check, or update those CLIs. The official Antigravity server files are part of its adapter payload. Assembly app updates and remote backend updates are separate again.

The Rust adapter interface

trait AgentRuntimeAdapter {
    initialize(...)
    new_session(...)
    load_session(...)
    resume_session(...)
    detach_session(...) // stop transport; keep native session
    close_session(...)  // intentionally close native session
}

That trait is the provider boundary. Today its live structured handle has one implementation family: ACP. Codex, Claude, and Agy differ through manifests and the adapter process, not through three separate Svelte pipelines.

A provider is data, not a Rust enum: providers/descriptors.json holds one descriptor per provider, and a provider id is valid only if a descriptor names it. The launch code reads the descriptor instead of matching on names: its initialize _meta, elicitation, effort encoding, canonical working folder, and four launch settings in one shape (mode, session/new _meta, adapter arguments, environment). unattended, pre_approval, proof_home and read_only merge in that order, read_only last; _meta and JSON environment values deep-merge and arguments append. A pre-approval may instead ask Assembly's permission handler to approve the agent's own assembly MCP tools, which is how Antigravity gets them. Each descriptor's login entry says how a copied login loses its refresh token. A new ACP agent is a descriptor plus its release-bundle entry; Rust changes only for a wire quirk the fields don't cover.

05 · Desktop startup

What happens when Assembly opens.

Startup reconstructs durable session metadata first. It does not eagerly start one ACP process per session.

  1. Tauri resolves the application data directory.

    Rust opens sessions.db there and creates or migrates it to the current schema version (22). On the desktop it then imports any project roots saved by older versions into the project registry, once (project_folders::import_saved_project_roots), and files older local sessions under their projects if a local project was added since the last back-fill (project_folders::backfill_local_session_projects).

  2. Rust builds the trusted provider registry.

    When a selected adapter installation exists, Rust verifies its manifest and files and registers only those providers whose files pass verification. A damaged provider stays unavailable for repair without hiding healthy providers. Otherwise, explicit development path/hash pairs or local development wrappers can bootstrap the registry. A clean release starts with no providers; choosing a provider in the picker offers its installation.

  3. The runtime manager recovers sessions.

    Stored rows become suspended, disconnected in-memory session records with their native IDs, capabilities, configuration, and next durable sequence. No adapter is attached yet.

  4. Legacy import runs only when appropriate.

    If the database has no owned sessions, the manager can import provider transcript history into the normalized journal rather than discarding it.

  5. Rust starts the stale-sidecar reaper.

    It removes marked adapter process groups whose owning app instance is dead. It does not kill sidecars belonging to a live Assembly instance.

  6. Tauri starts the two projection workers.

07 · One message, end to end

What happens every time you press Send.

A structured prompt is both a durable state transition and an asynchronous conversation with another process. The database write is part of the delivery path, not a later best-effort backup.

  1. The composer validates the submission.

    It refuses an empty prompt, a concurrent send, a read-only child view, or a state that cannot currently write. A new-session draft waits for the selected machine and provider's current catalog, shows no earlier machine's controls while waiting, and discards late replies after a switch. Remembered choices are used only when the selected machine offers them; an explicitly empty option family remains empty.

  2. Svelte clears the visible draft and its SQLite draft.

    If sending later fails, it restores both. Draft durability is no longer just localStorage.

  3. The service chooses the writer path.

    A structured-owned session follows ACP. An explicitly terminal-owned external session writes to its PTY instead. The writer lease prevents both paths from writing at once.

  4. Attachments become typed prompt blocks.

    For structured ACP, persisted image bytes are loaded and encoded as image content alongside text. Capability checks happen before delivery.

  5. The frontend ensures the session metadata.

    The current ownedId, provider, working directory, native ID, and generation are synchronized with Rust.

  6. Rust lazily activates if suspended.

    send_message launches or joins an adapter, initializes ACP, resumes or loads the native provider session, asks the restarted adapter for the model, effort and approval policy the session is on, and acquires the structured writer lease. A model or approval policy chosen in the composer is applied next through set_conversation_config: Codex and Claude use session/set_config_option for the option ids they advertise, while an adapter that offers no model option gets session/set_model. If both a legacy model projection and mutable options are present, the options are authoritative because they name the values the adapter accepts. Every choice is weighed against what the adapter now running offers rather than a stored list, and the session then reports the adapter’s answer, not the request. If activation, configuration, or the prompt itself is refused, the adapter this send started is stopped again.

  7. The generation is checked again.

    A request from an older activation cannot accidentally write into the current one.

  8. Rust creates an Assembly turn ID.

    The turn begins before the provider response. This gives the journal a stable boundary even when the provider uses different internal IDs.

  9. The turn-start event is written to SQLite.

    The manager allocates the next sequence and writes the updated session plus the event in one transaction.

  10. The user message is written to SQLite.

    Assembly records it itself, including attachment IDs. It does not depend on the provider echoing the input.

  11. Only committed events reach the agent Channel.

    After the transaction succeeds, the live in-memory state changes and the projection worker admits one new event frame. The UI is therefore never ahead of the durable journal; if admission overflows, the worker replaces queued data with a resync marker and the active frontend reloads SQLite.

  12. Rust sends session/prompt over ACP.

    The prompt contains a provider native session ID plus typed text/image blocks. The ACP client assigns a numeric JSON-RPC request ID.

  13. The Tauri send command returns.

    The provider turn remains active. A background task awaits the ACP response while independent session/update notifications stream.

  14. Each update is normalized, ordered, and persisted.

    Assistant text, reasoning, tools, files, plans, tasks, approvals, usage, warnings, and errors become canonical events and then frontend payloads.

  15. The prompt result closes the turn.

    Rust expires unresolved requests, writes completed/interrupted/failed state, clears active-turn state, and considers suspending the adapter.

The app sends the current prompt, not the entire transcript. The provider resumes its own native context. Assembly’s journal is the durable UI/audit copy; it is not re-uploaded as model context on every message.

Why the stop is not immediate

The process supervisor snapshots descendants before shutdown, including tools that created a separate process group. It sends SIGTERM to those observed tools and the adapter’s whole process group, then uses SIGKILL after the bounded grace. Each separately signaled tool must still match its captured PID and process-birth identity; reparenting is allowed, PID reuse is not. Normal stop schedules final cleanup in a detached watchdog after waiting for the leader, so an exited group adds no grace delay. Final application shutdown waits up to the stop grace for captured groups to leave after concurrent stops, then kills surviving groups and detached tools within the five-second quit cap; a previously stopped adapter's watchdog may be abandoned by exit. The snapshot is released after cleanup and adds no idle polling. The grace period exists because Claude can write its durable transcript shortly after returning the answer; immediate killing previously lost completed turns.

11a · Remote machines

The owning machine owns the session.

The same Rust backend runs headless on a remote Linux machine. The Mac reaches it through SSH and never exposes ACP to the network. A remote session, its adapter and its journal live on the machine that runs it; the Mac keeps a readable copy.

Connecting

The remote server listens on 127.0.0.1:7777 only. The Mac opens a Rust-owned SSH forward to that port, reads ASSEMBLY_SERVER_TOKEN over SSH into the connection's memory (the token stays on the remote machine), and opens one WebSocket to /assembly. The forwarded socket never carries the token: each side sends a fresh challenge and proves it holds the token with an HMAC-SHA256 over both challenges and the protocol version, using separate server and client proof domains. The desktop verifies the server before answering, and the backend verifies the desktop before it creates subscriptions or accepts commands. Every frame is defined once, in remote/wire.rs. Client and server protocol versions must match (24 today); an older server is asked to update, with no fallback to the old bearer header.

Saved machines are SSH profiles in the remote-assembly.profiles.v1 setting and stay dormant at startup. A connection is ready only after the version check and a full session list; an attempt is bounded to 30 seconds, and cancelling it drops its tunnel. Each machine has one connection state, derived from its live client and sent to the frontend as remote-connection-changed. Removing a machine wins over an attempt still in flight.

Sessions and history

A session record names its machine, local or a remote profile, and the new-session composer asks where work runs. Sends, approvals and controls go to the owning backend, which runs the adapter, writes its own sessions.db and streams events back. The Mac saves those events under the remote profile, so a saved remote chat stays readable while its machine is offline; controls are disabled until it reconnects. The remote-assembly.session-projections.v1 setting keeps remote rows in the rail between connections.

Saved history downloads once into the Mac's SQLite. DownloadHistory streams a session's stored events newest first in compressed chunks; the Mac saves them without publishing them as live events, finds any gaps with one SQL query when the stream ends, and fills them with ordinary EventsAfter pages. Opening a session waits only until a fifth of its bytes are saved.

On reconnect the server replays each session's events after the Mac's last saved sequence, between ReplayStart and ReplayComplete; the Mac saves them quietly and publishes only the newest, so a long replay cannot flood the frontend or revive a finished turn. Resume names the sessions to replay, and lag recovery replays only the sessions the socket has queued. If a pushed event skips past the highest row the Mac saved for its session, the Mac saves nothing past the hole, lowers that session's cursor to its saved maximum, sends Resume for that session alone and drops its pushed events until its ReplayStart; the quiet replay re-sends them in order.

A remote machine scans and imports its own past transcripts. History lists that machine's provider sessions, an import reads the transcript there, and the Mac saves only the rows the download sends. The scan also reports the git common directory of each transcript folder and the desktop's registered project roots on that machine; the desktop matches them in SQL, so a remote worktree outside the project root still appears under its project. A session still running outside Assembly is refused until it stops.

Files, terminal and attachments

Frontend paths for remote files carry their machine as assembly-remote://<profile>/<path>. workspaceInvoke.ts removes the qualifier at the boundary and restores it on results, and remote/workspace.rs sends each Files, Git and pull request operation to the function the local command uses. Remote Files has no idle watcher, and local language servers are not started for a remote editor.

A remote session's shell runs on its machine. The Mac sends TerminalStart over the same socket; the server keeps its own terminal registry and sends output back with its generation and sequence, which the Mac feeds into the ordinary terminal channel under an assembly-remote-terminal:// id, so the tab works unchanged. A folder that no longer exists starts no shell.

Attachments upload to the owning backend in bounded chunks and are saved in its attachment vault; a remote send carries attachment ids, not image bytes. Every request carries an id, so a frontend abort sends a Cancel frame and the server stops that task.

Installing the backend and adding projects

Install and connect checks the newest signed assembly-backend-v* release record on the Mac, then has the remote machine download the archive over HTTPS and check its size and SHA-256 before the package installer replaces files; durable data is kept. The service binds only 127.0.0.1:7777, so SSH is the only way in. A backend release is published on every merge to main.

Add project browses the chosen machine's folders with list_folders (a local command, or the remote operation of the same name) and registers the folder in the Mac's SQLite; New project can also run git init or git clone there. New-session worktrees are created on the machine that owns the project.

11c · Agents, messages and workflows

Agents reach each other through Assembly.

Each backend runs one Assembly MCP server (messaging.rs) on 127.0.0.1. Every ACP session is given it with a session-bound bearer token when the adapter supports HTTP MCP servers; the credential travels over the adapter's input pipe or environment, never in a command line. Its tools let an agent list and message sessions, start helper sessions, and start and watch workflows. Assembly checks each call's session and role on the server.

Who may reach whom

An agent's role is read from the store on every call: a worker is a session a workflow run started, a helper has a parent session, the orchestrator is the one session the owner marked, and every other session is top-level. One SQL statement filters the session directory for the caller, and lookup and delivery use the same filter, so a session the caller may not see is an unknown name. Workers cannot start sessions or runs, helpers cannot start helpers, and a session's unfinished helpers are capped by the helpers_per_session app setting of its backend (five when unset). A helper starts at its parent's permission level. Helpers with the same parent can message each other by name; each sibling message also queues a labelled copy to the parent, and one SQL count caps each direction of a pair at twenty messages. A busy helper receives its parent's and siblings' messages through the provider's steering; other senders wait until it is idle, and refused steering leaves the message queued.

A session is addressed by its handle, its name or its owned id, with @machine for a session on another machine; messages to another machine are relayed over the remote connection, and workers and helpers never use the relay. Assembly labels each agent message with its sender and refuses or quotes text that imitates that label. Only the owner's own turns carry the owner's authority. A remote sender's role comes from that backend's saved main-orchestrator choice, never from its own claim; every request names its sender, and source-prefixed labels stay valid reply addresses.

Workflows

Workflow definitions are YAML files in the project's .assembly/workflows folder. Starting one snapshots the file and the task into the run's ledger in sessions.db, so later edits do not change a saved run. Workers start in Auto ("Approve for me") unless the step's YAML names a mode; an elevated mode applies only to a run the owner started or one started by a session already in an elevated mode. A step waiting for the owner is answered from the Inbox or the run view with accept, another round or stop; gates keep their own approval.

Agents use start_workflow, list_workflow_runs, get_workflow_run and stop_workflow_run on their own machine, and write new files with workflow_format and check_workflow. check_workflow and start_workflow accept an optional registered project (exact root or unique title) on the executing machine; unknown or ambiguous projects are refused. A caller may have three unfinished runs. The engine messages the starting session when its run waits for the owner or ends. Answering pauses, approving gates and retrying steps stay with the owner.

What the owner sees

Agent messages are stored in workflow_messages on the sending machine. The Messages screen and the right drawer read one SQL page from each machine and merge them. A committed message calls the broker's change callback, which the desktop and each remote socket turn into one agent-messages-changed event, so open views reload without polling.

The owner Inbox asks each machine for workflow steps waiting on the owner and adds sessions waiting on a permission or a question. The rail lists a helper under its parent and a run's workers under that run, and adds a session an agent started the first time something names it. The Build board's cards and owner notes are stored in board_cards and board_notes, and the questions agents ask the owner in board_questions; its reads and counts are single SQL statements. Agents write cards and questions with the board_update tool (helpers are refused; the orchestrator may update any card, other sessions only their own). The desktop reads each connected machine's board and badge count over the messaging wire and sends owner actions to the machine that owns the card.

12 · Restart and long history

How the conversation comes back.

Remote download reconnects use SQL MIN saved sequence as an exclusive cursor, independently of Resume replay, which uses saved maxima. Protocol readiness and inventory filing restart durable incomplete root and child downloads. Disconnect pauses watches and clears dead request IDs; replaced frames cannot write. Local-only scrolling waits for committed chunks or cancellation and never starts a transfer. ExtendImport clears completion when it adds older rows, starts the same download below the saved minimum, and checks gaps again at done.

Assembly reconstructs its view from SQLite and reconstructs provider connectivity by native-session resume. Those are related, but they are not the same recovery operation.

  1. Rust opens sessions.db.

    Stored sessions that were not closed are recovered as suspended/disconnected with no runtime handle.

  2. The rail is loaded from SQLite.

    The Svelte route no longer treats an old localStorage rail as the session source of truth.

  3. Chat reading settings have a lightweight workspace representation.

    SessionConversationWorkspace.viewByHistoryId stores only followLatest, an optional native item ID/first sequence/signed viewport offset, and sparse turn expansion booleans. The existing workspace normalizer copies these named fields and discards message graphs or other extra fields inside each view record. This format is a migration prerequisite: session capture, restored-window loading and timeline consumption are not yet fully wired. Source: sessionWorkspaces.ts, sessionWorkspaces.ts.

  4. Selecting a session loads bounded conversation and workspace snapshots.

    The backend uses a window query with a 512 KiB budget and a 2,000-row ceiling for conversation events, plus one normalized workspace row. Live events arriving during a history read are buffered in its existing read record, including the first event that triggers gap recovery. Snapshot replay tops up the SQLite base with the contiguous retained/buffered suffix once per sequence, then publishes the complete projection. Only a real missing sequence, newer generation or buffer overflow needs another read, bounded to three attempts. The buffer uses the existing 20,000-event/4 MiB limits and releases its references on completion, failure, cancellation or stream shutdown. Svelte keeps only the selected session’s large projections. Leaving queues and awaits the SQLite workspace checkpoint before deleting frontend conversation state, so inactive sessions do not accumulate reactive transcripts, editor drafts, or view-state dictionaries.

  5. Attachments are rehydrated by ID.

    Selecting a conversation hydrates sent images from the user events' attachment IDs while the snapshot is loaded. The remote composer checkpoints each saved unsent ID before reading its thumbnail, including a late result for the original owner after selection changes. Uploads for one conversation finish in order, so several selected or pasted images stay in the same draft; Send waits for those uploads and leaves the prompt in place if an upload fails. The ordered write changes only that owner's attachment IDs in its saved workspace. An ID without a visible thumbnail remains a draft until its owner-scoped delete succeeds or that image is actually sent; another paste or send does not clear it. Selection restores only matching rows from that owner's vault. Persisted attachment rows locate the managed files; remote thumbnail metadata appears before up to three background reads fill the Mac vault, and its asset URLs survive repeated opens. Replacing visible draft attachments revokes unused preview URLs, while a pending send or sent message keeps its displayed preview; a duplicate sent-image restore revokes its unused copy. Remote composer and sent-image lightboxes fetch the owner-scoped original in bounded chunks only after a click, display loading while it arrives, and discard the temporary Mac-vault original on close or departure. Local lightboxes continue to read their managed local paths.

  6. History pages in both directions.

    The selected conversation reads complete native items from SQLite under a 512 KiB soft page budget and keeps admitted messages in one TanStack Svelte client until the selection is disposed. Retained content can grow beyond four MiB. An indivisible oversized page item stays complete. Each page contains stable item descriptors, exact required records and represented-turn facts from one read transaction. Raw records are released after translation into canonical messages; the old retained parent journal and replay processor are removed. Older and newer paging accumulates admitted messages and preserves the opposite boundary. Each page stays locked until the client consumes it. Reaching the latest page then resubscribes; an overlapping snapshot refreshes its suffix while retaining the earlier prefix and turn facts. A disjoint authoritative snapshot still replaces the content. Native control state continues to update while a historical window is selected; unrelated live content does not replace that window. The subscription uses an authoritative snapshot and a bounded race buffer on selection and reconnect. It tracks contiguous content separately from current pending controls, so controls sampled after copied content neither conceal a history gap nor revive older requests.

    Completed turn durations use native start/end metadata, not the span of rows currently loaded. The native final assistant identity determines which reply stays outside grouped work. A historical page cannot become the active turn merely because it is the last loaded group. Lightweight per-history reading settings use the existing workspace record; runtime anchor restoration uses the admitted native item. The admitted history uses measured TanStack virtual rows; this storage format alone does not establish interaction or memory acceptance.

  7. TanStack message updates use one published array.

    The pinned @tanstack/ai-svelte@0.24.3 pnpm patch uses $state.raw for messages. TanStack’s processor and Assembly’s custom metadata/tool updates replace changed messages and publish a new array; unchanged message objects do not need another deep reactive wrapper. The adapter also uses ChatClient’s existing no-op developer bridge, avoiding full retained-history diagnostic copies. History admission sends one MESSAGES_SNAPSHOT to reset stream state, followed by at most one assembly:running-tools custom event. The batch restores native unfinished tool state, input, output and metadata in one array update; it removes stale terminal results without republishing the full history for each tool. Individual live tool events continue through assembly:running-tool (conversationMessages.ts, conversationConnection.ts). TanStack’s developer snapshot and fixture panels are unavailable for this chat; streaming, tool parts and native controls still use the same client. 19a · Hosted pull requests

Review hosted PRs in the tab pane.

The Pull requests top tab (labelled with the selected PR's number) searches GitHub PRs across known local projects whose remote is on github.com, or within one selected remote project. Remote choices come from the rail's remote session roots; choosing one sends only that machine-qualified root, so search, detail, file versions, reviews, replies and merges run gh on the machine that owns the checkout, with the same stale-head guards. “All local projects” never mixes machines. The machine that owns the checkout needs GitHub CLI 2.63 or later, because the detail read asks gh pr view for baseRefOid, which the merge guard compares. A project's origin identifies its hosted repository; local branches and diffs are not treated as PR truth. The state (Open, Merged, Closed, All), whose (Everyone, Mine, Needs my review) and the typed text become GitHub search terms in pullRequestSearch.ts, newest activity first. Each plain word typed becomes (word OR head:word OR author:word), so a word, a branch name (GitHub matches head: by prefix) or a login finds its PRs; qualifiers and quoted phrases pass through untouched; a number, with or without #, is searched alone so that PR is found in any state. GitHub has no partial-word match. The list searches once typing pauses for 350 ms, or at once on Enter. git/github.rs sends the query as GitHub's advanced search (ISSUE_ADVANCED, which reads OR and parentheses), adds only is:pr and the projects' repo: terms (one OR group when there are several), and drops rows from any other repository. There is no background poll.

A github.com pull request link clicked in the chat opens that PR in this tab: openUrlInBrowser recognises the link, and the page's openPullRequest handler hands it to the tab through pullRequestSelection.link.
