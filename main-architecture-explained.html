00 · The short answer

Two durable ledgers. One disposable process.

The Svelte interface does not talk to Claude, Codex, or Agy directly. It calls Tauri commands. Rust owns the session, records every normalized event in SQLite, launches an ACP adapter only when work begins, and streams ordered updates back to Svelte.

The easiest accurate mental model is this:

The provider keeps the model’s real conversation context in its own native session. Assembly keeps a second, durable, normalized account of the conversation in sessions.db so the UI can restart, page backward, restore drafts, and audit what happened. The ACP adapter is a translator process between them. When a turn is finished and nothing is still running, Rust disconnects that translator to reclaim memory, but it keeps both durable records and the provider’s native session ID.

What exists now

A real ACP client

The newer Rust backend uses the pinned agent-client-protocol crate, a provider registry, an ACP stdio client, a runtime manager, and a durable SQLite store.

02 · Vocabulary

Protocol, adapter, agent, session.

These words name different layers. Keeping them separate makes the whole system much easier to reason about.

ACP
Agent Client Protocol. A JSON-RPC contract for initialization, sessions, prompts, streaming updates, cancellation, permissions, user input, configuration, and capabilities. It is the language on the wire, not the model.
ACP client
Assembly’s Rust code. It spawns an adapter, writes requests to stdin, reads stdout, answers requests from the adapter, and maps provider-specific updates into one app vocabulary.
ACP adapter
A provider-specific child process. It accepts standard ACP on one side and translates to Codex app-server, the Claude Code adapter, or Agy stream JSON on the other.
Coding agent
The underlying program that performs the actual model and tool work: Codex, Claude Code, or Antigravity/Agy. It may have its own native protocol and transcript storage.
Tauri
The desktop boundary. Svelte invokes named Rust commands in-process; Rust emits named events back to the webview. There is no HTTP server between this UI and its backend.
Sidecar
A child process launched and supervised by the desktop app. Here, it is usually the ACP adapter and sometimes a native provider process beneath it.

03 · Topology

Who talks to whom.

The normal structured path crosses four boundaries. Only the middle boundary—between Rust and the adapter—is ACP.

Svelte webviewComponents, stores, reducer, composer, safe Markdown renderer.
Tauri commands + eventsTyped in-process IPC. No localhost REST API.
Rust runtime managerIdentity, writer lease, SQLite, activation, normalization, recovery.
ACP sidecar over stdioOne JSON-RPC object per line on stdin/stdout.
Native coding agentCodex app-server, Claude Code adapter internals, or agy stream JSON.
Boundary 1

Svelte ↔ Rust

Svelte calls commands such as ensure, send, respond to approval, read snapshot, load older, save draft, and manage attachments. Rust emits agent-conversation-event.

Some of what crosses here is not ours. Tauri’s own plugins register commands on this same boundary, and the Files panel calls three of them directly rather than through a command of ours: plugin-fs to make, rename and watch, plugin-opener to show a path in the Finder, and plugin-clipboard-manager to copy one. plugin-dialog and plugin-notification were already registered and are called from elsewhere. Each plugin is registered in the builder and each carries its own permission in src-tauri/capabilities/default.json.

Boundary 2

Rust ↔ adapter

ACP JSON-RPC 2.0 over newline-delimited stdin/stdout. Requests have numeric IDs; notifications do not; responses resolve pending one-shot channels.

Boundary 3

Adapter ↔ provider

Provider-specific. Codex bridge speaks app-server JSON-RPC. Agy adapter invokes stream JSON. Claude behavior lives in the installed external adapter.

The Workflow Engine reuses this same runtime. Startup constructs WorkflowEngine::managed(agent_runtime.clone()). Workflows are orchestration above the ACP manager, not a second hidden way of talking to agents.

Claude

Manifest ID: claude-agent-acp — @agentclientprotocol/claude-agent-acp 0.70.0, the version CLAUDE_AGENT_ACP_VERSION declares. Its implementation is external to this repository. 05 · Desktop startup

What happens when Assembly opens.

Startup reconstructs durable session metadata first. It does not eagerly start one ACP process per session.

  1. Tauri resolves the application data directory.

    Rust opens sessions.db there and creates or migrates schema version 3.

  2. Rust builds the trusted provider registry.

    It reads the Codex, Claude, and optional Agy executable/hash environment pairs prepared by the launcher.

  3. The runtime manager recovers sessions.

    Stored rows become suspended, disconnected in-memory session records with their native IDs, capabilities, configuration, and next durable sequence. No adapter is attached yet.

  4. Legacy import runs only when appropriate.

    If the database has no owned sessions, the manager can import provider transcript history into the normalized journal rather than discarding it.

  5. Rust starts the stale-sidecar reaper.

    It removes marked adapter process groups whose owning app instance is dead. It does not kill sidecars belonging to a live Assembly instance.

  6. Tauri installs the event emitter.

    Normalized manager events are emitted to the webview as agent-conversation-event.

  7. The Svelte route attaches one event listener.

    It then initializes the terminal service, asks Rust for live PTYs and persisted sessions, reconciles them, and hydrates the rail from SQLite.

  8. Small UI workspace state is restored.

    Open files, split layout, selected child, scroll position, and conversation mode come from localStorage. Provider history and drafts do not.

Resource-saving starts at launch: a hundred suspended rows in SQLite do not mean a hundred adapter processes. Selecting a row loads its journal; the first operation that needs a provider calls activate.

06 · Session creation

When you start a session.

There are three related actions—creating an Assembly record, creating or loading a provider-native session, and creating a process. They intentionally do not all happen at the same moment.

Brand-new structured session

The first prompt creates it

The UI mints an OwnedSession only when the first non-empty composer submission arrives. Rust ensures the row and generation, but provider activation is lazy. Sending that same first prompt activates an adapter, negotiates ACP, calls session/new, saves the returned native ID, records the turn and user message, then prompts.

07 · One message, end to end

What happens every time you press Send.

A structured prompt is both a durable state transition and an asynchronous conversation with another process. The database write is part of the delivery path, not a later best-effort backup.

  1. The composer validates the submission.

    It refuses an empty prompt, a concurrent send, a read-only child view, or a state that cannot currently write.

  2. Svelte clears the visible draft and its SQLite draft.

    If sending later fails, it restores both. Draft durability is no longer just localStorage.

  3. The service chooses the writer path.

    A structured-owned session follows ACP. An explicitly terminal-owned external session writes to its PTY instead. The writer lease prevents both paths from writing at once.

  4. Attachments become typed prompt blocks.

    For structured ACP, persisted image bytes are loaded and encoded as image content alongside text. Capability checks happen before delivery.

  5. The frontend ensures the session metadata.

    The current ownedId, provider, working directory, native ID, and generation are synchronized with Rust.

  6. Rust lazily activates if suspended.

    send_message launches or joins an adapter, initializes ACP, resumes or loads the native provider session, restores configuration, and acquires the structured writer lease. A model or approval policy chosen in the composer is applied next through set_conversation_config: for Claude that is session/set_config_option on the offered model and effort options; an adapter that offers no such option gets session/set_model; either way the session then reports the adapter’s answer, not the request. If activation, configuration, or the prompt itself is refused, the adapter this send started is stopped again.

  7. The generation is checked again.

    A request from an older activation cannot accidentally write into the current one.

  8. Rust creates an Assembly turn ID.

    The turn begins before the provider response. This gives the journal a stable boundary even when the provider uses different internal IDs.

  9. The turn-start event is written to SQLite.

    The manager allocates the next sequence and writes the updated session plus the event in one transaction.

  10. The user message is written to SQLite.

    Assembly records it itself, including attachment IDs. It does not depend on the provider echoing the input.

  11. Only committed events reach Svelte.

    After the transaction succeeds, the live in-memory state changes and Tauri emits the normalized event. The UI is therefore never ahead of the durable journal by design.

  12. Rust sends session/prompt over ACP.

    The prompt contains a provider native session ID plus typed text/image blocks. The ACP client assigns a numeric JSON-RPC request ID.

  13. The Tauri send command returns.

    The provider turn remains active. A background task awaits the ACP response while independent session/update notifications stream.

  14. Each update is normalized, ordered, and persisted.

    Assistant text, reasoning, tools, files, plans, tasks, approvals, usage, warnings, and errors become canonical events and then frontend payloads.

  15. The prompt result closes the turn.

    Rust expires unresolved requests, writes completed/interrupted/failed state, clears active-turn state, and considers suspending the adapter.

The app sends the current prompt, not the entire transcript. The provider resumes its own native context. Assembly’s journal is the durable UI/audit copy; it is not re-uploaded as model context on every message.

08 · Streaming, tools, and questions

A turn is more than assistant text.

ACP can carry a conversation in both directions while the prompt is active. The provider sends notifications, and it can also send requests that require a response from the user.

Provider → Assembly

Streaming updates

The ACP reader recognizes session/update notifications and agent-to-client requests. Updates become typed content: assistant deltas, reasoning, plans, task state, command output, tool calls, file changes, children, usage, context compaction, warnings, and errors. A context_compaction update (the Claude adapter sends one; the Codex bridge sends one on thread/compacted) becomes a contextCompaction payload with the trigger and the token counts before and after, when the provider gives them. Child progress (childUpdate) updates the session’s children and draws no transcript row of its own.

Assembly → provider

Interactive responses

Permission or user-input requests are persisted and displayed. Accept, decline, or supplied input returns through the manager to the pending ACP request. The adapter’s original JSON-RPC request ID ties the response to the right operation.

09 · Resource lifecycle

Yes, it usually shuts down after a turn.

Your understanding is now substantially correct, with one important word: quiescent. Rust only detaches a resumable session after the turn and all related live work are truly finished.

Normal case: the prompt result is persisted, the active turn is cleared, Rust calls suspend_if_quiescent, the ACP session is detached, the sidecar process is gracefully stopped, and the SQLite row becomes suspended/disconnected. The provider-native session is not deleted. The next prompt launches a sidecar and resumes that same native ID.

Suspension is allowed only when all of these are true

Resumable

The adapter advertised resume support and a native session ID exists.

No turn

No active prompt or application turn remains.

No questions

No permission, user-input, or ownership handoff is pending.

No live work

No live tool or registered background work still depends on the runtime.

Dedicated sidecar

Process goes away

Detaching the only session leaves the pool empty, so Rust asks the runtime to detach and removes the pool. The child process receives a graceful stop.

Shared sidecar

Last member turns out the light

If a capability-safe pooled adapter still hosts another active session, removing this session does not stop the shared process. It stops when the pool has no members.

Why the stop is not immediate

The process supervisor sends SIGTERM to the adapter’s whole process group, waits up to three seconds, and then uses SIGKILL as a fallback. The grace period exists because Claude can write its durable transcript shortly after returning the answer; immediate killing previously lost completed turns.

sessions.db schema version 3

Table

sessions

One row per ownedId: provider/native identity, model and effort, working directory/worktree/branch, title/project, state/suspended flag, timestamps, and extensible JSON metadata.

Table

events

Primary key (owned_id, seq), optional turn ID, event kind, serialized JSON payload, and creation time. This is where messages are saved: as ordered event JSON, not in a dedicated messages table.

Table

drafts

One current composer draft per owned session, with an update timestamp.

Tables

attachments + annotations

Attachment identity, MIME, byte count and relative vault path; browser/page annotations store URL, rectangle JSON, note, and timestamp.

SQLite runs in WAL mode with synchronous=NORMAL and foreign keys enabled. A live event write uses an immediate transaction to upsert the session and append the event before anything is emitted to the UI. Deleting a session cascades its events, draft, annotations, and attachment rows; the rail’s Remove does that through delete_agent_conversation_session, so a removed session does not come back at the next launch. The attachment files in the vault are not removed yet (tracked follow-up).

How image attachments are made durable

  1. Rust validates owner ID, maximum size (20 MiB), and PNG/JPEG/GIF/WebP signatures.
  2. It writes a generated filename beneath the owned session’s app-data vault and verifies canonical path containment.
  3. It inserts the attachment row in SQLite. If that insert fails, it deletes the just-written file.
  4. The user-message event stores attachment IDs, so restart replay can reconnect timeline items to indexed files.
  5. Structured send loads the bytes as ACP image content. Raw terminal send can only append managed file paths to text.

12 · Restart and long history

How the conversation comes back.

Assembly reconstructs its view from SQLite and reconstructs provider connectivity by native-session resume. Those are related, but they are not the same recovery operation.

  1. Rust opens sessions.db.

    Stored sessions that were not closed are recovered as suspended/disconnected with no runtime handle.

  2. The rail is loaded from SQLite.

    The Svelte route no longer treats an old localStorage rail as the session source of truth.

  3. Selecting a session loads a bounded snapshot.

    The backend uses a window query with a 512 KiB budget and a 2,000-row ceiling; Svelte rebuilds the timeline from those durable events.

  4. Attachments are rehydrated by ID.

    Persisted attachment rows locate the managed files; browser object URLs are recreated only for the live UI.

  5. Older history pages on demand.

    “Load Older” asks SQLite for another byte-bounded page rather than retaining an unbounded DOM from startup.

  6. The next prompt resumes provider context.

    Activation launches an adapter and passes the stored nativeSessionId to ACP resume/load. It does not paste SQLite history into the prompt.

Provider transcript import

When adopting or migrating provider-owned history, the importer stores a byte-offset cursor in session metadata. Older imported records can receive negative event sequences, leaving zero and positive sequences available for current Assembly activity. When SQLite paging reaches the imported boundary, the frontend can ask Rust to extend the provider transcript import and then query SQLite again.

14 · Native terminal path

ACP and a PTY are different sessions.

Assembly supports a structured ACP conversation and a native interactive CLI/TUI. They can represent the same provider conversation, but only one may be the writer at a time.

Structured-owned

ACP owns writes

The composer sends typed prompt content through the Rust runtime. The UI receives normalized tools, plans, approvals, usage, and messages. Images are first-class content when supported.

Terminal-owned

PTY owns writes

Keyboard input and composer fallback write to a native terminal. Text uses bracketed paste followed by a separate carriage return; attachments are represented as managed paths because a terminal has no typed image channel.

The handoff rule

A session transitions through preparing states while Assembly detaches one writer and activates the other. The writer lease is the proof: structured prompting requires the structured lease, and PTY writes require the terminal lease. If preparation fails, the system can roll back without creating two competing writers.

StructuredOwned
      ↓ prepare + detach ACP
PreparingTerminal
      ↓ terminal acquires lease
TerminalOwned
      ↓ prepare + release PTY writer
PreparingStructured
      ↓ ACP resumes and acquires lease
StructuredOwned

A PTY is a deliberate mode, not ACP transport. The terminal can show a provider’s full native TUI and remains useful for recovery or unsupported capabilities. Its raw bytes are not parsed as ACP just because the command running inside is an agent.

16 · Proposed work

Building Assembly-owned compaction safely.

The journal now gives you enough durable source material to summarize a conversation. It does not by itself let Assembly replace the context inside an existing provider-native session.

Not implemented

There is currently no Rust summarizer service, no “fast tier” backend setting, no compaction artifact or boundary in SQLite, and no evidenced standard ACP method that mutates a session’s context. The contextCompaction event that exists records a compaction the provider performed (its own auto-compaction or /compact); it is a marker in the journal, not a compaction engine.

The minimum safe design

  1. Choose a stable durable boundary.

    Capture through_sequence for one ownedId. Never summarize “whatever happens to be loaded in Svelte.”

  2. Select source material in one backend SQL query.

    Read completed human/assistant content and required tool/file outcomes through that boundary. Exclude streaming deltas and superseded state.

  3. Hash the normalized source.

    A source hash plus boundary makes retries idempotent and proves exactly what the summary represents.

  4. Call a separate one-shot summarizer.

    The Rust backend sends a bounded document to the explicitly configured lower-latency/lower-cost model tier. This should not borrow the active conversation’s writer lease or silently alter it while a turn is running.

  5. Persist the result before applying it.

    Store summary text, boundary, source hash, model/tier, status, token accounting, and timestamps. Preserve the original event journal.

  6. Apply through an explicit provider strategy.

    If the adapter advertises a real provider compaction command, invoke it under the structured writer lease. Otherwise create or fork a new native session seeded with the summary plus the uncompacted tail. Do not pretend that writing a summary row changed the old provider context.

  7. Record the context transition.

    Append the durable contextCompaction event that already marks provider compactions, extended with the summary and the new native-session boundary, so the UI can explain what changed without hiding old messages.

  8. Resume ordinary prompting.

    Only after the compaction state and provider transition are durable should the writer lease return to normal use.

Smallest useful durable schema

compactions
───────────
id                 TEXT PRIMARY KEY
owned_id           TEXT NOT NULL REFERENCES sessions(owned_id)
through_sequence   INTEGER NOT NULL
source_hash        TEXT NOT NULL
summary_text       TEXT
model              TEXT
service_tier       TEXT
status             TEXT NOT NULL  -- pending | ready | applied | failed
created_at_ms      INTEGER NOT NULL
applied_at_ms      INTEGER

UNIQUE (owned_id, through_sequence, source_hash)

A dedicated row makes resumable work, retries, failure recovery, and “which summary was applied?” easy to query. The visible transition should still be an ordinary canonical event so timeline replay remains complete.

Guardrail

Never compact live work

Require the same quiescence checks as suspension: no active prompt/turn, approval, input, handoff, live tool, or background work. Compaction is another writer.

Guardrail

Never delete the journal

Compaction changes future model context; it should not erase the user-visible, auditable history that produced the summary.

Guardrail

Do not assume ACP support

Capabilities or provider command discovery must decide whether in-place provider compaction is possible. Otherwise use an explicit new/forked native session.

Guardrail

Measure the actual context

Trigger from provider telemetry when available; use conservative byte/token estimates when it is not. Message count alone is not a context-window measurement.

What the user should see

A compacted session should retain scrollback and show a small, inspectable timeline marker: what range was summarized, which model produced it, whether the provider accepted it in-place or a new native session was created, and where the full original history remains. Failure should leave the old session untouched and retryable.

Recommended implementation order: first add SQL-derived counts and a context-health DTO; then persist summary artifacts; then add the one-shot backend summarizer; only then implement one provider application strategy with an explicit capability check. That sequence keeps the risky provider-context mutation separate from the useful accounting foundation.
