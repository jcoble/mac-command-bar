Can TanStack AI back Assembly’s frontend chat state?

Keep the current chat for now. TanStack streamed a real Claude reply over Assembly’s unchanged Rust backend. It can back the view, but this spike does not establish a memory saving or safe replacement of the bounded state layer.

Ten-line verdict

  1. SQL can remain authoritative, but Assembly must continue owning the 512 KiB–4 MiB window and trimming.
  2. Incremental text is supported and processing yields to the UI; gap recovery still needs one safe reset rule.
  3. Approval, interrupt and steering can remain Assembly commands and events.
  4. Tool parts are structured and the app controls grouping, summaries and height.
  5. TanStack has recursive sub-agent parts with child transcripts.
  6. Media parts exist; immediate thumbnails and background uploads remain Assembly work.
  7. The custom adapter is transport-neutral, but this spike has only exercised the local path so far.
  8. Memory stability is unproven; process memory grew through repeated switches. Devtools are not a heap profiler.
  9. Fast switching is feasible only with explicit disposal and restore from Assembly SQL.
  10. The client is browser-side TypeScript over a custom Rust/Tauri adapter; no Node process or built-in harness is needed.

42.3 MiB lower final RSS is not proof of a library saving. The prototype still grew 61.4 MiB, generated 8.7% less text (11,450 versus 12,536 characters), and uses a simpler renderer. Its end-of-reply screenshot also loaded an older page before switching restored the tail. A later settled prototype sample fell to 631.6 MiB RSS / 387.1 MiB PSS and 0.21% CPU. There is no matching settled baseline; this reclamation means the earlier growth is not proof of a retained leak. Immediate post-switch CPU was 5.48% versus 6.51% of one core, including settling.

The prototype uses simpler markup and both builds load the client packages. Provider-native context continues across runs, although SQL starts identically. These are Linux debug measurements, not a macOS release prediction or proof that TanStack caused a difference. An earlier exploratory run rose from 663.6 MiB RSS after its reply to 699.0 MiB after ten switches, then 758.9 MiB after paging and ten more switches.

Smallest credible port

  1. Keep: all Rust session management, SQLite, Tauri/WebSocket commands and events, provider-native ids, permissions, attachment uploads, the byte-window reducer, paging and trimming.
  2. Gate first: prove safe reconstruction after gaps and a memory plateau in a release-like run (1–2 days). Stop if either fails. Then add one production custom adapter that translates Assembly events into TanStack chunks and recreates the client after a sequence-gap SQL resync. Estimate 250–400 TypeScript lines.
  3. Replace: the frontend’s incremental assistant/tool/reasoning assembly and turn-loading lifecycle with ChatClient, while projecting only Assembly’s current SQL window into it. Estimate 250–450 lines changed.
  4. Integrate: existing transcript, tool, approval, attachment and sub-agent components against TanStack parts. Estimate 200–350 lines changed; visual components remain.
  5. Delete last: only reducer branches and stream state proven redundant after local and remote parity. Do not delete the SQL projection or window logic. Expected implementation is roughly 700–1,200 changed lines across 5–8 frontend files over 4–7 focused days after the gates pass, plus 2–3 days of native local/remote and memory verification. This is a rough estimate; no Rust change is justified.

Top risks

  • One channel only: registering a second Tauri stream replaces the first (projection_streams.rs:99). The final prototype observes the existing frontend service after event application (conversationService.ts:94,1196).
  • Memory duplication: during migration, Assembly’s timeline and TanStack’s message graph coexist. Devtools add snapshot copies while active.
  • Unsafe gap repair: mid-stream setMessages() does not reset transient processor state. Treat a gap as a client reconstruction boundary.
  • Subscription retention: detach() is insufficient for a persistent subscribe adapter. Every destroyed session view must call dispose().
  • History semantics: TanStack’s built-in paging is count-based and grows the array; using it alone would violate Assembly’s byte cap.
  • Translation surface: Assembly has richer event kinds than the prototype. Approval and uploads should remain Assembly-owned instead of being forced through TanStack’s server conventions.

Persistence boundary: reconstructChat can page parent history when its store honors limit/before; full-array loading is a fallback, not inherent. Its save contract receives complete history, and child reconstruction loads a child without paging. Assembly should retain Rust SQL paging and provider-native resume.
