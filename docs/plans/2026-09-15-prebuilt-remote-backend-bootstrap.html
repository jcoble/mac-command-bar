Restore first-use remote installation with a prebuilt backend package

A new remote machine should not need an Assembly source checkout or Rust toolchain. Assembly should select a prebuilt Linux package, copy it over SSH, install one per-user backend, prove readiness, then save and connect the machine.

Implemented, 2026-09-17. The signed package and clean Workbox installation were proved first. Settings → Connections now uses one native deployment path for explicit Install and Update, followed by the existing authenticated Connect path.

Resolved gap

Commit d80e1306 originally exposed “Save, deploy, and connect,” but built from an Assembly checkout already present on the destination. Commit 00215d7a removed deployment entirely. The implemented flow restores first-use installation without a destination checkout: Install and Update deploy the newest signed backend release, while Connect remains the fast installed-backend path. Remove still deletes only the Mac-side profile.

One installation contract

ConcernDecision
BuildBuild Linux packages before installation. Release CI is the production producer. The Workbox may produce the same package for the first acceptance proof.
Supported targetStart with Linux x86_64, the evidenced Workbox target. Reject unsupported OS/architecture explicitly.
DestinationOne per-user installation: executable and wrappers under ~/.local/bin, configuration under ~/.config/assembly, durable data under ~/.local/share/assembly. No custom prefix in this wave.
TransportThe Mac's signed-in GitHub CLI streams the private release archive and signature without exposing its token to Assembly. The Mac copies the verified archive to a unique remote staging directory over SSH. No destination source checkout is required.
IntegrityA manifest names every package file and SHA-256. The deployment verifies the package before changing the installed service. Release publication signs the manifest.
BootstrapThe installer creates wrappers, a new token when absent, server.env, and the user systemd unit. First server startup creates and migrates sessions.db.
ReadinessThe deploy command proves the signed package is installed, the service and database exist, the binary hash matches, and every port-7777 listener is exactly 127.0.0.1:7777. The existing native Connect path then owns authentication, protocol compatibility and the session-list response; the complete first-use flow succeeds only after both steps pass.
OwnershipSaved connection removal, backend uninstall, and session-data deletion remain three distinct operations.

Delivery sequence

Linux release build→signed archive→explicit Install or Update→SSH staging→verified install→native Connect readiness→save connection
  1. Package checkpoint — complete. The release package has a versioned manifest, deterministic contents, file hashes, release signature, one per-user installer, and focused contract tests.
  2. Deployment checkpoint — complete. The terminal proof verified the signature and package before SSH, installed through one private staging directory, proved the installed service, database, executable hash and loopback listener, and then used the existing Connect readiness path.
  3. Clean acceptance checkpoint — complete. After explicit destructive approval, the Workbox backend was removed and reinstalled from the signed release with zero initial conversations. Remote file safety and a disposable small-project workflow then passed.
  4. Product checkpoint — complete. Settings → Connections separates saved machines from first-time installation. Explicit Install and Update use the same native implementation and then call Connect. The superseded TypeScript deploy command is removed, so there is no second installer path. Uninstall remains a separate future action.

Acceptance receipts

  • The package installs on Workbox without reading an Assembly source checkout there.
  • Package manifest hashes match before installation and the installed executable matches afterward.
  • A clean installation creates schema version 13 with zero sessions, zero events, and zero drafts.
  • The deploy receipt proves the service binds only to 127.0.0.1:7777; the immediately following native Connect proves authenticated protocol readiness and an empty session list. Installation makes no firewall, Docker-network, public-listener or Tailscale-listener changes; SSH is the only network entrance.
  • Failed installation leaves an actionable phase/error and does not report Connected.
  • Remote file refresh/conflict coverage and the end-to-end small-project scenario pass after first install.
  • Idle backend and client adapter processes return to their documented quiescent state.

The clean-slate Workbox removal occurred only after the owner's explicit approval. Normal Install and Update replace package-owned files without deleting the remote database, configuration token, provider sessions, or project files.

Explicitly deferred

Custom installation prefixes, multiple installations for one SSH account, non-systemd targets, automatic dependency installation, Linux arm64 packages, public-network listeners, and a general-purpose deployment framework are outside this wave. Add them only when a real supported target requires them.
