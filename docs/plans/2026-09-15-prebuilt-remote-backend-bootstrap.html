Restore first-use remote installation with a prebuilt backend package

A new remote machine should not need an Assembly source checkout or Rust toolchain. Assembly should select a prebuilt Linux package, copy it over SSH, install one per-user backend, prove readiness, then save and connect the machine.

Owner decision, 2026-09-15. The original first-use deployment behavior was required and must not have been removed. Prove the package and installation lifecycle through a visible terminal-driven Workbox run first. Add product UI only after that real run establishes the correct states and failure messages.

Current failure

Commit d80e1306 originally exposed “Save, deploy, and connect,” but built from an Assembly checkout already present on the destination. Commit 00215d7a removed deployment entirely. Current RemoteConnections.svelte therefore calls Connect, which reads an installed token and fails when no backend exists; Remove deletes only the Mac-side profile.

One installation contract

ConcernDecision
BuildBuild Linux packages before installation. Release CI is the production producer. The Workbox may produce the same package for the first acceptance proof.
Supported targetStart with Linux x86_64, the evidenced Workbox target. Reject unsupported OS/architecture explicitly.
DestinationOne per-user installation: executable and wrappers under ~/.local/bin, configuration under ~/.config/assembly, durable data under ~/.local/share/assembly. No custom prefix in this wave.
TransportThe Mac copies one versioned archive to a unique remote staging directory over SSH. No destination source checkout is required.
IntegrityA manifest names every package file and SHA-256. The deployment verifies the package before changing the installed service. Release publication signs the manifest.
BootstrapThe installer creates wrappers, a new token when absent, server.env, and the user systemd unit. First server startup creates and migrates sessions.db.
ReadinessSuccess requires the service to be active, loopback-only, authenticated, protocol-compatible, and able to return its empty session list.
OwnershipSaved connection removal, backend uninstall, and session-data deletion remain three distinct operations.

Delivery sequence

Linux build→versioned archive→Mac deploy command→SSH staging→verified install→protocol readiness→save and connect
  1. Package checkpoint. Add the package manifest, Linux packaging command, remote install script, deterministic archive contents, and focused tests. Produce one Workbox package and inspect it without touching the installed service. Commit.
  2. Deployment checkpoint. Add a Mac-side terminal command that probes OS/architecture, uploads the matching package, verifies it, installs it, and reports bounded phases. It must never delete session data implicitly. Commit and request independent review of both checkpoints.
  3. Clean acceptance checkpoint. With exact destructive approval, remove the existing Workbox test service, binaries, configuration, and data. Run the Mac deployment command. Verify schema, zero sessions, loopback listener, authentication, Connect, remote file safety, and the disposable small-project workflow. Commit only fixes discovered by the proof.
  4. Product checkpoint. After the observed flow is stable, connect Add Remote Machine to the same native deployment implementation and expose Install/Connect/Update states. Design Uninstall separately. No second installer path.

Acceptance receipts

  • The package installs on Workbox without reading an Assembly source checkout there.
  • Package manifest hashes match before installation and the installed executable matches afterward.
  • A clean installation creates schema version 13 with zero sessions, zero events, and zero drafts.
  • The service binds only to 127.0.0.1:7777 and reaches protocol readiness within a bounded wait.
  • Failed installation leaves an actionable phase/error and does not report Connected.
  • Remote file refresh/conflict coverage and the end-to-end small-project scenario pass after first install.
  • Idle backend and client adapter processes return to their documented quiescent state.

The existing Workbox backend and its data are not removed during the implementation/review checkpoints. That destructive clean-slate step waits at its explicit approval boundary.

Explicitly deferred

Custom installation prefixes, multiple installations for one SSH account, non-systemd targets, automatic dependency installation, Linux arm64 packages, public-network listeners, and a general-purpose deployment framework are outside this wave. Add them only when a real supported target requires them.
