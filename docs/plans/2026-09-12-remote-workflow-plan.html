One complete remote workflow

From Assembly, connect to Agent Workbox, reuse a healthy backend, open an existing folder there, and start or resume a chat. If a compatible backend is missing, the same connection flow offers installation. A project or branch choice never triggers deployment.

Choose machine→Connect / install if needed→Choose remote folder→Start or resume chat

The first supported target is Debian 13, Linux x86-64, using existing SSH keys/configuration. That is the live workbox, not a guessed cloud image. SSH, tar, sha256sum and sqlite3 are available there. Provider installation/login remains a prerequisite; Assembly must explain a missing provider rather than install credentials or silently change accounts.

Keep Svelte → Tauri → Rust → authenticated SSH-forwarded WebSocket → remote Rust/SQLite/provider. Keep existing session IDs, native provider context and saved profile IDs. The local machine never supplies a local path or branch as the remote project by accident.

Approval scope. This document proposes the implementation. No application changes or deployment are performed by writing it. Execution starts with Stage 1 after review; the remaining stages stay bounded by the proof gates below. The full feature is not complete until all final acceptance checks pass.

Stage 1 — Connect to the existing backend

First executable slice: make connection readiness independent of deployment. Prove the existing service can be reached using the wire contract it already supports. Do not rebuild or restart the service, migrate its schema, or create/delete remote sessions in this stage.

  1. Separate saved profile metadata from an active connection. Loading profiles from SQLite must not start an SSH loop for every saved host. Connect on explicit use, including resuming an existing remote session.
  2. Resolve the SSH destination with OpenSSH configuration, respecting the existing username and port. Retain current profile IDs. Reuse one native client for the resolved target; do not create another tunnel merely because the caller is a different draft or saved project.
  3. Open the owned tunnel, complete the existing authenticated WebSocket protocol handshake, and obtain a successful ListSessions response before reporting Ready. A listening port, spawned client task or active systemd unit alone is insufficient.
  4. Expose native connection status and cancellation to the current setup surface. Connect must never call the source-building installer. A missing backend is a distinct “Backend not installed” result; an unreachable host, denied SSH login and protocol mismatch are distinct failures.
  5. Bound the complete connection attempt to 30 seconds. Cancel releases the exact attempt’s processes and pending replies. A failed attempt does not overwrite a saved working profile or its session mapping.

Stage 2 — Replace source-checkout deployment with a managed runtime

Decisive change: users provide SSH details, not an Assembly source repository. Keep Sol’s per-user runtime/data locations for the first target; stop treating a project folder as an installation destination.

Packaging proof before installer coding. Produce a Debian-13-compatible x86-64 runtime bundle from an exact commit in CI, and boot it in an isolated Debian 13 environment. The existing binary links GTK/WebKitGTK. Establish its runtime requirements and provider-adapter contents rather than assuming a standalone binary. If this requires a broad core/headless-crate extraction, stop and revise the plan; that refactor is not pre-authorized.
  1. Extend the existing release workflow with a Linux runtime artifact and signed manifest containing build/protocol version, architecture and hashes. Keep production release artifacts CI-produced. Run the packaging proof as an artifact-only CI job, not the existing release-publication job. Use the existing signature-verification approach, not a new trust system. Do not claim arbitrary VM support.
  2. The native setup operation inspects the known per-user service/configuration and performs protocol readiness. A healthy compatible backend is reused. A missing or incompatible backend produces Install and connect or Update and connect, rather than running a build on every Save.
  3. Download and verify the compatible artifact before transferring it over SSH. Stage it without touching the running service. Check supported OS/architecture, required runtime libraries and provider prerequisites before activation. Report unmet prerequisites without running privileged package installation.
  4. For the first upgrade, require no active remote turn and make a consistent SQLite backup with the remote sqlite3 backup command. The observed database is schema 12; current source is schema 13. Test that migration on a copy first. Never copy only sessions.db while WAL writes may be active. Preserve the previous runtime and backup until the new service passes readiness.
  5. Activate through the existing per-user service, then validate the application handshake and a read-only request. No project/branch change participates. A failed preflight or transfer leaves the current service untouched; a failed activation reports the phase and retains recovery artifacts. Any rollback involving changed SQLite schema must use the tested backup restore while no new work has been accepted.
  6. Use explicit Checking, Transferring, Starting and Ready states, bounded output, one operation owner and functional cancellation. Download and transfer each have a 120-second timeout and stream bounded artifacts to disk instead of retaining their full bytes in memory; startup readiness is bounded to 60 seconds. Cancel before activation discards the attempt, not the existing service. Once activation begins, finish the bounded health/recovery sequence rather than abruptly killing an arbitrary service.
  7. Remove the source-checkout field, remote cargo-build installer and unconditional deployment command from the final path. Keep the local connection name and stable ID. Import existing profile metadata once, then write only the final SQLite format; do not leave legacy and new registries side by side.

Stage 3 — Choose the project after connecting

  1. Add a Connections section to the existing settings surface. One RemoteConnections.svelte owns machine setup/list UI. The draft’s Add/Manage actions open that section; delete the embedded duplicate form.
  2. Offer SSH host suggestions from config/known-hosts on demand. Resolve username/port with ssh -G. Never infer root from a placeholder. No periodic discovery, Tailscale peer scanning or new password storage.
  3. Remove setup’s default-CWD field. A remote draft chooses its folder after selecting a ready machine. Existing default CWD may seed a one-time recent-folder value keyed to that profile; it must not remain the required project selector. Preserve old session/profile IDs.
  4. Extend the remote command vocabulary with a bounded directory browse operation executed by the connected server. Return a canonical path and immediate directory entries, up to 500 entries/512 KiB. Use that same native/Rust route for every remote browse; delete the temporary pre-install SSH directory-listing path once no setup field needs it.
  5. Split typed input into directory and unfinished name. Filter returned names locally; only a directory change such as ~/dev/ triggers another RPC. Enter opens/applies the valid selected folder; Up/Backspace and Escape work predictably. Ignore stale responses and cancel pending reads when the chooser closes or the environment changes.
  6. Create the remote draft with the selected profile ID and remote CWD. Validate the directory on that server. Hide the local branch selector in the remote draft; use the existing checkout as selected, without creating or switching branches. Existing local behavior remains unchanged.

Stage 4 — Prove daily use before calling it done

Run one controlled native sequence against the final client/backend pair. Use an explicitly disposable proof conversation, not an EdiPlatform production task or an existing unfinished conversation.

  1. Connect, open an existing workbox folder, send a short diagnostic prompt, and verify its execution CWD and ordered remote SQLite events.
  2. Switch to a local session and back. The remote turn continues if active; only the selected heavy projection remains mounted. No duplicate agent, connection or transcript is created.
  3. Finish the turn and verify its ACP process is stopped when quiescent. The lightweight environment service is a different lifetime and remains available.
  4. Restart the Mac client and resume the same remote/provider session. Disconnect the client during a controlled turn, reconnect and verify no lost or duplicate displayed events.
  5. Open another remote folder and repeat. Neither project selection nor session switching rebuilds or restarts the backend.
  6. Exercise abort/cancel, denied SSH access, unreachable host, protocol mismatch and failed installation in isolated tests. Restore the original user view afterward.

Resource acceptance

  • No profile-wide reconnect polling on idle startup; one connected target owner at most. Release a client transport when no visible remote context, active turn or pending operation owns it; no idle linger timer. Reconnect on demand. Explicit Disconnect and app shutdown release owned transports.
  • Separate the saved SQLite record, remote environment service, network transport and ACP process lifetimes. Never stop a live turn merely because another session is selected.
  • No CSS relational selectors, idle visual timers or infinite animations. Lists remain bounded and cheap offscreen.
  • Record app and WebView CPU/RSS/physical footprint after warmup, after repeated switching, and after returning idle. Sample idle CPU for at least 10 seconds and observe memory for 60 seconds after 20 switches; investigate sustained growth rather than interpreting one RSS sample as a leak proof. Session interaction remains under approximately 350 ms once data is available.

Execution and scope control

Use the owned remote-workbox checkout, currently based on 4cfe1080. Sol’s main is moving independently (latest observed a4e43c85). Before implementation, recheck both Git states and compare the named files. Integrate relevant completed changes deliberately; never overwrite Sol’s work or treat directory names as branch identity.

Make focused commits as stages pass, with the architecture update in each behavioral commit. Do not merge the overall feature until the final path is complete and obsolete setup code is removed. No compatibility feature flag, duplicate registry or second remote transport. Preserve existing profile/session IDs through a one-time migration rather than maintaining old/new readers forever.

KISS/YAGNI gate: touch only the files named for the active stage. Approximately twice the expected diff, an unlisted file or a required architectural extraction means stop and return a short revised proposal. In-scope corrections are fine; unrelated discoveries are recorded separately, not implemented alongside this work.

Installation/restart/recovery tests are performed only when that stage is authorized, against the stated managed runtime and a consistent backup. Uninstall and data deletion are excluded. Publication or production release activation is a separate concrete action; this planning task performs neither.

Recommended first dispatch: Stage 1 only—native connection/readiness/cancellation against the installed backend, with no build, restart or database migration on the workbox. Its receipt should show a ready connection, existing session access, unchanged deployed executable/service/schema, and clean cancellation. Then use the packaging proof to lock Stage 2’s exact artifact contract before implementing it.
