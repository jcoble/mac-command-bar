Inspector-closed verification

On a restarted native app, ten original-image opens and 20 switches started at 686.9 MiB, peaked at 1414.1 MiB and settled to 682.5 MiB after 60 seconds without an inspector connection or explicit GC. The app/display stopped unexpectedly about 75 seconds into idle (launcher exit 143; display exit 0), so the five-minute result is unavailable. A stopped process is not a memory-recovery sample.

What the evidence supports

  • Remote synthetic streaming traversed the real server, native client and WebView. The fixture emitted 2048 approximately 2.6 KB chunks at 10 ms intervals, crossing the 4 MiB event-window threshold. Post-GC JS size after the stream was 30.96 MiB.
  • After the three completed batches, diagnostics showed one conversation projection, zero snapshot reads, and zero tracked attachment URLs. Total JS node self-size increased only 0.25 MiB across these batches; this does not identify an application retention owner.
  • Early switch snapshots grew from 29.79 to 32.04 MiB, with 2.65 MiB of additional FunctionCodeBlock storage. This is consistent with code warm-up, not proof that every increase is harmless.
  • WebKit RSS had already fallen to 396.4 MiB at 13:31:03.970 UTC, before the batch-1 explicit GC. Attributing the entire earlier drop to forced collection was incorrect and was corrected during independent review.
  • The number-array attachment path is allocation-heavy, but replacing it with raw IPC has not been shown to repair the owner's returning leak. Resync storms and repeated JSON conversion remain hypotheses, not measured retention causes.

Fixture and limits

Two isolated remote sessions were seeded with 1800 turns and 3600 journal events each, approximately 10 MB per session. The image fixture contains a 12,588,868-byte, 2048-square PNG and a 389,343-byte, 360-square thumbnail. The older interrupted lane used an invalid attachment ID; this run corrected the fixture to a UUID and verified both image dimensions. Earlier invalid-image switches are not image proof.

Originals loaded in the real lightbox before each close. The synthetic provider was injected through the existing adapter development override. No paid model, owner database or live assembly-remote service was used. Synthetic plain text is not a reproduction of the owner's tool-heavy sessions.

The large synthetic reply caused CPU-bound rendering. A separate older-page check moved the loaded range from sequence 5513 to 4973 and grew the event window from 487,442 to 1,971,362 bytes; further paging stalled the WebView. That stress branch was stopped and the isolated app restarted. Newer-page fetching, full editor-state acceptance, adverse-network resync behavior and a native retaining owner remain unverified. This is not evidence that the reported leak is absent.
