Fast-switch memory findings

Worktree tsk-808-memprofile · 2026-08-26 · Claude measurement campaign combined with Codex's fixes. Raw table: session scratchpad results-final.md.

Answer: 40 fast session switches (700 ms apart) retain +70…+100 MB of native WebKit malloc (~300k live allocations) in the WebContent process and none of it drains in 5 minutes idle. The JS heap is not the leak (13–17 MB ceiling, creates = evicts + 1, zero stale hydrations). The only subsystem whose removal moved the number is the Files panel, and Codex independently found why: the tree duplicated every loaded file into an editor-owned module map, rebuilt as a full array on every expand/collapse, owned by nothing, so session eviction never reached it.

2. Settled either way

  • JS side is clean. Counters (memprobe.ts): 41 creates / 40 evicts, 0 hydrations landed stale, 0 early bails; the select drain is serial, bodies never overlap.
  • Not animation. Idle CPU after a run: WebContent 0.2–0.3 %, GPU 0.2 % — the measurement floor — with or without spinners. The app holds compositor tiles, it does not redraw them.
  • Graphics plateaus at rest. 5-minute tails: 163→155→155 MB, or 349→236→228 MB. Earlier "keeps climbing" claim retracted (2-min tail caught the decay). Idle graphics wanders ±14 MB; smaller deltas are noise.
  • Malloc is flat at rest. 180→187, 188→189 MB over 5 idle minutes: nothing released, nothing taken.
  • Second WebContent process = the browser-tab child webview (browser.rs:1897-1943) created when a session with the browser panel visible is selected. Expected, not a leak.

4. Open

  1. Owner-observed real-mouse hover effect (80–150 MB, and blocks release on the next switch). Synthetic pointer events and class-toggled hover CSS do not reproduce it; the remaining candidates are native :hover hit-testing and the title= tooltips on the three row buttons (WorktreeAgentRow.svelte:257-263). Needs a real-cursor A/B on a quiet machine: title on/off, hover rules on/off.
  2. Growth curve past 40 switches. One run at 80 says not yet plateaued; a 120-switch run separates "filling a cache" from "unbounded".
  3. Unbounded backend maps activation_locks / broker_statuses (manager.rs:308-311): grow per distinct session, not per switch. Separate one-line task.
  4. WorkingSpinner is still a 3D infinite animation (WorkingSpinner.svelte:199-213). Not this leak, but against the performance rule; replace with a finite/cheap indicator when a spinner is actually on screen.

5. Next

  1. Codex removes the tree→editor map duplication (contents owned once, evicted with the session; tree keeps paths + expansion only). Do not virtualize or re-key first — neither addresses an unowned map.
  2. One 700×40 run on that build with the in-page driver (?fastswitch=700,40) and footprint/vmmap: Δ malloc near 0 → done; partial drop → the remainder is the tree's own per-session cost, then measure virtualization.
  3. Re-measure after each subsystem Codex brings back; the first one that pushes Δ malloc above ~+30 MB is the next retention path.

6. Harness notes (for the next measurement)

  • Driver and counters are dev-only: window.__memprobe, window.__fastSwitch(gap,count), ?fastswitch=GAP,COUNT, ?pointersweep=MS,SEC (fire 20 s after mount).
  • Rank on settled WebKit malloc; Δ needs a state-based baseline (first sample with JS ≥ 3 MB), not a fixed offset — a fixed offset raced three times.
  • Tear down supervisors (tauri, pnpm, vite) before the binary; refuse to launch beside a survivor. One run's whole stack was killed from outside mid-tail (no crash report) — scope pkill patterns by port.
  • Each measurement needs a fresh process because the retained memory never drains.
