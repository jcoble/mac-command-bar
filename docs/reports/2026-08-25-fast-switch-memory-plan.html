Fast-switch memory plan

Worktree tsk-808-memprofile · 2026-08-25 · controller plan, not yet executed

The defect: memory grows with each session switch only when switches come fast, and it never returns after the user stops. Slow switching plateaus. Every prior harness run switched slowly (wait-for-settle between clicks), so it could not see this by construction.

1. What the code says about "fast"

2. Hypotheses, ranked

  1. Resurrected store entries. A detached hydration or editor-content fetch for session A lands after A was evicted and writes A back into a Map (conversationSessions, sessionEditorStates, attachment blob URLs) with no owner left to evict it. Predicts: Map key count grows with fast switches, stays flat with slow.
  2. Skipped eviction. A superseded switch exits before line 1290, so its "previous" id is never released. Same signature as (1), different cause; the counter in E2 tells them apart.
  3. Svelte subtree retained by a pending closure. Transcript/editor components torn down by {#key} while an async callback still references them → detached DOM kept alive. Predicts: heap snapshot shows growing Detached HTMLElement / Detached DOM tree counts.
  4. WebKit-only retention (native, not JS). Rapid DOM churn leaves compositor/backing-store memory that the JS heap never sees. Predicts: JS heap flat in Chrome fixture, but physical footprint of WebContent grows natively.
  5. Backend maps (activation_locks, broker_statuses). Small, grows per distinct session, not per switch. Fix later; not this defect.

3. Experiments

E0 — gap sweep (Chrome fixture, headless, 1710×990)

Script under tauri-svelte-preview/scripts/ (TypeScript) driving /dev-fixtures through Playwright + CDP. Same 6 fixture sessions, 40 switches per run, one run per gap.

Gap between clicksWhat it exercises
3000 msControl: every switch settles. Must plateau (matches prior harness).
1500 / 1000 / 700 msThe overlap band: switch N+1 starts while N's hydration/restore is in flight.
200 msUnder the debounce: collapses to few switches. If this still grows, the leak is in the click path, not the switch.

After each run: 60 s idle, 3× HeapProfiler.collectGarbage, then record: usedJSHeapSize, DOM node count, listener count, Object.keys(conversationSessions).length, sessionEditorStates.size, terminal liveKeys().length, object-URL count. Output one table, gap × metric. Pass/fail: a metric that rises with shorter gap and does not recover after GC is the signature.

E1 — heap snapshot diff

Same script, two runs: 3000 ms gap and the worst gap from E0. Snapshot via CDP HeapProfiler.takeHeapSnapshot after the 60 s quiet + GC. Parse both snapshots (node-side, existing .heapsnapshot format) and report the top 15 constructors by retained-size delta, plus the shortest retainer path to a GC root for the top 5. This is the step that names the leak.

E2 — lifecycle counters (small diff, dev-only)

Add a window.__memprobe object, populated only under import.meta.env.DEV, with monotonic counters: ensureConversationSession creates, evictConversationSession deletes, hydrations started / landed-after-supersede, selectOwnedCurrent entries / early-exits by bail-point line, editor releaseSessionResources calls, blob URLs created / revoked. E0's table reads them. creates − deletes ≠ 1 after quiet = H1 or H2; the bail-point histogram says which.

E3 — native confirmation

Run the app from tauri.dev.next.conf.json, click the same 6 sessions at the worst E0 gap (owner by hand, or a small Playwright-over-WebKit driver if the dev config exposes the inspector), wait 60 s, read read_resource_sample physical footprint for WebContent before/after. Compare to the fixture heap delta: footprint grows while heap is flat → H4; both grow → the fixture reproduces it and E1's answer is the answer.

4. Order, lanes, time

  1. E2 first (Luna Max, tight spec, ~25-line diff across conversationStore.svelte.ts, conversationService.ts, +page.svelte) — ~20 min. Counters cost nothing to add and E0 needs them.
  2. E0 + E1 script (SOL medium, one script file, no app changes) — ~45 min to write, ~10 min per sweep run.
  3. Controller reads the table and snapshot diff, picks the hypothesis. ~15 min.
  4. E3 only if the fixture shows nothing, or to confirm before a fix. ~30 min.
  5. Fix lane (single hypothesis, failing test first) — sized after step 3.

5. What is deliberately not in scope

  • No fixes before E1 names the object.
  • No new abstractions; counters are plain numbers on one window object and are DEV-gated.
  • The two unbounded backend maps get a separate one-line task later.
