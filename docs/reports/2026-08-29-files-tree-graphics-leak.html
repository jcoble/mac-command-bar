The Files tree leaks compositor surfaces

2026-08-29 · branch tsk-808-assembly-wave · production build, measured with footprint

Result. A single session load grows the WebContent process from 122 MB to 969 MB, of which ~450 MB is orphaned compositor surfaces — graphics memory owned by the process but attributed to no live layer. Removing the <Tree> component from the Files panel is the only change that fixes it; graphics returns to its cold value of 41 MB. Nothing the tree renders matters.

1 · The leak is real in production

The first control was whether this was a Vite dev-mode artifact. Dev serves the app as thousands of unbundled ES modules with source maps, and that source text is retained by JavaScriptCore where it appears under WebKit malloc — unreachable from app state and never freed.

Dev inflates the idle baseline roughly 8× on the malloc term, so any ranking taken in dev is distorted. But production still climbs, so the leak is genuine. All numbers below are production.

2 · It is graphics, in one specific process

The app runs two WebContent processes. The second is the browser-tab child webview and is small and malloc-dominated; measuring it instead of the main one produces a flat, misleading trace. Every number here is the main webview.

Processfootprintdominant category
Rust app41–49 MB—
WebContent (browser-tab child)149 MBmalloc
WebContent (main webview)749–1040 MBgraphics, 174 regions ≈ 3 MB each

The Rust backend is not involved. Neither is the JS heap, the DOM, nor the conversation store — all measured clean at the time the process held 720 MB:

  • document.querySelectorAll('*').length → 1,206 nodes
  • conversation projections → 1 session, 220 bytes of reachable character data
  • retained editor states → 0
  • .timeline-scroll scrollHeight → 3,948 px (rules out tiled backing for a tall scroller)

The surfaces are orphaned

Web Inspector's Layers tab accounts for only about 53 MB of live layers (#document 24.78 MB, dv-render-overlay 10.96 MB, ltree-tree 9.95 MB, session-scroll 7.05 MB) while the process reports 507 MB of graphics. The gap belongs to no live layer: destroyed layers whose backing surfaces were never returned. The live-layer list looks near-identical at 120 MB and at 835 MB, so the leak is invisible to the Layers tab by construction.

It ratchets, and it does not drain

Sampled at 15 s for 25 minutes idle: total stepped down 690 → 687 → 686 → 649 and never below, with graphics pinned at 459 MB throughout. At 1 s resolution a single session load spikes to 969 MB and settles at 539 MB — roughly 430 MB is transient, and +417 MB stays. Because one session is enough to pay most of the cost, the curve is sub-linear rather than unbounded, which is why earlier work saw it plateau.

4 · Where that points

Every property of what the tree renders is innocent; only the component itself matters. The remaining mechanism is the virtual-scroll DOM recycling inside @keenmate/svelte-treeview v4.8.0 — rows recycled as the pointer and scroll move over them, and the whole dataset replaced on each session switch. That matches the observed worst case: moving the pointer across rows and then switching produces the largest jump, consistent with recycling churning composited layers and the switch orphaning their surfaces.

Recommendation. Replace @keenmate/svelte-treeview with the TanStack virtualizer the app already depends on. It drives the conversation timeline, which measured flat in every run in this session, so it is proven non-leaking in this exact app and WebKit build. It also removes a dependency rather than adding one, and ends the app having two virtualization mechanisms.

The replacement must preserve expand/collapse, selection, the context menu, search filtering and flat-render mode. It deserves a written contract before implementation.

5 · Corrections to earlier findings

The 2026-08-26 fast-switch campaign reached three conclusions that this measurement revises. The cause in each case is that its __fastSwitch driver switched faster than sessions could load, so it never rendered the content that allocates.

  • "The JS heap is not the leak." True but incomplete. The heap is indeed bounded, but it was read as clearing the frontend; the leaking term is graphics, which that campaign ranked on malloc and described as plateauing at rest.
  • "The Files panel is the only arm that moved the number." Correct subsystem, understated magnitude — it measured a fraction of a 600 MB effect.
  • Native title= tooltips as the hover candidate. Tested directly here and cleared.

Method notes

  • Rank on the main webview's footprint graphics category, not RSS and not the JS heap.
  • Identify the correct WebContent process; there are two, and the wrong one produces a flat trace.
  • Fresh process per measurement — retained graphics never drains, so runs contaminate each other.
  • Measure production. Dev inflates the malloc baseline about 8×.
  • Drive with a real pointer. Synthetic events do not reproduce the worst case.
