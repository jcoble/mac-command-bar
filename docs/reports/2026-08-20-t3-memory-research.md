# T3 Chat memory and responsiveness research for Mac Command Bar

T3 Chat's production client is closed source, so there is no public code receipt that proves why its observed memory stays near 400 MB. The public evidence does establish how it was made to feel immediate; the strongest transferable memory evidence comes from the same team's open-source T3 Code, which explicitly limits hydrated threads, virtualizes long transcripts, evicts inactive detail state, keeps panel state shallow, and bounds worker caches. Receipts: [Theo's open-source statement](https://ww.twstalker.com/theo/status/1931515264497254402), [T3 Code turn limits](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/packages/client-runtime/src/state/threads.ts#L43-L50), [virtual list](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/chat/MessagesTimeline.tsx#L572-L607), [idle eviction](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/packages/client-runtime/src/state/threadRetention.ts#L1-L3), [shallow panel state](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/rightPanelStore.ts#L1-L8), and [worker bounds](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/DiffWorkerPoolProvider.tsx#L48-L77).

The most important Mac Command Bar finding is narrower and more actionable: transcript virtualization, Monaco lazy loading, Monaco model caps, retained-editor caps, and language-server caps already exist, but every owned session still keeps a live xterm view, every right-side panel remains mounted, and conversation detail state has no inactive-session eviction. Those three lifetime mismatches are the best candidates for the reported growth. Receipts: [existing transcript virtualization](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/components/conversation/ConversationTimeline.svelte:98>), [existing Monaco lifecycle](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/components/EditorPanel.svelte:11>), [existing retained-editor cap](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/sessionWorkspaces.ts:427>), [existing LSP cap](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src-tauri/src/lsp.rs:41>), [per-session xterm lifetime](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/components/TerminalSurface.svelte:3>), [eight mounted panels](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/components/RightPanel.svelte:3>), and [conversation state lifetime](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/conversation/conversationStore.svelte.ts:80>).

## What the public history actually says

1. **Verified — the original T3 Chat was local-first.** At 03:09 Theo says chat was a good fit for local-first; at 07:16 he shows projects, threads, and messages stored in IndexedDB through Dexie; at 08:31 he describes streaming a message directly into that local database and reading it through a live query. Receipt: [How I Built T3 Chat in 5 Days, 03:09–08:42](https://www.youtube.com/watch?v=QLvIoi2s1zY&t=189s), with [timestamped transcript](https://lilys.ai/notes/645856).
2. **Verified — that first custom sync architecture was not retained.** In May 2025 Theo announced a move to Convex, and a June 2025 Convex postmortem confirms T3 Chat was using Convex WebSocket subscriptions. In January 2026 Theo described Dexie as the initial core and said the self-built sync concept was one of the first things removed. Receipts: [I changed databases again](https://www.youtube.com/watch?v=xFVh9beupwo), [Convex postmortem, lines 17–25](https://news.convex.dev/how-convex-took-down-t3-chat-june-1-2025-postmortem/), and [I moved off of Next.js, 05:29–06:53](https://podscan.fm/podcasts/theo-t3gg/episodes/i-moved-off-of-nextjs-theo-t3gg).
3. **Verified — the current public data model is reactive and deliberately preloads a small slice.** The Convex postmortem says clients subscribe to query results over WebSocket and that each online T3 Chat user was subscribed to the first 20 messages for preloading. Receipt: [Convex postmortem, lines 23–25 and 68–69](https://news.convex.dev/how-convex-took-down-t3-chat-june-1-2025-postmortem/).
4. **Verified — responsiveness was an explicit product constraint.** In January 2026 Theo described the goal as clicks happening immediately and responses starting as quickly as possible. T3 Code founding engineer Julius Marminge separately described low system-resource use and fast interaction as the reason for T3 Code. Receipts: [Theo, 03:30](https://podscan.fm/podcasts/theo-t3gg/episodes/i-moved-off-of-nextjs-theo-t3gg) and [Julius, 03:09–03:37](https://www.kentcdodds.com/chats/07/08/speed-prioritization-and-maintainability-product-engineering-with-julius-marminge).

**Conclusion — inference from the receipts:** do not copy the original Dexie/custom-sync design. Preserve its user-facing property — navigation and mutations should resolve against an immediate local projection — while using Tauri's Rust/SQLite authority and explicit bounded in-memory views. The later T3 migration is evidence that a bespoke dual-authority sync engine can cost more correctness and complexity than it saves.

## Transferable techniques

### 1. Make the data path local and immediate, but keep one authority

**What T3 does — verified:** the first T3 Chat streamed new content into Dexie and let live queries update the UI; the later version moved authority and sync to Convex while retaining a client-focused application. Receipts: [original local path, 07:16–08:42](https://www.youtube.com/watch?v=QLvIoi2s1zY&t=436s), [Convex reactive subscriptions](https://news.convex.dev/how-convex-took-down-t3-chat-june-1-2025-postmortem/), and [client-focused goal, 05:03](https://podscan.fm/podcasts/theo-t3gg/episodes/i-moved-off-of-nextjs-theo-t3gg).

**Why it feels instant — inference:** a thread selection, rename, or send can render from a local projection immediately instead of waiting for a network or process round trip. This is a responsiveness technique, not by itself a flat-memory technique; loading an entire local database into reactive memory would produce the opposite result.

**Mapping to Tauri/Svelte — recommendation:** keep transcripts, session metadata, file snapshots, and terminal scrollback in Rust/SQLite or bounded Rust rings; expose a small tail plus cursor to Svelte; apply live deltas to that tail; persist asynchronously. Svelte state should be the active projection, not a mirror of every persisted row.

**Where it does not map:** Mac Command Bar does not need browser IndexedDB or a cloud synchronization framework to read its own machine. It also cannot treat PTY output, unsaved Monaco models, or language-server process state as ordinary replicated chat rows. Those resources need explicit owners and teardown rules.

### 2. During streaming, update the smallest stable block

**What T3 Chat does — verified:** Theo describes lexing markdown into blocks, memoizing those blocks, and allowing only the incoming block to rerender; he reports a locked 60 FPS and up to 120 FPS in his test. Receipt: [How I Built T3 Chat in 5 Days, 23:55–26:38](https://www.youtube.com/watch?v=QLvIoi2s1zY&t=1435s).

**Why it feels instant — inference:** completed paragraphs and code blocks retain object identity and skip parsing/reconciliation while only the unstable tail changes. CPU and allocation rate fall between token batches, reducing garbage-collection pauses.

**Mapping to Svelte 5 — recommendation:** derive stable transcript blocks with stable keys; freeze completed blocks; parse and highlight only the current tail block; make tool calls and completed turns independent row components. Preserve existing turn virtualization around these blocks.

**Where it does not map:** Monaco already tokenizes editor models through its own machinery; do not wrap Monaco text in the chat markdown pipeline. Large diffs and terminal ANSI streams also need their native incremental parsers rather than markdown block splitting.

### 3. Bound the hydrated transcript, not only its DOM

**What T3 Code does — verified:** the transcript DOM is virtualized with LegendList, the initial detail window is 10 user turns, older pages add 20, and inactive thread state expires after five minutes without subscribers. Receipts: [`MessagesTimeline.tsx`, lines 546–607](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/chat/MessagesTimeline.tsx#L546-L607), [`threads.ts`, lines 43–50](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/packages/client-runtime/src/state/threads.ts#L43-L50), and [`threadDetail.ts`, lines 76–104](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/packages/client-runtime/src/state/threadDetail.ts#L76-L104).

**Why it keeps memory flat — inference:** virtualization limits mounted elements but leaves source messages in memory. Pagination limits the source array, and TTL eviction releases the inactive thread's subscriptions, derived arrays, messages, and activities. The three controls solve different layers of the same problem.

**Mapping to Mac Command Bar — verified current state and recommendation:** Mac Command Bar already virtualizes one turn per row with overscan 6 and loads older transcript events in 1 MB pages. Receipts: [ConversationTimeline.svelte, lines 98–164](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/components/conversation/ConversationTimeline.svelte:98>) and [conversationService.ts, lines 465–530](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/conversation/conversationService.ts:465>). The missing layer is inactive detail eviction: the global record stores full timelines, child timelines, attachments, agent items, plans, tasks, and recent events for every ensured session, while removal occurs only when the row is explicitly deleted. Receipts: [conversationStore.svelte.ts, lines 78–147 and 201–213](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/conversation/conversationStore.svelte.ts:78>) and [the only explicit removal path](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/routes/next/+page.svelte:1398>). Add a shell/detail split and evict detail after a measured TTL or small inactive-session cap; reload its bounded tail and cursor from SQLite when selected.

**Where it does not map:** an actively running agent may continue emitting events while its detail is cold. Rust must remain the durable event sink, and reactivation must merge the persisted tail with the live sequence cursor without duplication or loss.

### 4. Keep a small hot set and make the cold path genuinely cheap

**What T3 Code does — verified:** visible sidebar rows may prewarm fully hydrated thread detail, but the limit is three because the source explicitly calls each prewarm a renderer-heap and server-load multiplier. Cold opens use a cached snapshot. Receipt: [`Sidebar.logic.ts`, lines 18–24 and 345–360](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/Sidebar.logic.ts#L18-L24).

**Why it keeps memory flat and navigation fast — inference:** the cap prevents the speed optimization from scaling with the entire sidebar, while the cached snapshot prevents a cold selection from becoming a blank loading state.

**Mapping to Tauri/Svelte — recommendation:** retain full conversation detail only for the active session plus two or three recent sessions; retain shell rows for all sessions; prefetch the next likely session's bounded transcript tail only when the machine is idle. Use the existing session identity and transcript cursor rather than creating another cache layer.

**Where it does not map:** do not prewarm Monaco instances, xterm instances, or language-server processes just because their session rows are visible. Those objects have much larger fixed costs than a chat snapshot.

### 5. Store panel descriptors; mount expensive surfaces selectively

**What T3 Code does — verified:** its right-panel store calls itself a shallow workspace model and persists descriptors such as terminal IDs, paths, and preview tab IDs; `ChatView` selects one active right-panel component. Receipts: [`rightPanelStore.ts`, lines 1–8 and 28–47](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/rightPanelStore.ts#L1-L8) and [`ChatView.tsx`, lines 6196–6305](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/ChatView.tsx#L6196-L6305).

**Why it keeps memory flat — inference:** inactive panels retain small serializable state rather than component trees, observers, subscriptions, DOM, caches, and third-party widget instances.

**Mapping to Mac Command Bar — verified current gap and recommendation:** `RightPanel.svelte` says all eight panels remain mounted for the whole session and implements that with eight simultaneous component instances hidden by `display:none`. Receipt: [RightPanel.svelte, lines 3–15 and 45–69](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/components/RightPanel.svelte:3>). Mount the active panel only, and persist only the state users expect to survive — selected path, scroll position, filter, expanded IDs — in the owning store. If a specific panel proves expensive to reconstruct, grant that panel a small keep-alive exception backed by measurement.

**Where it does not map:** T3 Code itself demonstrates that unmount-on-hide is not dogma: visited PR tabs stay mounted because its diff virtualization and markdown parsing made remounting measurably worse. Receipt: [`PullRequestDetailPanel.tsx`, lines 424–436](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/pullRequest/PullRequestDetailPanel.tsx#L424-L436). Use selective exceptions, never “keep everything alive.”

### 6. Lazy-load large modules, then cap what they retain

**What T3 Code does — verified:** it lazy-loads preview, diff, file, and PR-code surfaces, while deliberately prefetching the PR code module and initial diff once the parent panel opens. Receipts: [`ChatView.tsx`, lines 443–447](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/ChatView.tsx#L443-L447) and [`PullRequestDetailPanel.tsx`, lines 469–487](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/pullRequest/PullRequestDetailPanel.tsx#L469-L487).

**Why it feels instant — inference:** startup avoids parsing and initializing code the user has not requested; narrowly timed prefetch moves unavoidable work into a lower-pressure interval after intent is clearer.

**Mapping to Mac Command Bar — verified current state:** Monaco is already dynamically imported only when the editor is visible with an active file; the editor is a single shared instance, external target models have a 24-entry LRU, clean tab models beyond a 24-entry LRU are disposed, and component teardown disposes providers, editor, and owned models. Receipts: [EditorPanel.svelte, lines 11–24, 455–491, and 891–903](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/components/EditorPanel.svelte:11>), [MonacoSourceEditor.svelte, lines 382–392 and 1363–1420](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/MonacoSourceEditor.svelte:382>), and [teardown, lines 2950–3030](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/MonacoSourceEditor.svelte:2950>). Session editor persistence is also capped at 12 paths and three sessions retaining full tab contents. Receipt: [sessionWorkspaces.ts, lines 100–123 and 427–495](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src/lib/shell/sessionWorkspaces.ts:100>).

**Recommendation — inference:** do not redesign Monaco first. Profile its retained models and workers to verify caps work, but direct lifecycle work first at terminals, conversation detail, and the eight always-mounted right panels. Lazy loading lowers startup cost; it does not free a module or instance after it has been loaded.

**Where it does not map:** language servers are OS processes, not JavaScript chunks. Mac Command Bar already starts them only in full mode and caps warm workspaces at five per language with LRU eviction. Receipts: [lsp.rs, lines 35–48](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src-tauri/src/lsp.rs:35>) and [eviction, lines 2267–2325](</Users/blackcolours/dev/work/worktrees/mac-command-bar/tsk-808-assembly-wave/tauri-svelte-preview/src-tauri/src/lsp.rs:2267>). Any lower cap needs native workload measurements because T3 Chat has no equivalent process.

### 7. Move heavy parsing off the UI thread, with finite pools and finite caches

**What T3 Code does — verified:** diff parsing/highlighting uses dedicated workers; the pool is half the logical core count bounded to 2–6, the total AST LRU size is 240, and tokenization skips lines beyond 1,000 characters. Receipt: [`DiffWorkerPoolProvider.tsx`, lines 48–77](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/DiffWorkerPoolProvider.tsx#L48-L77).

**Why it stays responsive and bounded — inference:** parsing does not monopolize the renderer event loop, while fixed pool and cache sizes prevent “more tabs means more workers and ASTs.” Workers alone do not save memory; uncapped workers can make it worse.

**Mapping to Tauri/Svelte — recommendation:** use Rust tasks or a small worker pool for large diff parsing, transcript normalization, and syntax-highlighting preparation that is currently performed in the WebView; return compact rows or tokens. Give every pool, result cache, and pending-job queue an explicit cap and cancellation behavior when its owning panel closes.

**Where it does not map:** xterm's ANSI parser, Monaco's worker topology, and language servers already own their parsing processes. Do not add a second worker layer around them without a profile showing renderer work that can actually be separated.

### 8. Hibernate the view without killing the underlying job

**What T3 does — analogous evidence only:** T3 Code separates shell metadata from detail state and allows cached detail to expire while the authoritative thread continues elsewhere. Receipt: [`threadDetail.ts`, lines 25–32](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/packages/client-runtime/src/state/threadDetail.ts#L25-L32) and [`threadRetention.ts`, lines 1–3](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/packages/client-runtime/src/state/threadRetention.ts#L1-L3). There is no public T3 Chat equivalent of a PTY/xterm lifecycle.

**Mac Command Bar gap — verified:** each owned session gets a permanently mounted xterm host; hidden views keep receiving output; terminated views remain until explicit close. ## What not to conclude

- **Verified limitation:** no public T3 Chat source or heap trace connects its observed memory ceiling to virtualization, Dexie, Convex, workers, or cache eviction. Those causal links remain assumptions until measured.
- **Verified correction:** local-first IndexedDB was the original architecture, not the current production authority. Receipts: [original build talk](https://www.youtube.com/watch?v=QLvIoi2s1zY&t=436s), [Convex migration video](https://www.youtube.com/watch?v=xFVh9beupwo), and [Convex production postmortem](https://news.convex.dev/how-convex-took-down-t3-chat-june-1-2025-postmortem/).
- **Verified correction:** T3 Code does not unmount everything. It selectively retains expensive visited PR tabs where remounting harmed behavior, while keeping only one top-level right-panel surface active. Receipts: [retained PR tabs](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/pullRequest/PullRequestDetailPanel.tsx#L424-L436) and [active top-level surface](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/ChatView.tsx#L6196-L6305).
- **Verified correction:** virtualization alone does not bound source data. T3 Code couples virtualization with windowed loading and idle eviction. Receipts: [virtual list](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/apps/web/src/components/chat/MessagesTimeline.tsx#L572-L607), [turn limits](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/packages/client-runtime/src/state/threads.ts#L43-L50), and [TTL](https://github.com/pingdotgg/t3code/blob/8824f8f24f8b81fd6aed6f228a57a1d4013d01d9/packages/client-runtime/src/state/threadRetention.ts#L1-L3).
- **Inference:** operating-system RSS may not immediately fall after JavaScript or Rust objects are freed because allocators can retain pages for reuse. The acceptance test should therefore require a stable repeated-cycle plateau and falling live-object counts, not insist that Activity Monitor return to the exact launch number after every close.

## Final recommendation

**Assumed until profiled:** start with the three source-proven lifetime multipliers, in this order: inactive xterm views, inactive conversation detail, and eight mounted right panels. Keep the current transcript virtualization/paging, Monaco lazy loading/model caps, retained-workspace caps, and LSP pool caps intact unless measurements show they fail their contracts.

**Verified design pattern from the T3 ecosystem:** the durable rule is not “use Electron,” “use React,” or “use IndexedDB.” It is to make the active path local and immediate, hydrate only a small working set, represent everything else with shallow descriptors, and put a visible numerical bound beside every optimization that keeps expensive state warm.
