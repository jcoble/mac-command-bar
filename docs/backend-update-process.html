Reliable backend updates

Assembly must offer a compatible backend before saying it is up to date. Updating keeps the remote conversations; uninstalling is unnecessary.

TSK-1351 · 1 October 2026 · Plan reviewed by SOL medium before implementation

What failed

Main required protocol 8 while the newest published backend, 0.1.13, still used protocol 7. The version-only status called it up to date. Backend releases required a manually pushed tag; the daily adapter release did not update the backend.

The corrected process

  1. Backend build inputs land on main, or the owner starts the backend workflow manually on main. Explicit backend release tags remain supported.
  2. One release job selects the next patch version from remote backend tags, tests packaging, and builds the triggering commit.
  3. The workflow signs the package and metadata, creates a draft targeting that commit, uploads every asset, then publishes.
  4. Connections verifies the signed metadata and checks protocol compatibility before showing update status. A newer protocol asks for a client update; an older protocol explains that a matching backend release is still needed.
  5. The owner clicks Update. The existing installer downloads directly onto the remote machine, verifies it, preserves data, restarts the service, and reconnects.

Updates interrupt work running in that backend service. Installation remains an explicit action.

Scope and acceptance

Changes are limited to the release workflow, its small version selector and tests, existing remote installer verification, Connections refresh wiring, package tests, and architecture documentation. No new protocol, database, cache, timer, or update setting.

Expected diff: 250–350 lines. Required checks: version selection, package integrity, focused Rust installer tests, frontend type/build checks, and the Connections refresh/error flow. A native install is separate proof from a browser simulation.

Recovery release

Backend 0.1.14 was built successfully from 2c2a2040 with protocol 8. All four release assets are published. This establishes package availability; it does not by itself prove installation on the Workbox.
