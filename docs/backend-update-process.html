Develop and update Assembly without guessing

Desktop, remote backend, ACP adapters, and provider CLIs are separate installations. Each check now explains what it checked and which machine an update affects.

TSK-1351 · Updated October 7, 2026 · Implementation and native checks completed; PR #130 awaits owner merge.

Fast development loop

  1. Pull the desired checkout and run pnpm app:dev. Frontend edits hot reload. Rust changes rebuild through Tauri; restart this command when starting from newly pulled Rust code.
  2. A development desktop uses its checkout. Its Updates screen says this directly and avoids the packaged desktop updater, including the misleading temporary-path error.
  3. For a development build, run pnpm deploy:remote-backend-dev <ssh-host> from tauri-svelte-preview; the host defaults to agent-workbox. It syncs the current checkout, including uncommitted source changes, builds with a persistent remote Cargo cache, and restarts the existing service without signing or publishing.
  4. The development command replaces only the binary and keeps the previous one as assembly-remote-server.prev; it does not touch sessions or configuration. Connections compares the installed package version, so after a development deploy it may still show the last signed release.
  5. Production backend releases come only from main or an explicit assembly-backend-v* tag. The release remains a draft until its signed archive and metadata are uploaded.

Publishing is handled by GitHub Actions. Backend installation is an explicit action and may interrupt work running in that backend service.

Only the selected provider on the selected machine shows update activity. CLI updates do not restart Assembly or its backend. Antigravity’s runtime updates with its ACP bundle.

When the two sides do not match

  • Published backend is older: the message names both protocol versions and explains that a compatible backend release must finish publishing. Reinstalling the same release will not resolve it.
  • Published backend is newer: update or rebuild the desktop from current main before installing that backend.
  • Status cannot be verified: the screen reports unverified compatibility or the check’s error, rather than claiming the machine is up to date.
  • A CLI operation fails: its error is shown and its spinner stops. SSH and provider updater output are retained; failure is not reported as an update success.
