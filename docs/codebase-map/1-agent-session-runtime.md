# Agent session runtime

## What this portion is

This portion owns the Rust side of an agent conversation: it creates and resumes ACP agent sessions, turns ACP messages into a canonical event journal, exposes the session state to Tauri, and reconstructs sessions from SQLite after restart. The manager keeps a live process/request overlay while SQLite keeps durable session identity, lifecycle fields, and events (`tauri-svelte-preview/src-tauri/src/agent_conversation/manager.rs:257-267`; `core/src/session_store.rs:7-21`). The canonical event and session shapes are defined in `agent_conversation/protocol.rs`, while `core/src/protocol.rs` contains a separate generic request/response envelope (`tauri-svelte-preview/src-tauri/src/agent_conversation/protocol.rs:261-285,683-701`; `core/src/protocol.rs:4-62`).

## How it works today

### Session creation, activation, and generations

1. `SessionStore::open` creates or opens the SQLite database, enables write-ahead logging, normal synchronous mode, and foreign keys, then applies schema migrations (`core/src/session_store.rs:119-153`). `AgentRuntimeManager::open` uses that store and invokes the legacy importer only when the store is empty; `with_store` then recovers every stored row into the live session map without starting an adapter (`manager.rs:283-309,2368-2494`).

2. The manager has one `ManagedAgentSession` per `owned_id`. The entry contains the provider identity, native session identity, generation, runtime state, capabilities, sequence counter, active turn, pending requests, transport and process handles, event tail, lease state, configuration, and rail metadata (`manager.rs:104-142`). The manager comment describes this as a live process/request overlay; durable identity, lifecycle, and events are reconstructed from SQLite (`manager.rs:257-267`). A database row without a live entry is not treated as listable: session recovery and listing require an overlay for every stored row (`manager.rs:2381-2394,1586-1623`).

3. `ensure_agent_conversation` calls `ensure`, which serializes activation decisions per `owned_id`, validates the identifier and working directory, normalizes native-session and effort inputs, and requires a native ID for load mode (`manager.rs:522-564`). Ensure initializes or replaces the live overlay and upserts its session row; it does not start an adapter in this step (`manager.rs:614-674`). A generation-zero imported transcript is a stored/listable session with no adapter or capabilities; a later ensure starts a real generation (`manager.rs:569-581`).

4. Ensure reuses an existing generation when provider, working directory, expected native ID, native-session mode, spawn effort, and connection state all match. Otherwise it removes the old live entry and creates the next generation, retaining the same owned event journal and continuing its sequence (`manager.rs:582-613`). Generation and owned ID are part of request identity, and stale generations are rejected by manager guards (`protocol.rs:287-297`; `manager.rs:2527-2566`).

5. `activate` takes the per-session lifecycle lock and calls `activate_locked`. It can reuse an already connected runtime, starts only from `Starting` or `Suspended`, and uses a shared adapter pool when provider capabilities advertise multi-session support; otherwise it uses an isolated pool key (`manager.rs:677-778,779-852`; `manager.rs:91-102`). The adapter initializes ACP, then resumes, loads, or creates the native session. A resume/load failure releases the pool and either starts fresh when there is no user history or leaves the session suspended with a recoverable `session-resume-failed` error (`manager.rs:731-897`).

6. Activation installs the provider capabilities, commands, native session ID, configuration, transport, ordered event channel, and structured writer lease into the live overlay, then records the connected/ready lifecycle event (`manager.rs:929-1018`). `send_agent_conversation_message` activates first, applies optional model, reasoning-effort, and approval-policy values, converts ordered content blocks, and calls `prompt` (`mod.rs:104-136`; `prompt_content.rs:28-64`; `manager.rs:1021-1102`).

7. A prompt creates a turn ID, rejects a second active turn or a terminal writer, records `Turn Started` and a user message, derives the first title from the first prompt line when no title exists, and sends ACP prompt parameters containing a session ID and ordered text/image blocks (`manager.rs:1021-1102,2735-2748`; `protocol.rs:550-567`). User message payloads carry attachment IDs so a journal record can find the screenshots after restart (`protocol.rs:550-567`).

8. A session can suspend only when it is ready, has a native session ID and resume capability, has no active turn, pending approval or input, live tools, background work, one-shot request, writer transition, or existing suspension operation (`manager.rs:4378-4395`). Suspension detaches the transport without closing the native session, records disconnected/stopped state, retains the native ID and event journal, and changes the native-session mode back to resume (`manager.rs:1702-1783`; `providers/mod.rs:105-127`). The next send activates the provider again and resumes that native session (`manager.rs:686-897`).

9. Close expires pending approvals and inputs, cancels child scans, records closed connection/lifecycle events, closes the native session, and releases the adapter pool. Releasing the last pool member closes the whole runtime; releasing a member for suspension detaches it without destructive close (`manager.rs:1785-1896,379-421`; `providers/acp.rs:197-211`; `providers/acp_client.rs:795-842`).

### Adapter process lifetime

The current ACP path starts a sidecar only from `activate_locked`: `AcpRuntimeAdapter::initialize` asks `AcpClient::spawn_with_environment` for a transport, and the client starts `SidecarProcess::spawn_with_environment` (`manager.rs:779-852`; `providers/acp.rs:156-172`; `providers/acp_client.rs:453-480`; `providers/process.rs:118-171`). The sidecar receives a visible command marker and owner/session marker, runs in a new process group, has piped JSON input/output and bounded stderr, and is configured to stop when its process handle is dropped (`providers/process.rs:118-171`).

The process remains while a turn, approval, structured input, live tool, or background task is active. When the prompt result arrives and the session is quiescent, the manager detaches and removes the adapter process while keeping the native session ID for a later resume (`manager.rs:3621-3632,4378-4395`; `providers/acp_client.rs:837-842`). The sidecar process group is terminated with a group `SIGKILL` by the handle stop path and by `Drop` (`providers/process.rs:224-257`). Closing the last session in a shared pool closes the native sessions and the transport (`manager.rs:379-421`; `providers/acp_client.rs:795-815`).

At application startup, the reaper writes an app-instance identity below `app_data_dir/instances`, scans marked process groups, skips groups belonging to a live owner or live session, and sends `SIGTERM` followed by `SIGKILL` after a two-second grace period when the owner is dead (`reaper.rs:13-18,74-97,139-221`).

The directory also contains an older direct-process path. `ConversationProcess` launches a named program directly with `COMMANDBAR_SESSION_ID`, a fresh process group, piped streams, and kill-on-drop (`process.rs:8-93`). `provider.rs` uses it for direct `codex app-server` and Claude stream-json commands, while the current module declarations expose the ACP provider modules instead (`provider.rs:13-51,78-145,261-318`; `mod.rs:3-14`).

### Provider adapters

`ProviderRegistry` registers the bundled `codex-acp`, `claude-agent-acp`, and `agy-acp` manifests with pinned versions, ACP stdio transport, empty argument lists, and bundled sources. The environment loader requires the executable path and SHA pair for each configured adapter, and Codex and Claude must be configured as a pair; the registry rejects missing manifest fields, `latest`, `@latest`, `npx`, non-absolute executables, and non-existent executable paths (`providers/mod.rs:129-239`; `capabilities.rs:14-38`). The current capability-version constants are Codex `1.1.9`, Claude `0.23.1`, and Antigravity `0.1.0` (`capabilities.rs:10-12`).

`AcpRuntimeAdapter` owns one ACP client reference for one manager pool member. It provides initialize, new session, load, resume, detach, close, prompt, prompt-once, configuration, and command access through `AgentRuntimeAdapter` and `StructuredRuntimeHandle` (`providers/acp.rs:15-22,105-211,214-323`; `providers/mod.rs:105-127`). `AcpClient` sends ACP initialize/session JSON-RPC, retains per-native-session state, routes updates by native session ID, maps request IDs for permissions and structured input, and reports transport closure to the manager (`providers/acp_client.rs:40-57,71-149,367-435`).

Codex and Claude have local transcript discovery and projection implementations; Antigravity has no local transcript path and returns an error for transcript reads (`transcript/mod.rs:85-126`; `transcript/codex.rs:17-25`; `transcript/claude.rs:13-34`). Claude has a provider-specific extra-model list in the ACP client (`providers/acp_client.rs:445-451`). The adapter capability object supplies the provider-specific implementation, session, prompt, interaction, configuration-option, and command details to the manager (`protocol.rs:136-190`).

The manager's child-rollout scan is enabled for Codex and runs on a ten-second interval while a Codex child is active; Codex transcript discovery also recognizes parent and sub-agent records, while Claude's child records come from its project `subagents` files (`manager.rs:44-46,1104-1173`; `transcript/codex.rs:27-118`; `transcript/claude.rs:220-281`).

### ACP events and request routing

The wire event is `AgentEvent`: an event type, owned ID, provider, provider-instance ID, generation, sequence, timestamp, optional native session/turn/item/request IDs, a `BTreeMap` payload, and optional provider metadata or a redacted raw-frame reference (`protocol.rs:242-285`). Event types include session, turn, item, content, approval, user-input, plan, task/child, command, usage, rate-limit, warning, and error events with the serialized names listed in `AgentEventType` (`protocol.rs:192-240`). The tagged `AgentConversationPayload` variants carry connection state, user/assistant messages, tool state, children, approval/input requests and resolutions, plans, turns, commands, usage, terminal projection, and errors (`protocol.rs:436-524`).

The payload variants have these shapes: connection carries state and an optional native session ID; user messages carry item ID, text, completion, and attachment IDs; assistant deltas/messages carry text; tools carry item ID, name, state, and optional summary; child updates carry child ID, parent tool-call ID, optional label, state, and latest activity; approval carries request ID, state, and summary; input requests carry request ID, title, optional description, and fields; input resolution carries request ID and cancellation; plans carry plan items; turns carry turn ID and state; command updates carry descriptors; usage carries optional input/output/used/context counts; terminal projection embeds its provider/native/item/payload fields; errors carry code, message, and recoverability (`protocol.rs:443-523`).

`AgentConversationSessionRecord` is the durable/list response shape: owned ID, provider, optional model and effort, working directory, lifecycle state, suspension, creation/activity timestamps, optional active turn and native session IDs, pending-permission and pending-input flags, and flattened worktree, branch, title, project, PTY, origin/source, cmux, resume command, completion/settlement, task, pull request, message count, latest-turn preview, and scanned-activity metadata (`protocol.rs:653-701`). `AgentConversationConnection` carries owned ID, provider, generation, optional native ID, connection state, and configuration; `AgentConversationSnapshot` adds suspension, last sequence, and the recent canonical events (`protocol.rs:633-651`).

The lifecycle enums distinguish runtime state (`Starting`, `Ready`, `Working`, `WaitingApproval`, `WaitingInput`, `Interrupting`, `Suspended`, `Failed`, `Closed`), execution owner (`Structured`, `Terminal`, `TransitioningToStructured`, `TransitioningToTerminal`, `Stopped`), and connection state (`Disconnected`, `Connecting`, `Connected`, `Reconnecting`, `Failed`, `Closed`) (`protocol.rs:30-52,346-380,391-399`).

ACP inbound updates enter one transport receiver. The manager creates an ordered channel for each live session and uses the channel to serialize updates, prompt results, and terminal projections before they reach persistence and the frontend (`providers/acp_client.rs:71-92`; `manager.rs:2762-3064`). A candidate copies all event-owned fields, writes the session row and event row in SQLite, and only then applies the candidate to the live session and advances the in-memory sequence (`manager.rs:144-224,2569-2733`; `core/src/session_store.rs:262-313`). The event write is capped in SQLite at the newest configured rows, while the live snapshot keeps at most 2,000 events and normal event reads are capped at 10,000 (`manager.rs:38-48`; `session_store.rs:434-508`).

ACP updates can change configuration, emit lifecycle/item/content/plan/task/child/usage events, or request permission and structured user input. Permission request IDs use `perm-N`, input request IDs use `input-N`, and the manager records waiting state before forwarding the request; responses carry the same owned ID, generation, request ID, and optional turn/item identity (`manager.rs:2762-3064`; `protocol.rs:287-344`). Routing first uses native session ID, then a unique matching live session or active turn; ambiguous updates are dropped (`manager.rs:3157-3202`).

When a turn settles, the ordered pump records completed, interrupted, or failed turn state, clears the active turn, and lets the quiescence path suspend the process (`manager.rs:3395-3632`). Resume replay is marked separately; if display events already exist, replay-tagged updates are discarded so stored items are not rendered twice (`manager.rs:2762-3064`; `core/src/session_store.rs:474-488`).

Tests name the runtime contracts directly: `ensure_is_idempotent_and_generation_rejects_stale_writers`, `restart_recovers_sessions_from_store`, `turn_completion_suspends_and_stops_the_runtime`, `pool_shares_one_process_across_two_sessions`, `last_session_close_kills_process`, `resume_failure_without_user_history_starts_fresh`, `resume_failure_with_user_history_stays_suspended`, `load_replay_populates_two_turns_once_across_repeated_ensure`, `failed_event_write_leaves_memory_and_dispatch_unchanged`, and `transport_exit_emits_connection_failure_and_recoverable_error` (`manager.rs:5669-5670,5920-5921,6441-6442,6507-6508,6522-6523,6565-6566,6652-6653,7488-7489,7654-7655,7771-7772`). Store tests include `open_creates_schema_and_reopens`, `session_and_event_commit_is_atomic_and_caps_events`, `recent_event_page_is_bounded_and_keeps_transcript_order`, `drafts_roundtrip_and_clear`, `annotations_roundtrip_and_cascade_on_session_delete`, and `crash_safety_recovers_committed_wal_rows` (`core/src/session_store.rs:814-868,955-1005,1032-1053,1110-1205,1208-1256`). Protocol, provider, transcript-import, and terminal-projection tests name their wire, manifest, bounded-import, and watcher contracts (`protocol.rs:709-792`; `providers/mod.rs:246-270`; `transcript_import.rs:413-670`; `terminal_projection.rs:357-573`).

### Transcript reading and import

The transcript reader accepts Codex or Claude and a safe session ID, dispatches to the provider parser, and reads only complete JSONL records from a bounded tail of up to four megabytes (`transcript/mod.rs:85-126,158-230`). Codex searches `.codex/sessions` and `.codex/archived_sessions`, maps user and assistant messages to historical item events, maps turn context to configuration, token counts to usage, and sub-agent activity to child updates (`transcript/codex.rs:17-118,143-284`). Claude searches `.claude/projects`, filters parent and sidechain records, maps user/assistant text, model/effort/permission mode, usage, and child-agent files (`transcript/claude.rs:13-34,36-133,220-281`).

`import_session` takes the bounded oldest-first tail, creates a session row, stores the cursor (`transcript_path`, `cutoff_offset`, `reached_start`) in `extra_json`, and writes each projected record as a full `AgentConversationEvent` payload. `extend_session` reads an older bounded tail ending at the cursor and assigns negative database sequence numbers before the existing zero-or-higher events (`transcript_import.rs:16-23,34-175,177-245`). The import path limits the read to one megabyte or 2,000 records from the Tauri command layer (`mod.rs:362-393`).

The imported event keeps an embedded event sequence of zero when its database sequence is negative; the database sequence orders imported history, while live streaming compares the embedded sequence only after activation (`transcript_import.rs:177-222`). A later extension merges the cursor with all other session `extra_json` fields (`transcript_import.rs:248-273`).

### Terminal projection, attachments, and handoff

The terminal projector stores a canonical file identity, byte offset, partial line, and a bounded set of seen stable keys. It polls every 250 milliseconds, reads at most one megabyte incrementally, reconciles every 40 polls with at most 512 records, and projects each record as a `TerminalProjection` event with a redacted raw reference (`terminal_projection.rs:15-19,43-171,280-305`).

Attachment save accepts image bytes up to 20 MB, checks PNG/JPEG/GIF/WebP signatures, writes `screenshot-<uuid>.<extension>` below the application-data attachment root, and inserts a row containing the relative path. It removes the file if the row insert fails; deletion verifies that the requested path remains below the owned-session directory before deleting the row and file (`attachments.rs:8-19,29-77,102-164`).

Handoff requests carry owned ID, generation, direction, mode, phase, a history boundary, and a process-tree assertion. Terminal acquisition requires a live TUI, exactly one registered user PTY, zero sidecars, and a PTY session ID; release requires the corresponding released proof. The command prepares the manager transition, detaches structured transport for a same-session terminal handoff, validates history and identity, commits the new owner, or rolls back the transition (`handoff.rs:7-136,138-193`; `manager.rs:1898-2177`).

## Why it is the way it is

- The runtime and event/ownership/config shapes were frozen together in commit `c78e3dd`; the source now carries those shapes in `AgentEvent`, `AgentConversationPayload`, capability, lease, and transition types (`protocol.rs:136-190,192-240,261-285,346-380`; commit `c78e3dd`).
- SQLite is the durable session truth, while the manager map is the active process/request overlay. Commit `b638155` introduced the SQLite session store, provider-shared adapter pool, and quiescent suspension; the manager comment records that the two layers serve durable reconstruction and live runtime access (`manager.rs:257-267`; commit `b638155`).
- The adapter process is stopped after a quiescent turn because the process tree retains hundreds of megabytes between turns; the native session survives and is resumed by the next send (`manager.rs:3621-3625`; commit `f12bf30`).
- Lifecycle operations use a per-session lock so ensure, activate, suspend, close, and handoff do not mutate one session concurrently (`manager.rs:522-541,2180-2252`; commit `9685aef`).
- Session row and event row are written in one immediate transaction. The store comment says this prevents a failed event insert from leaving the session ahead and caps the journal before the transaction becomes visible (`session_store.rs:262-313`; commit `a2236e2`).
- A replacement generation keeps the same owned event journal and continues its event sequence, so stale writers can be rejected without creating a second journal (`manager.rs:596-613`; commit `270b09b`).
- Stored sessions are recovered as suspended, and capability objects are parsed during recovery so later resume has the information required to activate (`manager.rs:2381-2494`; commit `998621`).
- A resume failure with no user history can start a fresh native session; a resume failure after user history leaves the session suspended and records a recoverable error (`manager.rs:858-897`; commits `3a631c6`, `7eb6f6d`).
- Resume replay is filtered when display events already exist because replay had previously been persisted into canonical journals and caused duplicate rendered items. The replay filter is keyed on persisted display-event presence and stable item identity rather than rendered text (`manager.rs:2762-3064`; commit `cce129e`).
- The first prompt supplies a title from its first trimmed line, capped at 64 characters, because raw UUIDs had previously appeared as titles; explicit stored titles remain authoritative (`manager.rs:1058-1068`; commit `dd54fb9`).
- Transcript reads use a bounded tail and complete-line cutoff. The transcript history records that a full transcript was not copied on resume and that a bounded byte/record page was needed (`transcript/mod.rs:15,221-230`; commit `8aab513`).
- Transcript extension stores older records with negative database sequence numbers, keeping existing nonnegative event numbers unchanged (`transcript_import.rs:109-175,177-222`; commit `30ce778`).
- Transcript import was added as two commands because the reader and store writer existed without a caller; the import is bounded to one megabyte or 2,000 events (`mod.rs:362-393`; commit `95b32f1`).
- Imported rows are written as whole `AgentConversationEvent` values and recovered into live overlays because an earlier import shape could not be decoded by stored-event reads and had no corresponding live entry (`transcript_import.rs:177-222`; commit `06147a5`).
- The startup reaper records an app instance and only signals process groups with visible owner/session markers after proving the owner is dead; it uses a two-second `SIGTERM` grace period before `SIGKILL` (`reaper.rs:74-97,139-221`; commit `ba9ea64`).
- Terminal output goes through the same journal-backed event stream as ACP output, so a terminal-owned session still has canonical event records (`manager.rs:1643-1660`; commit `cfc4c96`).
- Screenshot attachment IDs were added to user-message records because the in-memory association between a sent screenshot and its message disappeared after restart; old records decode with an empty attachment list (`protocol.rs:448-456,550-567`; commit `e3eca0e`).
- The older pre-ACP provider layer was removed from the active module graph during the provider cutover; the remaining `provider.rs` file still contains the old direct runner but is not declared by current `mod.rs` (`provider.rs:1-13`; `mod.rs:3-14`; commit `beb5967`).
- The core store was introduced as a SQLite-backed set of sessions, events, drafts, and annotations with WAL recovery and retention behavior (`session_store.rs:119-254,256-600`; commit `7276816`).

## What is stored, and where

### SQLite database

`SessionStore` uses schema version 2 (`core/src/session_store.rs:7`). It enables WAL, `synchronous=NORMAL`, and foreign keys when opening the connection (`session_store.rs:133-148`). The schema contains:

- `sessions`: `owned_id` primary key; nullable `native_session_id`, `model`, `effort`, `worktree`, `branch`, `title`, and `project`; required `provider`, `cwd`, `state`, `created_at`, `last_activity_at`, and `extra`; and integer `suspended` constrained to zero or one (`session_store.rs:155-218`).
- `events`: `owned_id` foreign-keyed to `sessions` with cascade delete, `seq`, nullable `turn_id`, `kind`, `payload`, `created_at`, and composite primary key `(owned_id, seq)` (`session_store.rs:155-218`).
- `drafts`: one row per `owned_id`, with non-null `text` and `updated_at`, foreign-keyed with cascade delete (`session_store.rs:155-218,510-550`).
- `annotations`: integer `id`, foreign-keyed `owned_id`, `url`, `rect`, `note`, and `created_at`, plus `annotations_owned_id_idx` on `(owned_id,id)` (`session_store.rs:155-218,552-600`).
- `attachments`: text `id` primary key, foreign-keyed `owned_id`, `file_name`, `mime_type`, `byte_length`, `relative_path`, and `created_at`, plus `attachments_owned_id_idx` on `(owned_id,file_name)` (`session_store.rs:9-21,155-241,602-658`).

Version zero creates the sessions, events, drafts, annotations, and attachment tables and sets `user_version` to 2. Version one adds only the attachment table/index and leaves existing rows unchanged; version two is a no-op; any other version returns an unsupported-schema error (`session_store.rs:150-248`).

The manager writes session rows and event rows through `upsert_session_with_event`; this also updates activity and deletes events older than the configured newest-event cap (`manager.rs:2569-2733`; `session_store.rs:262-313,490-508`). Draft commands write `drafts`, annotation commands write `annotations`, transcript import writes `sessions` and `events`, legacy import writes `sessions` and `events`, and attachment commands write `attachments` (`mod.rs:52-88,138-164,414-450`; `legacy_import.rs:15-126`; `transcript_import.rs:34-222`; `session_store.rs:510-658`). `SessionStore::delete_session` removes the session row; the foreign-key cascades remove its events, drafts, annotations, and attachments (`session_store.rs:347-353,155-218`).

### Session row and `extra_json`

The durable `SessionRow` stores owned ID, native ID, provider, model, effort, working directory, rail metadata fields, lifecycle state, suspension flag, creation/activity timestamps, and `extra_json` (`session_store.rs:64-81`). The manager places generation, native-session mode, ownership, configuration, capabilities, rail metadata, and transcript-import cursor values in that JSON object (`manager.rs:2278-2357`; `transcript_import.rs:16-23,248-273`). A recovered row starts with no runtime, transport, or ordered event sender; non-closed rows with native IDs are reconstructed as suspended so activation can resume them (`manager.rs:2381-2494`).

### Files on disk

Attachments are stored under the application-data directory at `conversation-attachments/<owned_id>/screenshot-<uuid>.<extension>`, while the database keeps the owned-session-relative path (`attachments.rs:118-145,29-77`). Codex transcripts are read from `.codex/sessions` or `.codex/archived_sessions`, and Claude transcripts from `.claude/projects`; these files are read as source data rather than copied wholesale into the store (`transcript/codex.rs:17-25`; `transcript/claude.rs:13-34`; `transcript/mod.rs:221-230`).

The reaper writes app identity files under `app_data_dir/instances/<pid>-<start>.json` (`reaper.rs:74-97`). The legacy importer reads `legacy-owned-sessions.json` and `legacy-agent-events.jsonl` from its configured legacy root and writes their contents into SQLite (`legacy_import.rs:11-13,15-126`).

## Contracts other portions rely on

- Event consumers rely on the serialized `AgentEventType` names, the `AgentConversationPayload` `kind` tag, and the canonical event fields `owned_id`, `provider`, `generation`, `sequence`, and optional native/turn/item/request identifiers (`protocol.rs:192-240,261-285,436-524`).
- Request handlers rely on `AgentRequestIdentity` matching owned ID, generation, request ID, and optional turn/item IDs; approval and input responses flatten that identity into their response shapes (`protocol.rs:287-344`).
- Session list and recovery consumers rely on `AgentConversationSessionRecord` fields, including native ID, lifecycle state, suspension, timestamps, pending-request booleans, and flattened rail metadata (`protocol.rs:653-701`; `manager.rs:1586-1623`).
- ACP adapters implement `AgentRuntimeAdapter` with initialize, new/load/resume, detach, and close. Detach keeps the native session resumable while stopping transport (`providers/mod.rs:105-127`).
- ACP clients use newline-delimited JSON-RPC over the sidecar process, with `session/update`, `session/request_permission`, `session/request_user_input`, and `session/request_input` as the manager-facing update/request methods (`providers/acp_client.rs:26-38,367-435`; `manager.rs:2762-3064`).
- Prompt callers pass `SendAgentConversationMessageRequest` with text, ordered content blocks, attachment IDs, and optional model/approval policy; ACP parameters are shaped as `{sessionId, prompt:[...]}` (`protocol.rs:550-567`; `manager.rs:2735-2748`; `prompt_content.rs:28-91`).
- Durable event readers rely on `(owned_id, seq)` ordering, `list_events` pagination, `latest_seq`, `has_display_events`, and bounded recent-event ordering (`session_store.rs:392-488`).
- Draft and annotation callers rely on `drafts` being keyed by `owned_id` and annotations being returned in ascending ID order (`session_store.rs:510-600`).
- Attachment callers rely on attachment IDs, owned-session-relative paths, MIME type, byte length, and the 20 MB image validation rule (`attachments.rs:11-19,29-77,147-164`).
- Provider startup relies on the registered manifest IDs, pinned versions, executable/SHA environment pair, `COMMANDBAR_SESSION_ID`, `COMMANDBAR_OWNER_INSTANCE_ID`, and visible process marker environment values (`providers/mod.rs:129-239`; `providers/process.rs:118-171`; `reaper.rs:13-18,63-72`).
- Terminal projection consumers rely on `TerminalProjectionPayload` carrying the provider instance ID, native session ID, optional item ID, payload map, provider metadata, and redacted raw-frame reference (`protocol.rs:248-259`; `terminal_projection.rs:280-305`).
- The generic core command layer relies on `CoreRequest` with `id`, `action`, `dryRun`, and `payload`, and `CoreResponse` with `id`, `ok`, `summary`, `data`, `warnings`, and optional `proposedCommand` (`core/src/protocol.rs:4-50`).
- The Tauri command names and purposes are the commands listed in `mod.rs:52-450` and `handoff.rs:138-193`; their input and output types are the protocol and store shapes described above.

## Known gaps

- `legacy_import.rs` describes itself as a one-time cutover importer and says the module is to be deleted after the SQLite migration window closes (`legacy_import.rs:1`).
- `AcpClient` retains methods marked `dead_code` with the comment “Track B calls this after manager multiplexing cutover”: multi-session new/resume, `set_model_on`, `close_session`, and `commands_on` (`providers/acp_client.rs:587-604,778-819,952-953`).
- Antigravity does not expose a local transcript path; discovery returns none and durable-line projection returns no records for that provider (`transcript/mod.rs:100-124,143-155`).
- `provider.rs` is present in the directory but is not declared by the current `agent_conversation/mod.rs`; its code references the older direct-runner registry and command types (`provider.rs:1-13`; `mod.rs:3-14`).
