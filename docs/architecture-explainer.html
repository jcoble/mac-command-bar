mac-command-bar: how the desktop app is put together

A reference for someone fluent in C# and SvelteKit who has not written Rust and has only passing familiarity with Tauri. Every claim points at a real file under tauri-svelte-preview/, so this doubles as a map of the codebase. C# comparisons appear throughout, including the places where the comparison stops being true.

1The big picture

The app is one native macOS window whose entire visible surface is a webview rendering a SvelteKit page. Everything that touches the operating system — files, git, child processes, SQLite, language servers, extra webviews — lives in Rust. The two halves talk over a single narrow channel: the frontend calls invoke('command_name', args), and a Rust function annotated #[tauri::command] answers.

If you have written an ASP.NET app with a JavaScript client, the shape is familiar: the Rust side is the API, the Svelte side is the client. The difference is that there is no HTTP, no port, and no serialization boundary you configure — Tauri hands the arguments across the webview boundary as JSON and back. generate_handler! is the route table; #[tauri::command] is the controller action; serde is System.Text.Json.

Two ways to run the same frontend

The same Svelte code runs in two environments, and it knows which one it is in by looking for a global that only Tauri injects:

src/lib/tauriSource.ts:1538
export function isTauriRuntime(): boolean {
  return typeof window !== 'undefined' && '__TAURI_INTERNALS__' in window;
}

In a plain browser tab (pnpm dev) that returns false, and every bridge wrapper in tauriSource.ts returns null instead of calling anything. Panels that can tolerate null render empty; panels backed by a Vite dev-server shim (file browsing, git reads) still work, because vite.config.ts installs two middleware plugins that answer /__mcb/source/* and the git bridge from Node. That split is the single most useful thing to remember about this repo: browser preview is real for source and git, and blank for anything that needs a process, a PTY, or SQLite.

2The two Rust crates

There are exactly two crates. A crate is the unit Cargo compiles — the closest analogue is a .csproj, and Cargo.toml plays the role of both the project file and the PackageReference list.

CrateManifestWhat it is
mcb-core core/Cargo.toml A plain library. No Tauri, no GUI, no window handle. Scanners, the reference counter, source parsing with tree-sitter, crypto helpers, protocol types.
mac-command-bar-webview-preview tauri-svelte-preview/src-tauri/Cargo.toml The executable. Owns every #[tauri::command], every registry, and the window.

They are linked by a path dependency, not a Cargo workspace — each has its own Cargo.lock and its own target/:

Incremental builds work like .NET's: change one .rs file and only that crate recompiles and relinks. The catch is that linking a Rust binary of this size is not instant, so a one-line change in main.rs is seconds, not milliseconds — see §5.

This repo has one unusual bit of Cargo configuration worth knowing, because it explains an otherwise baffling first build:

tauri-svelte-preview/src-tauri/Cargo.toml
# Dev builds keep the app crate unoptimized (fast rebuilds, debuggable) but
# compile every dependency — serde, the file walker, the PTY layer, mcb-core —
# at full optimization.
[profile.dev.package."*"]
opt-level = 3

In .NET terms: compile your own project in Debug, but every referenced package in Release. There is no built-in way to do that in MSBuild; Cargo makes it one line. The cost is one long first build; the payoff is that dev-profile JSON parsing and file walking are not 3–30× slower than release.

Why core is a separate crate

Two reasons, both stated in the code. The first is reuse — mcb-core has no Tauri dependency, so it can be tested and used without a window (core/tests/scanner_tests.rs, core/tests/protocol_tests.rs). The second is the optimization trick above:

core/src/reference_counts.rs — module doc comment
//! This lives in the core crate rather than in the desktop app crate for one
//! reason: speed in a development build. The desktop app crate is compiled
//! unoptimized while it is being worked on, and this pass touches every byte of
//! every source file in the project — unoptimized it takes seconds instead of
//! a fraction of one. The app crate compiles all of its dependencies, this
//! crate included, at full optimization even in a development build.

What is in there:

  • core/src/scanners/ — sessions.rs (parse Claude/Codex transcript files off disk into session records), disk.rs, processes.rs, resources.rs, worktrees.rs.
  • core/src/reference_counts.rs — counts how many lines in a project mention each of a set of symbols, in one bounded parallel pass. This is what draws "N references" above a symbol.
  • core/src/source.rs, protocol.rs, crypto.rs, dispatcher.rs.

3Rust survival kit for a C# developer

Enough to read this codebase. Not enough to design in Rust, and deliberately so.

Ownership and borrowing, in two paragraphs

C# has a garbage collector: any reference keeps an object alive, and you never think about who owns it. Rust has no GC. Every value has exactly one owner, and when the owner goes out of scope the value is dropped — memory freed, files closed, processes reaped. Assigning a value to a new variable normally moves ownership, and the old variable becomes unusable. That is why you see .clone() sprinkled around: it is an explicit "I want a second copy, at a cost", and its presence in a diff is information, not noise.

Instead of copying, code usually borrows: &T is a shared read-only borrow (any number at once) and &mut T is an exclusive one (only one, and no shared borrows while it lives). The compiler proves at compile time that no borrow outlives what it points at and that nothing mutates while something else is reading. That is the borrow checker. Practically, reading Rust means treating & as "a reference I do not own" and &mut as "a reference I may write through, and nobody else has one right now". The 'a markers you occasionally see (ReferenceCountFile<'a> in core/src/reference_counts.rs) are lifetimes — the compiler's name for "this borrow may not outlive that data". You almost never need to write them to read this code.

C#

The GC decides when to free. using/IDisposable is opt-in and easy to forget.

Rust

Scope decides. Drop runs automatically, so a PTY handle or a child process is cleaned up when its owner dies — no finally.

Option, Result, and ?

Option<T> is T? done properly: either Some(value) or None, and the compiler will not let you use the value without handling None. Result<T, E> is the return-instead-of-throw pattern: either Ok(value) or Err(error). Rust functions in this codebase do not throw; they return Result. Every command in the repo has the shape Result<Something, String> — success payload on the left, human-readable error on the right.

The ? operator is the ergonomic half: let x = thing()?; means "if this is Ok, unwrap it and continue; if it is Err, return that error from this function right now." It reads like exception propagation and compiles to an early return. When you see a one-line function body ending in ?, that is a chain of fallible calls with the error path elided.

C#

throw new InvalidOperationException(...), caught somewhere up the stack, invisible in the signature.

Rust

The failure is in the return type. You cannot call the function without deciding what to do about it. There is a panic mechanism (panic!, .expect(...)) but it means "this is a bug", not "this failed".

match, enums with data, and traits

A Rust enum is a discriminated union — the same idea as OneOf or an F# DU, not the same as a C# enum. Each variant may carry data:

src-tauri/src/agent_conversation/providers/acp.rs:146
pub enum StructuredRuntimeHandle {
    Acp(AcpRuntimeAdapter),
}

impl StructuredRuntimeHandle {
    pub async fn prompt(&mut self, input: AgentPrompt) -> Result<StartedTurn, AgentRuntimeError> {
        match self {
            Self::Acp(adapter) => adapter.prompt(input).await,
        }
    }
}

match is a C# switch expression with real exhaustiveness checking: add a second variant to that enum and every match in the file stops compiling until it is handled. That is the point of the one-variant enum above — it is a seam prepared for a second provider transport, and the compiler will find every site when one arrives.

A trait is an interface. impl Trait for Type is class Type : ITrait, except the implementation lives in its own block rather than inside the type. This is the app's agent adapter contract:

src-tauri/src/agent_conversation/providers/mod.rs
pub trait AgentRuntimeAdapter: Send + Sync {
    async fn initialize(&mut self, input: InitializeAgentInput) -> Result<AgentCapabilities, AgentRuntimeError>;
    async fn new_session(&mut self, input: NewAgentSession) -> Result<StartedAgentSession, AgentRuntimeError>;
    async fn prompt(&mut self, input: AgentPrompt) -> Result<StartedTurn, AgentRuntimeError>;
    async fn cancel_turn(&mut self, turn_id: Option<&str>) -> Result<(), AgentRuntimeError>;
    /// Stop the transport without sending the destructive session/close
    /// request. The native session id remains valid for a later resume.
    async fn detach_session(&mut self) -> Result<(), AgentRuntimeError>;
    async fn close_session(&mut self) -> Result<(), AgentRuntimeError>;
}

: Send + Sync is a constraint meaning "safe to move between threads / share between threads". It is roughly the compiler-enforced version of a comment saying "this type is thread-safe", and you will see it wherever something is stored in a registry.

async, tokio, Arc and Mutex

async fn and .await mean what they mean in C#. The difference is that Rust has no built-in runtime; tokio is the runtime, and Tauri starts it for you. A Rust future does nothing until awaited (a Task starts running the moment you create it), so "fire and forget" needs an explicit tokio::spawn.

Arc<Mutex<T>> is the shape you will see most often in registry types. Arc is a reference-counted shared pointer (many owners, freed when the last one goes) and Mutex is a lock — but unlike C#'s lock, the data lives inside the mutex, so there is no way to touch it without taking the lock. Read Arc<Mutex<HashMap<String, T>>> as "a shared singleton dictionary behind a lock":

src-tauri/src/terminal.rs
pub struct TerminalRegistry {
    inner: Arc<Mutex<HashMap<String, TerminalSessionHandle>>>,
}
src-tauri/src/agent_conversation/manager.rs
#[derive(Clone)]
pub struct AgentRuntimeManager {
    sessions: Arc<Mutex<HashMap<String, ManagedAgentSession>>>,
    providers: Arc<ProviderRegistry>,
}

Because the state is behind Arc, cloning an AgentRuntimeManager clones the handle, not the sessions — the same trick as passing an injected singleton around in C#. You will also see tokio::sync::Mutex imported as AsyncMutex; that is the variant you may hold across an .await, whereas the standard Mutex must not be.

derive macros, modules, and use

#[derive(Debug, Clone, Serialize, Deserialize)] is a source generator that runs at compile time, comparable to a source generator or to attributes plus reflection — except the code is generated, not discovered at runtime. Serialize/Deserialize come from serde, which is System.Text.Json's job. The naming convention is set per type rather than globally:

src-tauri/src/usage_history.rs
#[derive(Debug, Clone, Deserialize, Serialize)]
#[serde(rename_all = "camelCase")]   // Rust snake_case ⇄ TypeScript camelCase
pub struct UsageHistoryQuery {
    pub provider: Option<String>,
    pub project_id: Option<String>,   // arrives as `projectId`
    pub start_micros: Option<i64>,
    pub limit: Option<usize>,
}

mod x; declares a module and tells the compiler to look for x.rs or x/mod.rs. That is stricter than C#: a file is not part of the build until some parent module declares it. main.rs opens with exactly that list, which is a serviceable table of contents for the backend:

src-tauri/src/main.rs:24-36
mod agent_conversation;   mod browser;        mod git_diff_models;
mod git_pr;              mod lsp;            mod orchestration;
mod resources;           mod terminal;       mod usage_current;
mod usage_db;            mod usage_history;  mod usage_indexer;
mod usage_sources;       mod workflow;

use is using, but it imports individual items rather than whole namespaces: use mcb_core::scanners::sessions::{scan_sessions, AgentSessionRecord};. pub is public; the default is private-to-the-module, and there is a pub(crate) that means internal.

4The command lifecycle, end to end

One real feature, all six hops: the Stats & Usage panel asking for per-day token totals. Every excerpt below is trimmed but otherwise unchanged.

Hop 1 — the Rust command

src-tauri/src/usage_history.rs
#[tauri::command]
pub fn read_usage_daily_totals(
    app: AppHandle,
    query: UsageHistoryQuery,
) -> Result<Vec<UsageDailyTotalsRow>, String> {
    UsageDb::open(usage_db_path(&app)?)?.read_usage_daily_totals(&query.into())
}

Read that as a minimal-API endpoint. app: AppHandle is injected by the framework (it is how you reach app data directories and emit events) and does not appear on the JavaScript side. query is deserialized from the JSON the frontend sent. The two ? marks are the error path: if the data directory cannot be resolved, or the database cannot be opened, the function returns Err(String) immediately. &query.into() converts UsageHistoryQuery into the internal UsageFilter via an impl From block a few lines above — the Rust idiom for an implicit conversion operator.

Hop 2 — the SQL

The repo rule is that aggregation happens in the database, never in a loop over materialized rows. read_usage_daily_totals builds one statement and maps the result rows straight into structs:

src-tauri/src/usage_db.rs:365
pub fn read_usage_daily_totals(&self, filter: &UsageFilter) -> Result<Vec<UsageDailyTotalsRow>, String> {
    self.query(&daily_totals_sql(filter))?.into_iter().map(|row| {
        Ok(UsageDailyTotalsRow {
            day: value_string(&row, "day"),
            event_count: value_u64(&row, "event_count"),
            input_tokens: value_u64(&row, "input_tokens"),
            /* … output/cache/reasoning/cost … */
        })
    }).collect()
}

and the statement itself groups, sums, orders, and pages entirely in SQL, against a pre-computed usage_daily_rollups table:

WITH filtered AS (SELECT day, event_count, input_tokens, … FROM usage_daily_rollups WHERE …),
     grouped  AS (SELECT day, COALESCE(SUM(event_count), 0) AS event_count,
                          COALESCE(SUM(input_tokens), 0) AS input_tokens, …
                  FROM filtered GROUP BY day)
SELECT … FROM grouped ORDER BY day DESC LIMIT {limit} OFFSET {offset}

Two surprises here if you come from EF. First, there is no ORM and no Rust SQLite driver: UsageDb shells out to the sqlite3 command-line binary with -batch -json and parses its JSON output (sqlite_command(), usage_db.rs:418; overridable with the MCB_SQLITE_BIN environment variable). Second, there is no migration runner. The whole schema lives in migrations/0001_usage_history.sql, is embedded into the binary at compile time with include_str!, and is re-applied inside BEGIN IMMEDIATE … COMMIT on every UsageDb::open — so it must be idempotent (CREATE TABLE IF NOT EXISTS style). Closer to a Dapper codebase with an idempotent bootstrap script than to EF migrations.

Hop 3 — registration

A command that is not named in generate_handler! does not exist, exactly like a controller action on a class that was never routed:

Confusingly, the codebase also has something called "backend capabilities" — see §8 — which is a third, unrelated thing.

Hop 4 — the bridge wrapper

Nothing in the app calls invoke directly. Every command gets a typed wrapper in src/lib/tauriSource.ts that guards the runtime check and imports the Tauri API lazily, so a browser build never pulls it in:

src/lib/tauriSource.ts:608
export async function readUsageDailyTotalsFromTauri(
  query: UsageHistoryQuery = {}
): Promise<UsageDailyTotalsRow[] | null> {
  if (!isTauriRuntime()) return null;
  const { invoke } = await import('@tauri-apps/api/core');
  return invoke<UsageDailyTotalsRow[]>('read_usage_daily_totals', { query });
}

The second argument's keys are the Rust parameter names, converted to camelCase. The generic parameter on invoke<T> is an unchecked assertion — TypeScript believes you. Nothing verifies at build time that the Rust struct and the TypeScript type agree; that agreement is maintained by hand and, in a few places, by the pinned tests in §8. This is the single sharpest edge in the whole architecture.

Hop 5 — backend module, service, store

Between the bridge and the UI sit three thin layers. The convention across the shell is store → service → backend → tauriSource, and each has one job.

Backend — the feature's own re-export of the wrappers it uses, so a feature never reaches into tauriSource.ts from a component:

src/lib/shell/usage/usageBackend.ts
export async function readUsageDailyTotals(query: UsageHistoryQuery = {}) {
  return readUsageDailyTotalsFromTauri(query);
}

Service — request policy: deduplication, in-flight coalescing, retries. No UI state:

src/lib/shell/usage/usageService.ts
const currentInFlight = new Map<string, Promise<ProviderUsageSnapshot | null>>();

export const usageService = {
  readCurrent(provider, instanceId) {
    const key = `${provider ?? 'unknown'}:${instanceId ?? 'unknown'}`;
    const existing = currentInFlight.get(key);
    if (existing) return existing;              // don't ask twice at once
    const request = readCurrentProviderUsage(provider, instanceId)
      .finally(() => currentInFlight.delete(key));
    currentInFlight.set(key, request);
    return request;
  },
  readDailyTotals(query) { return readUsageDailyTotals(query); },
  refreshHistory() { return refreshUsageHistory(); }
};

Store — the reactive state, and the only place that decides what "loading" and "error" mean. Note the .svelte.ts extension: that is what lets a plain TypeScript module use runes.

src/lib/shell/usage/usageStore.svelte.ts
export const usageState = $state<{
  summary: UsageSummary | null;
  dailyTotals: UsageDailyTotalsRow[];
  historyLoading: boolean;
  error: string | null;
  /* … */
}>({ summary: null, dailyTotals: [], historyLoading: false, error: null /* … */ });

export async function refreshUsageHistory(): Promise<UsageSummary | null> {
  if (usageState.historyLoading) return usageState.summary;   // re-entrancy guard
  usageState.historyLoading = true;
  usageState.error = null;
  try {
    await usageService.refreshHistory();          // re-index transcripts first
    const [summary, providerSummary, daily, dailyTotals] = await Promise.all([
      usageService.readSummary(),
      usageService.readProviderSummary({ limit: 20, offset: 0 }),
      usageService.readDaily({ limit: 31, offset: 0 }),
      usageService.readDailyTotals({ limit: 31, offset: 0 })
    ]);
    usageState.summary = summary;
    usageState.dailyTotals = dailyTotals ?? [];
    return summary;
  } catch (error) {
    usageState.error = error instanceof Error ? error.message : 'Usage history could not be read.';
    return null;
  } finally {
    usageState.historyLoading = false;
  }
}

Errors and serde at both edges

Serialization happens twice per call. On the way in, Tauri deserializes the JSON payload into the command's parameter types using serde; a missing required field or a type mismatch fails before your function body runs, and the frontend sees a rejected promise. On the way out, the Ok value is serialized with serde using each type's #[serde(rename_all = "camelCase")] attribute, which is why input_tokens arrives in TypeScript as inputTokens.

Error handling maps cleanly onto what you already know:

RustJavaScriptASP.NET analogue
Ok(value)Promise resolves with value200 OK + body
Err(String)Promise rejects; catch receives the stringException → ProblemDetails
panic! / .expect(...)Promise rejects with a panic message; the app may be left in a bad stateUnhandled exception — a bug, not a failure mode

The rejected value is the raw string, not an Error object, which is why store catch blocks in this repo all read error instanceof Error ? error.message : '…fallback…'. Practically: pick error strings in Rust that a user could read, because they are shown.

5Dev workflows

Web preview — pnpm dev

Plain Vite on http://127.0.0.1:5177 (port pinned with strictPort in vite.config.ts). No Rust is built or running. Full Svelte HMR: save a component and the page patches in place. isTauriRuntime() is false, so every bridge wrapper short-circuits to null.

Two Vite plugins in vite.config.ts partly make up for it by answering from Node: localSourceBridgePlugin() serves /__mcb/source/validate|list|read|write|search| definitions|references|reference-counts|agent-sessions out of src/lib/server/localSourceFs.ts, and gitBridgePlugin() (src/lib/server/gitBridge.ts) serves read-only git so the source-control panes and commit graph render. Both are also installed on configurePreviewServer, so pnpm preview behaves the same.

Why Resources and Usage are empty in the browser. Neither has a Vite shim. readResourceSnapshotFromTauri() and readUsageDailyTotalsFromTauri() both return null at the first line, the stores keep their empty initial state, and the panels render their empty branch. The usage store even names it: 'Usage is available in the desktop app.'. Nothing is broken — those features need a process tree and a SQLite file that a browser tab has no way to reach.

Desktop dev — pnpm tauri:dev:next

src-tauri/tauri.dev.next.conf.json

6Frontend architecture

SvelteKit that ships as static files

svelte.config.js
import adapter from '@sveltejs/adapter-static';

export default {
  preprocess: vitePreprocess(),
  kit: { adapter: adapter({ fallback: 'index.html' }) }
};

SvelteKit is normally a server framework — server routes, load functions, SSR. None of that applies here. adapter-static with an index.html fallback turns the whole thing into a single-page app: routes still exist as directories under src/routes/, but they are resolved by the client-side router inside a webview that is loading files from disk. There is no Node process in the shipped app. The closest .NET analogue is Blazor WebAssembly with a fallback route — the routing is real, the server is not.

There are three routes. src/routes/next/+page.svelte is the current shell and the one the desktop window opens (url: "/next"). src/routes/+page.svelte is the older source-preview shell, still built and still type-checked, but not what the app shows. src/routes/preview/+page.svelte is a smaller scratch route.

Svelte 5 runes

This codebase is Svelte 5 throughout and uses runes rather than the old writable()/$store pattern. Three you will see constantly:

  • $state(...) — a deeply reactive value. Assign to a property and everything reading it re-renders. There is no .set(), no $ prefix, no subscription.
  • $derived(expr) — a computed value that recomputes when its inputs change. Comparable to a get-only property that the framework knows how to invalidate.
  • $props() — component parameters, destructured with defaults.

A store here is therefore just a module that exports a $state object and some functions that mutate it — usageStore.svelte.ts above is the canonical shape. The .svelte.ts suffix is required for runes to work outside a component; a plain .ts file cannot use them.

Old Svelte stores

const s = writable(0); $s = 1; — subscription objects, auto-subscribe syntax, only usable in components.

Runes

const s = $state({ n: 0 }); s.n = 1; — plain objects, compiler-tracked, usable in any .svelte.ts module. Note that $derived is not a store either; it is a value.

The shell layout: Gridview, Dockview, and the parking stage

The window is divided by dockview-core: an outer Gridview holds five regions (sessions column, center, tools column, activity bar, bottom dock), and the center region holds a Dockview with six draggable tabs. Both are configured in code, not markup:

src/lib/shell/components/ShellFrame.svelte:113-137
centerDock = createCenterDock(centerSlot, {
  storage: window.localStorage,
  panels: [
    { id: 'session',         title: 'Session',         element: sessionSlot },
    { id: 'editor',          title: 'Editor',          element: editorSlot,         group: 'display' },
    { id: 'browser',         title: 'Browser',         element: browserSlot,        group: 'display' },
    { id: 'diff',            title: 'Diff',            element: diffSlot,           group: 'display' },
    { id: 'session-library', title: 'Session Library', element: sessionLibrarySlot, group: 'display' },
    { id: 'agents',          title: 'Agents',          element: agentsSlot,         group: 'display' }
  ],
  onPanelActivated: (id) => onCenterPanelShown?.(id)
});

Every panel is given an element rather than a component. That is the crux of the design and the reason for the parking stage.

Why elements are parked and moved

Dockview owns the DOM of its panels: when a tab closes or a layout is restored, it destroys the element it was given. If Dockview owned Svelte-rendered content, closing a tab would destroy a live xterm terminal, a Monaco model, or a native browser view — losing scrollback, undo history, and process attachment. So the shell inverts ownership. All content is rendered by Svelte into hidden <div>s, and only those elements are handed to Dockview, which moves them into place. When a panel dies, the element is moved back:

src/lib/shell/components/ShellFrame.svelte:172-187
<!-- Parking stage: content lives here until (and unless) dockview claims it, and
     whenever a panel hands it back. Not rendered at all, so nothing parked here
     can be measured. -->
<div class="parking-stage" aria-hidden="true">
  <div class="slot" bind:this={sessionsSlot}>{@render sessions()}</div>
  <div class="slot slot-center-dock" bind:this={centerSlot}></div>
  <div class="slot" bind:this={toolsSlot}>{@render tools()}</div>
  <div class="slot" bind:this={editorSlot}>{@render center.editor()}</div>
  <!-- … one slot per region and per center tab … -->
</div>

The stage is display: none rather than a 1px box, and the comment in the stylesheet explains why with a real bug: a terminal parked in a 1px stage measures its host at zero, xterm's fit addon clamps that to 2 columns by 1 row, and it resizes the real PTY to match — reflowing the agent's screen. With display: none the computed height is auto, the fit addon proposes NaN, and returns without touching anything.

{@render slot()} is Svelte 5's snippet-rendering syntax — the replacement for <slot>. The parent passes named snippets as props, and ShellFrame renders them into parking divs it controls.

Layout is persisted to localStorage through src/lib/shell/layout/layoutStorage.ts, versioned by key (CENTER_LAYOUT_KEY_V4), so a stored layout describing a panel set that no longer exists is discarded rather than restored. The right-hand tool column's roster of views is a pure module, src/lib/shell/layout/sidebarViews.ts, deliberately containing no DOM and no IO so the activity bar and the column cannot disagree about what an id means.

src/lib/shell/problems/problemsBackend.ts is the best example of why the backend layer earns its place: it distinguishes three outcomes — null (not the desktop app at all), { unavailable: true } (desktop app too old to have list_source_lsp_diagnostics_for_root), and a real answer — and its header comment states the wave rule that produced it: a feature lane adds its own *Backend.ts rather than editing the shared tauriSource.ts, and an integrator folds them in later.

src/routes/next/+page.svelte is ~1,780 lines and is the orchestrator: it owns terminal sessions and nothing else, tells each panel which project it points at and when it may start (shellPanels.ts, panelActivation.ts), and — per its own header comment — keeps IO in explicit functions, never in an $effect.

7The subsystems tour

Session library

Lists agent sessions found on disk — Claude and Codex transcript files, plus worktree state — so you can reopen or resume one. Frontend: src/lib/shell/sessionLibrary/ (sessionLibraryStore.svelte.ts, sessionLibraryModel.ts, SessionLibraryWorkspace.svelte). Backend: core/src/scanners/sessions.rs via scan_sessions, imported into main.rs. The scanner is worth a skim if you ever wonder why the list is fast: it reads bounded windows from the head and tail of each transcript (CODEX_SESSION_HEAD_BYTES = 256 KB, CLAUDE_SESSION_TAIL_BYTES = 256 KB) rather than whole files, with the constants annotated by measurements taken on real transcripts.

Terminals and PTYs

Real pseudo-terminals, one per session, backed by the portable-pty crate. Rust: src-tauri/src/terminal.rs — TerminalRegistry holds Arc<Mutex<HashMap<String, TerminalSessionHandle>>>, and output is pushed to the frontend as a Tauri event (TERMINAL_OUTPUT_EVENT = "terminal_output") rather than polled. The backend keeps a 16 MB scrollback ring per session so a hidden or reattached view can be replayed. Sessions have a TerminalKind: UserPty, AgentTool, RunConfiguration, BrowserAutomation. Frontend: src/lib/shell/terminalService.ts, xtermFactory.ts, and components/TerminalSurface.svelte, drawing with xterm.js.

Agent conversations (ACP)

The largest backend subsystem. Coding agents run as separate child processes and speak the Agent Client Protocol — JSON-RPC over the child's stdin/stdout. The mental model from .NET is a hosted background service that manages a pool of external worker processes and talks to them over a pipe.

  • src-tauri/src/agent_conversation/mod.rs — the #[tauri::command] surface (ensure_agent_conversation, send_agent_conversation_message, stop_agent_conversation_turn, approvals).
  • manager.rs — AgentRuntimeManager, the registry: HashMap<String, ManagedAgentSession> keyed by "owned id", each session holding its runtime handle, capability set, event journal, and a writer lease that decides who may currently speak to the agent.
  • providers/ — AgentRuntimeAdapter (the trait shown in §3), AcpRuntimeAdapter (its one implementation), acp_client.rs (the JSON-RPC client), process.rs (spawning and cwd validation), and ProviderRegistry. StructuredRuntimeHandle is the enum wrapper the manager stores, so the session type does not name a concrete transport.
  • Adapters are pinned by path and SHA-256 through environment variables — ProviderRegistry::bundled_from_environment() requires MCB_CODEX_ACP_PATH/MCB_CODEX_ACP_SHA256 and the Claude pair to be set together or not at all.
  • terminal_projection.rs projects an agent's tool calls into terminal-looking output; handoff.rs moves a conversation between owners; journal.rs caps retained events (2,000 in the snapshot, 10,000 in the journal).

Frontend: src/lib/shell/conversation/ — note conversationReducer.ts, which folds the event stream into timeline state, and conversationMessageSafety.ts.

Embedded browser

Not an iframe. src-tauri/src/browser.rs creates a genuine native child webview per (workspace_id, tab_id) and positions it over the main window using logical coordinates the frontend sends (BrowserBounds). BrowserRegistry keeps them alive across hide, move, and re-show, and main.rs shuts the whole registry down on WindowEvent::Destroyed. Pages get one bounded init script (browser_inspector.js, embedded with include_str!) for element picking; there is deliberately no general "evaluate this JavaScript" command and no cookie or storage bridge. State changes come back as events: browser-tab-navigation, browser-tab-load, browser-element-selected, browser-tab-closed. Frontend: src/lib/shell/browser/ and components/BrowserPanel.svelte.

The consequence of "native child webview" is the one that bites: the browser view is above the page, not in it, so anything that should overlap it (a dropdown, a dialog) has to move the webview or hide it. That is why browserModel.ts has verbs like collapseBrowserToControl and minimizeBrowserToPrevious.

Resources

What the app is currently costing the machine: processes it owns, disk used by worktrees and build output, and actions to stop or clean them. Rust: src-tauri/src/resources.rs over mcb_core::scanners::{resources, disk, processes}. Every destructive action goes through validate_resource_action and a DiskProtection check before anything is removed. Frontend: src/lib/shell/resources/.

Usage and SQLite

Covered end to end in §4. The pipeline in one line: usage_sources.rs discovers provider transcript files → usage_indexer.rs reads only the new tail of each file using a stored per-source cursor → usage_db.rs inserts events and rolls them up → usage_history.rs exposes query commands. usage_current.rs is a separate, smaller path for the provider's own live quota number. The incremental cursor is what makes refresh_usage_history cheap on the second run.

Git and the PR flow

src-tauri/src/git_pr.rs shells out to git and the GitHub CLI (gh) with argument arrays, never through a shell string — so a branch name cannot become a command. It also hosts the agent-assisted commands (generate_commit_message, read_pull_request_context, generate_pull_request_details, create_pull_request, read_pull_request_status), which prompt the caller's current ACP session rather than opening a chat, with the diff capped at MAX_PROMPT_DIFF_BYTES = 160_000. Diff parsing lives in git_diff_models.rs on the Rust side and src/lib/shell/git/parseUnifiedDiff.ts on the frontend; the commit graph lanes are computed in src/lib/shell/git/gitGraphLanes.ts and src/lib/gitGraphViewModel.ts.

LSP, Monaco, and code lens

src-tauri/src/lsp.rs is 7,145 lines and is the app's language-intelligence layer. A language server is another child process speaking JSON-RPC over stdio — for C# that is a Roslyn-based server, which is the same thing your IDE runs behind the scenes; for TypeScript it is typescript-language-server; there is also a Svelte server. The module owns process lifecycle, request/response correlation with timeouts (LSP_REQUEST_TIMEOUT = 6s), a bounded log of each server's stderr, a cap of five workspaces per language, and — because monaco-languageclient wants a socket — an axum websocket server that bridges the browser-side client to the child process. Status changes are pushed as the source-lsp-status-changed event, wired up in main.rs's .setup() block, so nothing has to poll.

Monaco is the editor component from VS Code, running in the page (src/lib/MonacoSourceEditor.svelte, ~2,950 lines). It knows nothing about your project on its own; everything smart is a provider you register — closer to registering middleware or a filter in ASP.NET than to subclassing anything:

registerSourceHoverProvider(monaco);         // tooltip on hover
registerSourceDefinitionProvider(monaco);    // go to definition
registerSourceReferenceProvider(monaco);     // find all references
registerSourceCompletionProvider(monaco);    // IntelliSense
registerSourceRenameProvider(monaco);
registerSourceCodeActionProvider(monaco);
registerSourceInlayHintsProvider(monaco);
registerSourceDocumentSymbolProvider(monaco);

Each one is a callback Monaco invokes with a document and a position; the callback asks Rust and returns the answer. Registration returns a disposable, and the file tracks every one so providers can be torn down and rebuilt.

Code lens is the small clickable line Monaco draws above a symbol — here, "N references", plus fixed "Build workspace" / "Test workspace" actions on C# files. It has two halves: a provider that says where the lenses go and what they say, and a command that runs when one is clicked. Both are registered only when the app is not in native C# language-client mode:

src/lib/MonacoSourceEditor.svelte:2455-2470

  codeLensReferenceCommandDisposable?.dispose();
  codeLensReferenceCommandDisposable = null;

  dotnetCodeLensCommandDisposables = [];

So: if reference counts vanish above C# symbols, check nativeCsharpLanguageClient before suspecting the counter. The counter itself is count_source_references in main.rs over mcb_core::reference_counts, with a 1.5 s soft deadline after which it returns what it has. The two identifier schemes behind a lens — the id Monaco uses and the cache key the editor uses — are extracted into src/lib/sourceCodeLensKeys.ts specifically so they can be tested without a browser, after a bug where including the model version in the key gave every visible lens a new identity on every keystroke.

Assistance recipes

A fixed catalogue of agent-backed actions offered next to specific surfaces — "Draft a commit message" by git, "Explain this problem" by Problems, "Draft browser feedback" by the browser. The registry is a literal list in src/lib/shell/assistance/assistanceRecipeRegistry.ts, and each entry declares its surface, a mutation policy ('none' or 'proposal'), and an allowedFields list validated against assistanceSchemas.ts. A recipe can only ever propose values for fields on its own allow-list, and a proposal is shown for approval rather than applied. Think of it as a whitelist-driven command catalogue rather than a free-form prompt box.

Problems panel

Aggregated diagnostics from the language servers. Frontend only: src/lib/shell/problems/ — problemsStore.svelte.ts, problemsService.ts, problemsBackend.ts (the three-outcome degradation described in §6), and csharpDiagnosticsAdapter.ts. Backed by list_source_lsp_diagnostics_for_root in lsp.rs. It can live in the bottom strip or in the right-hand tool column depending on settings.panels.problemsLocation, which is why the Problems view is permanently present in sidebarViews.ts while the activity bar decides whether to draw its icon.

Orchestration and workflows

Not in the brief, but you will trip over them: src-tauri/src/orchestration.rs (1,356 lines) records run events for long-running agent loops, and src-tauri/src/workflow.rs (2,588 lines) is a workflow engine with typed receipts (PlanReceipt, ImplementationReceipt, ReviewReceipt, VerificationReceipt) whose TypeScript mirrors live in src/lib/shell/workflows/workflowTypes.ts. The WorkflowEngine is created in main() holding a clone of the AgentRuntimeManager.

8Testing model

Node script tests — no framework

There is no Vitest, no Jest, no test runner. Each test is a standalone Node script under scripts/ that imports node:assert/strict, asserts, prints a line, and exits non-zero on failure. There are roughly a hundred of them, each with its own package.json script:

"test:center-dock": "node --experimental-strip-types scripts/centerDock.test.mjs",
"test:usage-view-model": "node --experimental-strip-types scripts/usageViewModel.test.mjs",
"test:tauri-source": "node --experimental-strip-types scripts/tauriSource.test.mjs",

--experimental-strip-types lets Node import .ts files directly by discarding the type annotations — no build step, no transpiler config. The trade is that anything needing a DOM cannot be tested this way, which is why the pure logic (view models, reducers, layout math, key derivation) is deliberately extracted out of components into plain modules. If you are wondering why sourceCodeLensKeys.ts, gitGraphLanes.ts, or usageViewModel.ts exist as separate files, this is the answer.

Source-text pin tests

A subset of these tests do something unusual: they read a source file as text and assert on its contents. scripts/centerDock.test.mjs is the whole file, and it is short:

tauri-svelte-preview/scripts/centerDock.test.mjs
const shellFrame = readFileSync(new URL('../src/lib/shell/components/ShellFrame.svelte', import.meta.url), 'utf8');

const centerDockStart = shellFrame.indexOf('centerDock = createCenterDock(');
const parentLayout  = shellFrame.indexOf('frame.layout(gridHost.clientWidth, gridHost.clientHeight);');

assert.ok(
  parentLayout < centerDockStart,
  'the parent Gridview must have real bounds before center Dockview restore/build'
);

That is testing ordering inside a function — something no unit test could reach without a browser and a real Dockview. scripts/sourceUi.test.mjs goes further and asserts on CSS declarations inside <style> blocks.

The tradeoff, stated plainly. These tests catch a class of regression that is otherwise invisible — an invariant that lives in the order of two statements, or in one CSS property — and they cost nothing to run. They are also brittle in a specific way: renaming a variable or reformatting a line breaks them without any behaviour changing, and they can pass while the behaviour is broken, because matching the text is not the same as doing the thing. Treat a failure as "read the comment above the assertion and decide whether the invariant still holds", not as "make the string match again".

Cargo tests

Rust tests live in the same file as the code they test, at the bottom, inside #[cfg(test)] mod tests — main.rs has about 90 of them from line 5484, and usage_db.rs, terminal.rs, browser.rs each carry their own. #[cfg(test)] means the block is compiled out of a normal build entirely, so there is no runtime cost and no separate test project. mcb-core additionally has integration tests in core/tests/, which sit outside the crate and can only use its public API — the equivalent of a separate test project that references the assembly rather than living inside it.

Two examples of what these protect. In usage_db.rs, the repo's "aggregate in SQL" rule is enforced by asserting on the generated statement rather than the result:

#[test]
fn usage_queries_are_db_side_and_bounded() {
    let sql = breakdown_sql_for_test(&UsageFilter { limit: Some(20), offset: Some(40), ..UsageFilter::default() });
    assert!(sql.contains("GROUP BY"));
    assert!(sql.contains("COUNT(*) OVER ()"));
    assert!(sql.contains("LIMIT 20 OFFSET 40"));
}

The pinned capabilities test

This one deserves its own explanation because the name collides with two other things. The app publishes a list of feature-flag strings that the frontend reads once, at startup, via the read_backend_capabilities command, and checks with hasBackendCapability('…') before offering a feature. It exists because a desktop binary can be older than the frontend it is serving, and there is no other way for the page to ask "does this build have that command?":

src-tauri/src/main.rs:1242
const BACKEND_CAPABILITIES: [&str; 25] = [
    // `start_terminal_session` accepts `command` and exits with its code.
    "terminalCommandSpawn",
    // `count_source_references` counts every requested symbol in one project pass.
    "referenceCounts",
    // The app sends a `source-lsp-status-changed` event whenever a language server
    // changes what it is doing, so nothing has to ask on a timer.
    "lspStatusEvents",
    "usageHistory", "usageDailyTotals", /* … 20 more … */
];
src-tauri/src/main.rs:8255
#[test]
fn backend_capabilities_name_every_addition_the_frontend_cannot_otherwise_detect() {
    // Pinned on purpose. Each name is a promise the frontend checks before it offers a
    // feature, so quietly renaming one turns that feature off in the app instead of
    // failing loudly.
    assert_eq!(backend_capabilities(), vec![ /* all 25, in order */ ]);
}

The failure mode it prevents is silent: rename "referenceCounts" and nothing errors — the frontend's check simply returns false forever and the feature disappears. The test turns that into a red build. If you add a capability you must add it in both places, and the array length [&str; 25] has to be updated too, which is a third reminder.

Three unrelated things called "capabilities". (1) BACKEND_CAPABILITIES — this feature-flag list. (2) src-tauri/capabilities/default.json — Tauri's own permission manifest for the window. (3) agent_conversation/capabilities.rs — what an ACP agent says it can do, negotiated at session start. They never interact.

The type-check gates

pnpm check runs tsc --noEmit, which cannot read .svelte files at all — so it checks the .ts modules and nothing else. pnpm check:svelte closes that gap with a wrapper, scripts/checkSvelteNext.mjs, whose header explains the compromise: svelte-check checks the whole project, the old shell has a long-standing backlog of its own type errors, and reporting a hundred pre-existing problems is the same as reporting nothing. So it runs the tool over everything, keeps only errors in the files the /next shell owns (an OWNED list in the script), fails on those, prints warnings without failing, and reports the old shell's error count as a single line so the backlog stays visible.

The aggregate gate

"test:tauri-app": "pnpm test:tauri-source && pnpm test:tauri-config && pnpm build
                   && pnpm test:native-lsp && cargo build --manifest-path src-tauri/Cargo.toml"

test:native-lsp is the one real integration test: it sets MCB_RUN_CSHARP_LSP_SMOKE=1 and runs cargo test … lsp, which starts actual language servers against TypeScript and C# scratch workspaces and checks symbols, hover, definition, references, and diagnostics through the same registry the Tauri commands use.

The build fails after a backend change Read the Rust error from the top: the first error is usually the real one and the rest are consequences. A test fails on a string that "should not matter" It is a source-text pin test. Read the assertion message and the comment above it — the string is standing in for an invariant.
