# Agy (Antigravity) ACP adapter recon

Read-only recon for wiring `agy-acp` in as a third ACP provider alongside Claude and Codex. No code changed anywhere in the repo; this file is the only addition.

## Headline finding

This is not green-field. The app already has real wiring for a third provider:

- `AgentConversationProvider::Antigravity` exists as an enum variant (`tauri-svelte-preview/src-tauri/src/agent_conversation/protocol.rs:59`).
- `ProviderRegistry::initial_manifests` already builds a manifest for it from `MCB_AGY_ACP_PATH`/`MCB_AGY_ACP_SHA256` env vars (`.../providers/mod.rs:149,211-225`), pinned to `AGY_ACP_VERSION = "0.1.0"` (`.../capabilities.rs:12`), which matches the vendored adapter's `Cargo.toml:3` (`version = "0.1.0"`).
- `dev-next.sh:96-117` already builds an `agy-acp` wrapper script that sets `AGY_EXTRA_ARGS="--dangerously-skip-permissions"` and exports `MCB_AGY_ACP_PATH`/`MCB_AGY_ACP_SHA256` whenever the prebuilt binary and the `agy` CLI are both present.
- The generic `AcpRuntimeAdapter` / `AcpClient` machinery (`providers/acp.rs`, `providers/acp_client.rs`) is provider-agnostic: it drives any ACP-stdio adapter through the same `initialize`/`session/new`/`session/prompt`/config-option code, with no Claude/Codex-only branches in the hot path except one Claude-specific model-list patch (`acp_client.rs:1407-1417`).
- The only two places that explicitly special-case `Antigravity` are stubs for a different (older) per-provider runner: `provider.rs:27-28` (`"Antigravity is handled by the ACP runtime"`) and `transcript/mod.rs:117-118` (`"Antigravity does not expose a local transcript"`) — both are intentional routing to the generic ACP path, not missing functionality.

So the follow-up task is mostly: build `agy-acp` into the real bundle (today it's a recon binary at `artifacts/recon/probe-agy/agy-acp/target/release/agy-acp`, wired only through the dev script), and close the source-level gaps below.

## Three-frame ACP probe result

Ran the existing probe harness (`tauri-svelte-preview/artifacts/recon/probe-agy/probe-agy.ts`) against the built `agy-acp` binary twice: once from an earlier pass (2026-08-15, `agy-acp-frames.jsonl` as first found) and once freshly re-run today to independently verify reproducibility (`node --experimental-strip-types probe-agy.ts`, exit 0). Both runs are hermetic on purpose — the probe strips `GEMINI_API_KEY` and points `HOME` at a scratch dir so it can't touch the real Antigravity session state or spend real API calls; this repo's real `~/.gemini` home *does* have live Antigravity credentials (`oauth_creds.json` present, `agy models` returns 14 real models when run outside the sandbox — see below) but a live prompt call was intentionally not fired, matching the original probe's own precedent of staying hermetic.

**initialize → OK.** Full ACP handshake succeeds:
```json
{"jsonrpc":"2.0","id":1,"result":{"agentCapabilities":{"loadSession":true,"sessionCapabilities":{"resume":{}}},"agentInfo":{"name":"agy","version":"0.1.0"},"authMethods":[],"protocolVersion":1}}
```

**session/new → OK.** Returns a session id plus the model config shape described above (empty because the sandboxed probe has no credentials to run `agy models`):
```json
{"jsonrpc":"2.0","id":2,"result":{"configOptions":[{"category":"model","currentValue":"","id":"model","name":"Model","options":[],"type":"select"}],"models":{"availableModels":[],"currentModelId":""},"sessionId":"b012285c-f410-4c07-a07a-441793df75ab"}}
```

**session/prompt "reply with the single word ok" → JSON-RPC error, by design of the sandbox.** The adapter itself behaves correctly: it spawns `agy`, `agy` cannot authenticate in the scratch `HOME` (60s OAuth wait, then times out), and agy-acp faithfully reports that failure back as an ACP error instead of hanging or crashing:
```json
{"jsonrpc":"2.0","id":3,"error":{"code":-32000,"message":"agy failed: authentication failed or timed out"}}
```
Full stderr agy-acp forwarded: `Authentication required. Please visit the URL to log in: https://accounts.google.com/... Waiting for authentication (timeout 60s)... Error: authentication timed out.` — this is `agy` itself asking for a real browser OAuth flow, which the hermetic probe correctly refuses to do.

Separately, confirmed with real credentials (outside the adapter, direct CLI call) that `agy models` works when it can see the real Antigravity home: it returned 14 real model ids (`gemini-3.7-flash-high` … `gpt-oss-120b-medium`) with exit code 0. This confirms the empty `models`/`configOptions` in the probe above is purely a sandboxing artifact, not an adapter defect — with real credentials, `Adapter::fetch_available_models` (`adapter.rs:48-57`) would populate the same fields for real.

No stray `agy`/`agy-acp` processes were left running after either probe run (`pgrep -fl "agy-acp|agy "` empty both times).

| `session/new` ignoring `cwd` relies implicitly on process-per-session isolation | No fix needed today (isolation makes it correct in practice), but worth a one-line comment or a small regression test pinning `provider_is_multi_session_safe` staying false for Antigravity, so nobody "fixes" multi-session pooling later without also fixing agy-acp's cwd handling | ~5-10 lines if a guard test is wanted |
