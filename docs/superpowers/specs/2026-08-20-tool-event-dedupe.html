Store each tool call once, not three times

Spec · 2026-08-20 · core/src/session_store.rs · one lane

The problem

A tool call is written to the database again on every status change, and each copy carries the entire output. One session in the live database holds 669 tool rows for 223 actual tool calls. The largest single call is stored four times at 91,759 bytes each.

10.3 MBtool rows on disk
3.2 MBnewest copy per call
669rows written
223real tool calls

Dropping the superseded copies is a 69% reduction with nothing lost. The conversation folds these events into one value per itemId and the newest one wins, so the older rows are already dead weight by the time they are read back.

This is the same session that made the app feel slow to open and that started the whole investigation. Measured with: 

WITH t AS (
  SELECT json_extract(payload,'$.payload.itemId') AS item_id, LENGTH(payload) AS bytes
  FROM events WHERE json_extract(payload,'$.payload.kind') = 'tool'
)
SELECT COUNT(*), COUNT(DISTINCT item_id), SUM(bytes)/1024,
       (SELECT SUM(mx)/1024 FROM (SELECT MAX(bytes) mx FROM t GROUP BY item_id))
FROM t;

Why the existing mechanism does not cover it

Superseding already exists. SUPERSEDED_BY_NEWER (core/src/session_store.rs:22) names two kinds whose older rows are deleted on write (:485-495) and on upgrade (:288, :308, and clear_superseded_events at :881).

Tool rows cannot be added to that list. The existing rule supersedes by kind, and every tool update shares the kind item.updated with every other item in the session. Adding it would delete all but the newest item in the entire transcript.

Tool rows have to be superseded by (owned_id, kind, itemId), and itemId today exists only inside the JSON payload.

The design

Add a generated column so itemId becomes a real, indexable column without changing EventRow (:124-131) or any caller of the write path. 

ALTER TABLE events ADD COLUMN item_id TEXT
  GENERATED ALWAYS AS (json_extract(payload, '$.payload.itemId')) VIRTUAL;

CREATE INDEX IF NOT EXISTS events_item_idx ON events(owned_id, kind, item_id, seq);

A virtual generated column stores nothing and is computed on read, so the table does not grow. The index is what makes the delete cheap.

What gets superseded

EventRuleWhy
item.updated with payload.kind = 'tool' Superseded by newer row with the same item_id The reducer keeps one value per itemId; older copies are never read.
content.delta Never touched On a live session the assistant's words exist only as deltas. Deleting them deletes the conversation. Already documented at :18-21.
item.completed Never touched Terminal event. It is not an update and may carry a final state the last update did not.
Everything else Unchanged Out of scope.

Every existing upgrade arm sets user_version to SCHEMA_VERSION directly, so bumping the constant means each arm must also do the new work. Miss one and a version-3 database claims to be version 6 without the column. Check all of them: 0, 1, 2, 3, 4.

Tests, written first

In core/src/session_store.rs's test module. Each names what it proves.

  1. a_tool_update_replaces_the_one_before_it — append three item.updated tool rows with the same itemId, then one with a different itemId. Reading back returns two rows, and the surviving row for the repeated id is the newest payload.
  2. a_tool_update_leaves_other_items_alone — interleave two itemIds. Both survive, each with its own newest payload.
  3. streamed_words_are_never_superseded — append twenty content.delta rows. All twenty survive.
  4. a_finished_tool_keeps_its_completion — item.updated then item.completed for the same id. Both survive.
  5. an_upgraded_database_loses_only_the_duplicates — build a user_version = 5 database by hand with three copies of one tool call and one message, open it through the normal path, and assert the duplicates are gone, the message is untouched, and user_version is 6.

Scope discipline

  • KISS: the smallest diff that makes the named tests pass. Two designs that both work — ship the one with fewer moving parts.
  • YAGNI: no code for hypothetical futures. "This makes it easier to add X later" is a reason to reject a change unless X is in this spec.
  • Adding any of these is a defect unless named above: a new interface or abstraction, a config option or flag, a compatibility shim, a factory around one call site, a drive-by refactor, or a retry/caching layer.
  • One problem per lane. "While I was here" changes are rejected in review.
  • Do not merge content.delta rows. The header at :18-21 calls that a rewrite; it is not this task.
