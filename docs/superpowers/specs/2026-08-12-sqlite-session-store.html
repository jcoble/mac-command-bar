rusqlite, bundled SQLite, WAL, synchronous=NORMAL. No ORM, no migrations framework — a single schema_version pragma and hand-written upgrade steps.

Cutover plan — importer, then delete

  • 1. Manager writes and reads only SQLite. All session lifecycle paths (create, activate, suspend, resume, close, reap) update rows in the same transaction as their state change.
  • 2. One-time importer at first launch: existing journal entries and known owned-session records → rows. It runs once, stamps schema_version, and is ~100 lines we can delete next month. A converter, not a bridge.
  • 3. Same wave: delete journal.rs persistence, delete the frontend owned-sessions localStorage store + reconciliation, frontend session list comes from a backend query. If any of these can't be deleted tonight, the wave doesn't merge.
  • 4. Verification: restart the app mid-conversation → rail, transcript tail, drafts, and suspended states all restore from the DB; kill -9 the app → same result (WAL survives).

What this buys immediately

  • Session library search and history become SQL (LIKE/FTS later if ever needed — YAGNI now).
  • Cross-restart and cross-crash resume for free (native id + provider + cwd in the row; pairs with suspend commit 6c310ca).
  • The supervisor digest feed and handoff context packages (agents phase) read from events with one query.
  • Deletes the whole localStorage-reconciliation bug class.

Open question (spike running)

muxspike19 is live-testing whether one adapter process can host multiple sessions. Outcome only changes one thing here: whether sessions rows map to a per-session process or to a shared per-provider process pool. The schema stays identical — runtime attachment is manager state, not database state.

Out of scope tonight (YAGNI)

  • Full-text search indexes, sync, encryption-at-rest, multi-machine anything.
  • Storing raw provider wire payloads beyond what events already captures.
  • Settings/preferences migration — different concern, different day.
