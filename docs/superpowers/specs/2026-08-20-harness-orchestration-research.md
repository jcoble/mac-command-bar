# Agent-harness orchestration research

Research date: 2026-08-20. Scope: Pi/`pi-subagents`, Herdr, Claude Code teams, then brief ACP/Zed, Codex CLI, and Mac-fleet comparisons.

## Evidence rules

- **Verified** means the linked primary documentation or source was read directly.
- **Inferred** means a design conclusion from verified behavior; it is not a product guarantee.
- **Unverified** means the reviewed public sources do not establish the detail. I do not fill gaps with guesses.

## Short synthesis

- Pi is the closest match to a programmable supervisor: child runs, keyed steering, supervisor decisions, durable run artifacts, and a live fleet inspector are explicit features. Its background control path is a file inbox, not ACP ([package/docs](https://github.com/nicobailon/pi-subagents), [control source](https://raw.githubusercontent.com/nicobailon/pi-subagents/main/src/runs/background/control-channel.ts)).
- Herdr is a terminal/process multiplexer. It makes real panes, PTYs, prompts, lifecycle state, and event subscriptions scriptable, but its documented primitive is terminal input rather than a durable agent-message bus ([agents](https://herdr.dev/docs/agents/), [socket API](https://herdr.dev/docs/socket-api/)).
- Claude Code teams use separate Claude instances plus a shared task list and per-teammate JSON mailbox files. Direct teammate addressing is explicit; exact delivery timing into an already-running turn is not ([teams guide](https://code.claude.com/docs/en/agent-teams)).
- ACP is the agent/client session boundary. It provides prompt, updates, permissions, cancellation, and session lifecycle, but the public protocol does not define agent-to-agent messaging or workflow/DAG semantics ([ACP v2 overview](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/overview.mdx)).

## 1. Pi and `pi-subagents`

Primary sources: [`pi-subagents` README](https://github.com/nicobailon/pi-subagents), [workflow API](https://github.com/nicobailon/pi-subagents/blob/main/docs/workflows.md), [observability](https://github.com/nicobailon/pi-subagents/blob/main/docs/observability.md), [missions](https://github.com/nicobailon/pi-subagents/blob/main/docs/missions.md), [tool reference](https://github.com/nicobailon/pi-subagents/blob/main/docs/tool-reference.md), and the [runner](https://raw.githubusercontent.com/nicobailon/pi-subagents/main/src/runs/background/subagent-runner.ts), [Pi spawner](https://raw.githubusercontent.com/nicobailon/pi-subagents/main/src/runs/shared/pi-spawn.ts), and [control channel](https://raw.githubusercontent.com/nicobailon/pi-subagents/main/src/runs/background/control-channel.ts) source.

- **Process model — Verified.** A background child is a separate OS process: the runner uses `node:child_process`, and the spawn helper resolves a Pi executable/CLI. The package also has foreground and background/async modes. The public sources do **not** establish whether a foreground child is a separate process, thread, or an attached in-process session; that boundary is **unverified**.
- **Transport — Verified.** Parent-to-background-child control is a per-run file inbox: atomic JSON steer/stop/interrupt requests are written under the run directory; the child consumes them with `fs.watch` plus safety polling. This is a local side channel, not ACP or a socket.
- **Addressing/routing — Verified/Unverified.** Workflow handles are stable keys, so `runs.steer(key, message, options)` can target a specific live child. Native `contact_supervisor` sends a child request to its exact parent Pi session; the parent replies with `subagent_supervisor`. A normal workflow is parent/child-oriented (**Verified**). **Unverified:** the core workflow docs do not promise arbitrary worker-to-worker delivery; the optional [`pi-intercom`](https://github.com/nicobailon/pi-intercom) package adds same-machine session-to-session targets.
- **Mid-run interaction — Verified.** Steering has `steer`, `follow_up`, and `auto` modes and receipts `queued`, `delivered`, `missed`, or `failed`. “Delivered” means the child session accepted the input, not that the model followed it. Interrupt/stop are separate controls. Supervisor requests can be blocking (`need_decision`, `interview_request`) or non-blocking (`progress_update`). Exact model-turn timing is intentionally not promised.
- **State/persistence — Verified.** Async runs write `status.json`, `events.jsonl`, output logs, and a Markdown transcript/log under a temporary `pi-subagents-*` directory. Missions add durable project/mission/run/receipt records under `~/.pi/agent/missions/projects/<project-hash>/`; a mission links objectives, runs, decisions, artifacts, and receipts. Resume/status/interrupt are exposed by run ID. Temporary completion replay is best effort, so the mission records are the durable layer.
- **Workflow shape — Verified.** Current workflows are ordinary JavaScript (`workflowScript`), not a separate declarative DAG file. In the requested vocabulary, `runs.run` covers a single child or a sequential chain, `runs.all` covers parallel fan-out, the async/background flag covers detached work, `context: "fresh"` or `"fork"` covers clean versus forked context, and run IDs expose resume/status. Structured output can drive dynamic fan-out; rolling `Promise.race` patterns can keep a supervisor responsive; gates are explicit supervisor decisions/interviews. **Inferred:** retries, timeouts, and joins are script policy rather than a universal scheduler contract; the reviewed docs do not specify automatic retry semantics.
- **Human visibility — Verified.** Foreground runs stream into the conversation. The FleetView widget and `/subagents-fleet` inspector show child state, current tool, recent output, tokens/cost, duration, transcript, and steering controls; a selected live child can be steered or stopped. Textual fallback exists when the full TUI is unavailable.
- **What to borrow — Inferred.** Pi demonstrates that a useful supervisor needs (1) stable run/agent IDs, (2) a control queue with acknowledgements, (3) append-only lifecycle/event records, and (4) a UI that can inspect and steer without pretending “delivered” means “obeyed.”

## 2. Herdr

I found the product under **Herdr** (not merely “Herd”): [official site/docs](https://herdr.dev) and [source repository](https://github.com/motionharvest/herdr).

- **Process model — Verified.** Herdr runs a background server that owns workspaces, tabs, panes, and terminal processes. Each agent remains in a real terminal pane with its shell, logs, prompts, and process; supported integrations add hooks or screen-manifest state. The docs do not claim threads or containers.
- **Transport — Verified.** The CLI wraps a local newline-delimited JSON socket API: Unix-domain socket on Unix (named pipe on Windows). The API exposes pane text/keys, semantic `agent.prompt`, lifecycle waits, state reporting, and event subscriptions. It is local IPC, not an agent-to-agent protocol.
- **Addressing/routing — Verified/Unverified.** A live agent has a unique name alias and a pane ID. `agent start` attaches to an existing shell pane; any client with the socket can address a pane or named agent (**Verified**). **Unverified:** no durable peer mailbox or arbitrary worker-to-worker message API appears in the reviewed docs; peer coordination would therefore be agents invoking Herdr’s control surface themselves.
- **Mid-run interaction — Verified.** `agent.prompt` may prompt an agent already working. If the agent is blocked, the documented escape hatch is deliberate terminal key input (`pane.send-keys`). Herdr waits on lifecycle state, not individual model turns, and does not document a queued-turn/interrupt guarantee.
- **State/persistence — Verified.** Integrations report semantic state (`working`, `blocked`, `idle`, etc.) and optional native session references; socket events include agent-status changes. Detach normally keeps server, PTYs, processes, and layout alive. Snapshots can restore layout and optional screen history; native session restore depends on the agent. Live handoff does **not** preserve transient coordination, in-flight requests, waits, subscriptions, or pane-to-pane messages.
- **Workflow shape — Inferred.** The reviewed Herdr docs expose composable CLI/socket primitives and waits, not a declarative DAG, fan-out/join model, gates, or automatic retries. Shell or another controller can compose those primitives, but that is external workflow code.
- **Human visibility — Verified.** The terminal-pane UI, workspace/tab navigation, agent status rollups, notifications, direct attach, and event subscriptions make a fleet visible. Herdr’s strength is “real process plus terminal observability,” not a durable conversation log between agents.

## 3. Claude Code teams and teammates

Primary sources: [official agent-teams guide](https://code.claude.com/docs/en/agent-teams), [tools reference](https://code.claude.com/docs/en/tools-reference), and [official changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md).

- **Process model — Verified.** A team consists of a lead and separate Claude Code instances. The default display is an in-process team view; split-pane display uses tmux or iTerm2, and the tools reference describes those teammates as separate Claude Code processes. The exact OS/thread boundary of the in-process runtime is **unverified**.
- **Transport — Verified.** The team mailbox is a JSON file per teammate at `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`; the send operation reports success only after the inbox write succeeds. Team config records names, session IDs, and pane IDs; tasks live under `~/.claude/tasks/{team-name}/`.
- **Addressing/routing — Verified/Unverified.** Teammates can message any other teammate by name; broadcasting means sending one message per recipient. `ListAgents` discovers sendable local/remote sessions, while the team roster is the source for teammates (**Verified**). **Unverified:** the public docs do not claim that the mailbox is a globally ordered message bus.
- **Mid-run interaction — Verified/Unverified.** SendMessage is a direct teammate message and docs say delivery is automatic; idle notifications can tell the sender when a teammate next becomes idle. Recent releases added `notify_when_idle` and rejected over-size/burst inbox writes up front. The public docs do **not** say whether a message interrupts the current model turn, queues until the next tool round, or is injected at another boundary.
- **State/persistence — Verified/Unverified.** The shared task list supports pending/in-progress/completed states and dependencies and is retained locally subject to cleanup settings. The team config is removed when the session ends (**Verified**). **Unverified:** the docs do not promise mailbox durability or cross-restart replay, so treat the mailbox and config as runtime coordination state unless a separate transcript is retained.
- **Workflow shape — Verified.** The task list is a lightweight dependency graph with file locking on claims. Hooks (`TeammateIdle`, `TaskCreated`, `TaskCompleted`) provide quality gates and notifications. The docs do not describe a general declarative workflow file with retries or compensation.
- **Human visibility — Verified.** In-process mode lets the human select a teammate, view it, type, and use Escape to interrupt; split-pane mode exposes one terminal per teammate. The lead panel shows teammate status, and idle notifications/task updates surface progress.
- **Release signal — Verified.** The changelog’s recent SendMessage changes show that reliability (oversized messages, burst handling, idle notification) is a first-class concern, not an afterthought.

## 4. Brief comparisons

**Zed and ACP.** [ACP’s v2 overview](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/overview.mdx) defines JSON-RPC client↔agent session methods: `session/new`/`resume`, `session/prompt`, `session/update`, permission requests, and `session/cancel`; it does not define an agent-to-agent method. [Zed external agents](https://zed.dev/docs/ai/external-agents) run as their own ACP agent process and Zed hosts the thread UI; [parallel agents](https://zed.dev/docs/ai/parallel-agents) gives each thread its own context/history and a sidebar/history view. **Verified:** Zed is a strong human-facing session host, not evidence of an ACP peer-message bus.

**OpenAI Codex CLI.** [Official Codex docs](https://learn.chatgpt.com/docs/agent-configuration/subagents) say current local Codex releases spawn specialized subagents in parallel, expose each as an agent thread, route follow-ups, wait for results, and let `/agent` inspect/switch while running. Custom agents are TOML files under `~/.codex/agents/` or `.codex/agents/`; the main thread collects results. **Verified:** orchestration and human inspection are public features. **Unverified:** the docs do not expose whether children are processes/threads, the wire transport, mailbox/storage layout, or a worker-to-worker API; no peer-message contract is documented.

**Conductor and Mac fleet UIs.** [Conductor](https://www.conductor.build/docs/reference/harnesses) is a workspace layer around Claude Code, Codex, Cursor, and OpenCode; its unit is a workspace with a branch, Git worktree, terminal, chat, diff, checks, and PR path. Its [parallel-agent guidance](https://www.conductor.build/docs/concepts/parallel-agents) chooses separate workspaces for independent work or one workspace for shared-branch collaboration. **Verified:** excellent isolation/review UI; **Inferred:** the reviewed docs do not describe a peer-message transport or durable agent conversation bus. Another notable Mac product, [Fleet](https://runfleet.dev/), markets parallel isolated worktrees, live diffs, and review in one cockpit; its public page does not expose implementation details.

## Implications for Assembly (opinions, not a decision)

### Fit with an app that owns ACP stdio

1. Keep ACP as the per-agent session transport. It already gives Assembly prompt, streamed updates, permission requests, cancellation, and session lifecycle ([ACP v2 overview](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/overview.mdx)); do not overload it with harness coordination.
2. Add one harness-owned broker beside ACP: stable `agentId`/`runId`/`sessionId` addressing, an append-only event/message log, per-agent pending queues, and explicit receipts (`queued`, `delivered-to-session`, `failed`, `expired`). This combines Pi’s receipts/artifacts with Claude’s named mailboxes while avoiding terminal scraping.
3. Expose the broker to workers through the smallest universal bridge Assembly can support (a local harness tool/CLI or MCP bridge). A worker sends `to`, `body`, and `kind`; the broker appends the envelope and wakes/presents the recipient at a safe ACP boundary.

### Cheapest credible first slice

- **Worker → orchestrator status:** consume ACP `session/update` and prompt completion/idle signals; normalize them to `running`, `waiting`, `blocked`, `idle`, `done`, and `failed`; append every transition and tool/progress summary to the broker log.
- **Orchestrator → worker mid-run message:** queue it in the broker. Deliver on the next safe prompt boundary; for urgent intervention, use ACP cancellation and then a new prompt. Do not claim true arbitrary mid-token injection unless an agent-specific adapter proves it.
- **Worker ↔ worker:** route through the broker by stable IDs, never by window title or PID. The orchestrator can relay messages without forcing every agent pair to know transport details.
- **Human view:** render the same append-only log as a timeline filtered by run/agent, with receipts and source (`human`, `orchestrator`, `worker`). Show ACP updates beside coordination messages so the user can distinguish “agent is working” from “agent sent a message.”
- **Workflow layer:** start with code/config that can express sequential steps, fan-out, join, and a human gate. Add retries only when a concrete workflow needs them; neither ACP nor the reviewed products justify a speculative scheduler.

### ACP boundary

ACP is enough for agent-session lifecycle and live progress, but not for peer discovery, worker-to-worker messages, durable coordination history, workflow gates, retry policy, or a cross-agent message log. Those belong in Assembly’s side channel and persistence layer; ACP remains the adapter used to talk to each individual agent.
