A · Editor / Supercharged switch and tree-sitter highlighting decided

A0 · What exists today (why it is unreliable)

The editor is Monaco through @codingame/monaco-vscode-api 25.1.2 (package.json:116) with 28 monaco-vscode-*-default-extension packages and the textmate, files and keybindings service overrides. Highlighting is VS Code's TextMate grammars registered asynchronously by those extension packages on the main thread; the C# language client (src/lib/shell/editor/csharpLanguageClient.ts) rides on the same layer. The "half the time" highlighting and the #464 start error ("MarkdownRendererService.setDefaultCodeBlockRenderer is not supported … without registering the corresponding service override") are both start-order races inside that layer. Language servers exist for C# (Roslyn, native client), TypeScript/JavaScript (typescript-language-server) and Rust (rust-analyzer) — src-tauri/src/lsp.rs:60-64, 4578-4592; nothing for HTML, CSS, JSON, Markdown, shell, Svelte. The editor toolbar shows a per-file LSP toggle on every file regardless (#443, #464 "C#").

A1 · The switch

Where

Title bar, global, persisted: a two-segment control Editor | Supercharged (the word "Supercharged" is a placeholder the owner may rename; keep it in one constant). Visible from every panel.

On

Language servers start lazily for the language of each file you open, limited to servers enabled in Settings → Supercharged. CodeLens, references, rename, diagnostics come from them. Status line on a file with no server: "Editor only — no language server for HTML".

Off

Running servers stop immediately (RAM back). Editor only: tree-sitter highlighting, outline, folding, go-to-symbol in file. Nothing else starts.

Settings → Supercharged

One row per server (C#, TypeScript/JavaScript, Rust, later Svelte…): "on when Supercharged" / "always off". This section is where future Supercharged things plug in (indexers, formatters). Default: all on when Supercharged.

Removed (one way only): the per-file toolbar toggle (EditorPanel.svelte "C#"/"SH" control) and the separate C# on/off in Settings → General → Language support (SettingsDialog.svelte, lsp.rs:83-112 csharp_language_server_enabled), replaced by the per-server allow map. Backend contract: language_server_allowed(language_id) becomes supercharged_enabled() && server_enabled(server_name); one Tauri command to read/write the switch and the map; turning the switch off calls the existing stop path for every running server.

A2 · Highlighting: tree-sitter only

  • Engine: web-tree-sitter (WASM) running in a Web Worker; one grammar .wasm per language, fetched on first open of that language and cached; incremental reparse on edit (only the changed span).
  • Output: highlight captures from each grammar's highlights.scm mapped to ~12 app token kinds (keyword, string, number, comment, type, function, variable, property, operator, punctuation, tag/attribute, constant). The same tree yields outline (symbols), folding ranges and go-to-symbol in file.
  • Into Monaco: the semantic-tokens overlay, with TextMate/Monarch switched off so there is exactly one colourer. The 28 monaco-vscode-*-default-extension packages and the textmate service override are removed (one way only). monaco-vscode-api itself stays only as long as the C# language client needs it; the spike says whether that is the right long-term base.
  • Theme: the 12 token colours live as CSS custom properties in src/lib/shell/styles/nextTokens.css next to the other theme tokens and are pushed into a Monaco theme whenever the app theme changes. Roslyn's semantic highlighting is disabled in the C# client options.
  • First grammars: C#, TypeScript, TSX, JavaScript, Svelte, HTML, CSS, JSON, Rust, Markdown, Bash, YAML, TOML, Python, Swift, SQL. Adding one later is a grammar file plus a capture map, nothing else.
  • What tree-sitter is not: no cross-file references, definitions, rename, types or diagnostics — those remain Supercharged. CodeLens keeps working under Supercharged unchanged.

A4 · Extensions stance decided

No VS Code extension host in this app. Web extensions would run in a Worker host; Node extensions (Svelte LS, SQLTools, most language tooling) need a VS Code server process. What those would give us we do cheaper and measurably our own way: Svelte LS as one more LSP binary in the same registry under Supercharged (later); a DB panel over tauri-plugin-sql or a Rust command (later); git graph as our own component over git log --graph data (later). The spike's extension-host number is kept so this stays a measured decision.

B · The in-app helper model decided

A small, fast model that lives in the app and does jobs for the user — not a chat. Bring-your-own-key.

B1 · Settings → Helper

Vendor (OpenAI, Anthropic), model id from a short per-vendor list (ids confirmed from vendor docs when the plan is written, never from memory), key field, "Test" button making one tiny call. Key → macOS Keychain under our own service name via /usr/bin/security add-generic-password/find-generic-password -w (silent for an unsigned dev build, as proven in claude_quota.rs); settings file holds vendor + model only. No key → helper off.

B2 · Rust helper module

One interface, two implementations: complete(job, system, input, max_output) → text. 20 s timeout, one retry on a network error, no streaming, no memory between calls. One Tauri command run_helper_job(job, input). Every call logged to the usage-history store (job, vendor, model, in/out tokens) so it shows in the Usage popover.

B3 · Jobs, in order

(1) Title: fires once per session, after the first assistant reply; input = the user prompt + that reply (trimmed to a budget); output ≤ 6 words; written to the session row; the rail updates in place; a title the user typed is never overwritten (flag on the row). (2) Inspect: the worktree card button gathers facts deterministically (status, ahead/behind, last activity, sessions that touched it) and asks for a 3–5 sentence summary + recommended action, shown inline in the card; no session is started; the current "start a session with a skill" path is removed. (3) later command check, commit-message check, PR-text check, save check — same command, new job names.

B4 · Failure

No key, offline, timeout or unusable answer → keep the fallback silently (first-words title; Inspect shows "Helper unavailable — add a key in Settings → Helper"). Never blocks, never holds a process. later fallback chain: key → Claude Code sign-in on this Mac → other providers present → Settings choice.

C1 · Plan chip above the composer decided

Reference: Codex desktop (#466, #467). The plan leaves the transcript. A pill chip sits centred above the composer: ● Step 2 / 5 · 1 file changed +12 −3 (file-change summary only when the turn has one). Click expands upward into a panel listing the steps with their state (pending / active / done); collapses on click, Escape, or when the turn ends. It shows the session's latest plan (fixes the doubled PLAN card in #446). Agy (Antigravity / Gemini) as a first-class provider decided

Owner: a major item; Gemini is wanted mainly as sub-agents. Today the adapter is a recon artifact (artifacts/recon/probe-agy/agy-acp/, README lines 1–21, 60–61, 109–111), registered by scripts/dev-next.sh:95-113 only when both agy and a built adapter binary exist, passing skip-permission mode because it has no interactive permission answers. Bring it in properly: recon lane first (what the artifact supports today — sessions, prompt, tools, images, usage, cancel — against the current agy CLI), then a provider lane: adapter built from a tracked location and trusted like the others (capabilities.rs manifest + hash), dev-next.sh wiring, new-session picker offers it with its models, a session runs end to end, permissions either answered or the absence documented in the UI, usage if it reports it, and the architecture guide's provider section updated in the same commit.

Non-goals for this wave

  • No VS Code extension host. No marketplace extensions.
  • No editor migration decision before the A3 numbers.
  • No local (on-device) helper model.
  • No Assembly-owned context compaction (still proposed only, see the architecture guide §16).
  • No UI regression tests (repo rule) — logic and data tests only; visuals verified by screenshot.
