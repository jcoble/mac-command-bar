TSK-1345 — Projects become the identity of a session

Refreshed technical design · 6 October 2026 · branch tsk-1345-projects-v2 · base tsk-1389-ui-pass @ 52af4e430. Replaces the 1 October design (written against ad11d88f2). PR 1 implementation spec: docs/superpowers/specs/2026-10-06-tsk-1345-pr1-spec.md. Visual approval artifact: 2026-10-01-tsk-1345-projects-mockup.html.

Receipt labels: VERIFIED = read by this lane at the cited lines. ASSUMED = reported by a read-only recon pass in this lane and not re-read line by line.

The model (owner decisions, binding). A project is one folder on one machine. A session records its project once, at creation, and never changes it. Branch and worktree are separate, changeable facts about the session. The sidebar and history group and filter by project, and copies of the same repository on different machines share one group, matched by the repository's remote URL. New sessions pick a project, then Current checkout or New worktree, then a branch. Nothing runs git init or git worktree add without an explicit user action, and opening a draft changes nothing on disk.

Shared contract with TSK-1344 (chat). Every session carries five separate facts: the Assembly session id (ownedId), the project id, the owning machine (executionEnvironment + remoteProfileId), the physical checkout path (cwd), and the provider-native session id. The chat keys on ownedId only. A project name or folder path is never a chat identity.

2. Decisions

Owner answers, 6 October 2026 (binding): Q1 — first-message worktree creation is in PR 1 as sub-PR 1c. Q2 — all project records live in the Mac app's database (D1). Q3 — in a new draft the Current-checkout branch switch happens on first send (D8).

#DecisionWhy
D1Owner-approved deviation from T3. The project registry is one projects table in the desktop app's sessions.db, one row per (machine, folder), for local and remote copies alike. Remote machines store only each session's project_id. (T3 keeps each machine's projects on that machine.)The registry is always readable, including while a remote machine is offline, so PR 2 can derive every session's group with SQL on the desktop alone. No remote commands, remote tables or offline cache are needed for projects.
D2The same SessionStore schema runs everywhere, so the remote host's database also has an empty projects table.Avoids a second opener or a "client-only" flag. An empty table costs nothing.
D3sessions.project_id is write-once in SQL: the upsert sets project_id = COALESCE(sessions.project_id, excluded.project_id).The store itself enforces "a session's project never changes", whatever path writes the row (ensure, meta update, startup normalization).
D4A project folder must be an existing directory that is not inside Git's own data (git rev-parse --is-inside-git-dir is true) and, if it is in a repository, is that repository's top level. A bare repository root is refused like any Git-data folder.Resolves the 1 Oct conflict C1 without an exception: the mockup (screens 3 and 3b) adds a checkout folder such as ~/dev/work/worktrees/mac-command-bar/main and refuses ~/dev/work/mac-command-bar/worktrees/main. A sub-folder project would make checkout and worktree rules ambiguous.
D5Title = the repository name from the remote URL (last path segment, no .git), else the folder name. Badge = first letters of the first and last word, or first and last letter of a single word (mac-command-bar → MB, EdiPlatform → EM).The workbox checkout folder is named main; the mockup shows "mac-command-bar". The badge rule reproduces every badge in the mockup and T3 screenshots.
D6Repository key = remote URL (remote.upstream.url, else remote.origin.url) normalised to host/owner/repo: lower-case host, no scheme, user, port, leading slash or .git. Empty when there is no remote.Matches T3's repository identity (receipts in the Notion task). Computed once at Add time, on the owning machine.
D7"No project" stays (mockup screen 1): a plain conversation in the home folder of a machine picked from the sub-bar. Its project_id is null.The mockup keeps it; plain conversations exist today (DraftSessionSurface.svelte:289-305 VERIFIED).
D8In a new draft, the Current-checkout branch switch runs at first send, not at pick (owner, Q3).A discarded draft leaves the repository untouched; a failed switch keeps the draft and creates no session.
D9Add project does not create folders or initialise repositories; "create a remote project" stays with TSK-1211. No "remove project" in this task.YAGNI; the owner did not ask for removal.
D10Sub-PR 1a imports the saved new-session.custom-project-roots entries into the registry once, at desktop startup, then deletes that key and new-session.last-project-root. Entries that fail inspection (missing folder, inside Git data, sub-folder of a repository, or a non-absolute path) are skipped and written to the backend log. 3. Data contract

-- sessions.db schema 20 (core/src/session_store.rs)
CREATE TABLE IF NOT EXISTS projects (
  id          TEXT PRIMARY KEY,      -- UUID v4, made in Rust
  machine     TEXT NOT NULL,         -- 'local' or a saved remote profile id
  root_path   TEXT NOT NULL,         -- canonical absolute path on that machine
  title       TEXT NOT NULL,
  repo_key    TEXT NOT NULL,         -- 'github.com/jcoble/mac-command-bar' or ''
  created_at  INTEGER NOT NULL,
  UNIQUE (machine, root_path)
);
ALTER TABLE sessions ADD COLUMN project_id TEXT;   -- no foreign key: remote hosts never hold the row it names
CREATE INDEX IF NOT EXISTS sessions_project_idx ON sessions(project_id);
Add projectPick machine → browse folders on it → Add. Rust inspects the folder on that machine (local function or the inspect_project_folder remote operation) and inserts or returns the existing row.
DraftProject menu lists registry rows (local and remote copies separately, cloud icon for remote). Machine is the project's machine. Opening is read-only.
First sendOptional checkout (1b) or new worktree (1c) on the project's machine, then ensure with projectId, then send. Git failure keeps the draft; no session.
AfterwardsSession record carries projectId on both machines' rows and the desktop's remote cache. It never changes.

Existing sessions keep project_id = NULL through PR 1. PR 2 back-fills them once with SQL (section 5) and switches grouping to the project in the same PR.

Remote sessions on the desktop. The desktop keeps no rows for remote sessions' metadata: it keeps one JSON blob, the app setting remote-assembly.session-projections.v1 (remote.rs:55; read at :424-439, written at :525-537 VERIFIED). Each record in that blob carries projectId from 1a onward because the record type gains the field. (The sessions rows marked cached_remote_profile_id are history-copy placeholders with empty cwd, remote_history.rs:615-631 VERIFIED; they are not the session list.)

5. PR 2 outline — group and back-fill by project, in SQL

Contract. Every session record gains projectGroupKey and projectGroupLabel, computed in SQL on the desktop:

group_key   = CASE WHEN p.id IS NULL THEN 'none'
                   WHEN p.repo_key <> '' THEN 'repo:' || p.repo_key
                   ELSE 'project:' || p.id END
group_label = COALESCE(p.title, 'No project')
  • Local sessions: SessionStore::list_sessions (core/src/session_store.rs:1876-1893 VERIFIED) becomes … FROM sessions s LEFT JOIN projects p ON p.id = s.project_id and returns both columns, ordered by group_label, last_activity_at DESC, owned_id.
  • Cached remote sessions (the JSON blob, not rows): one new store method reads the blob in SQL — SELECT json_extract(e.value,'$.ownedId'), <group_key>, <group_label> FROM app_settings a, json_each(a.value_json) e LEFT JOIN projects p ON p.id = json_extract(e.value,'$.projectId') WHERE a.setting_key = 'remote-assembly.session-projections.v1'. list_agent_conversation_sessions (S/agent_conversation/mod.rs:645-669 VERIFIED) and the remote refresh attach those two fields to the cached records. The remote host never computes them (it has no registry, D1).
  • TypeScript derives no project identity from paths: resolveOwnedSessionProject and the projectPath || cwd keys are deleted. The rail draws one header per projectGroupKey with its label. The rail's existing live status sub-groups and the Provider / Status / Location pills keep working on the loaded live projection, because status is runtime state that SQL does not hold. No Project filter is added (not in the mockup).
  • Each row's second line names its machine ("This Mac" or the profile name), then its branch; the cloud glyph replaces the Server glyph; the group header gets the two-letter badge. Changing cwd or branch can never move a session.

Back-fill (write-once, SQL). Runs at desktop startup after the registry is readable and before the first session list, and on each remote machine before its first session list after connecting. Step 1 is one statement:

UPDATE sessions SET project_id = (
    SELECT p.id FROM <candidate projects> p
    WHERE sessions.cwd = p.root_path
       OR substr(sessions.cwd, 1, length(p.root_path) + 1) = p.root_path || '/'
    ORDER BY length(p.root_path) DESC, p.created_at, p.id LIMIT 1)
WHERE project_id IS NULL AND cached_remote_profile_id IS NULL
  AND EXISTS (SELECT 1 FROM <candidate projects> p WHERE … same match …);

On the desktop, <candidate projects> is projects WHERE machine = 'local'. For a remote machine, the desktop sends that machine's projects as one JSON array in a new remote command BackfillProjects { projects: [{ id, rootPath, createdAt }] } (protocol 14), and the remote host runs the same statement over json_each(?1). Step 2 handles only the rows left over: select DISTINCT cwd where project_id IS NULL, run git rev-parse --git-common-dir once per distinct cwd and once per candidate project root, and write all matches in one statement: UPDATE sessions SET project_id = m.project_id FROM json_each(?1) … WHERE sessions.project_id IS NULL AND sessions.cwd = m.cwd. Ties go to the oldest project. Re-running changes nothing that is already set. Offline remote sessions stay "No project" until their machine connects; the next session list refreshes the blob with the new ids.

History. Adopted sessions use the same key. Scanned provider transcripts that are not in SQL get their project from the scan command in Rust: one statement over json_each of the scan's distinct cwds joined to projects with the same exact/prefix rule, then the git-common-dir check once per leftover distinct cwd. Adoption passes the matched id into begin_import_session.

6. PR 3 outline — existing sessions: branch switch and worktree removal

Contract. An open session shows the same sub-bar under its composer: machine label, workspace, branch picker. Picking a branch checked out in another worktree points the session there (cwd/worktree/branch change only); otherwise git switch runs in the session's current checkout. Deleting a session offers to remove its worktree only when the path is a registered linked worktree (not the project root) and no other session on that machine uses it; the backend re-checks just before removal and runs a normal git worktree remove. If Git refuses (uncommitted changes, unmerged commits, locked), the session is still deleted, the worktree stays, and Git's message is shown. No forced removal. Archive never touches worktrees.

7. Risks

  1. Protocol collision with TSK-1344. Both change PROTOCOL_VERSION, manager.rs ensure and the session record. Sequence the merges and rebase; the remote backend on the workbox must be re-installed after 1a lands (client and backend versions must match, remote.rs:2408-2409 VERIFIED).
  2. Source-text tests. scripts/newSessionSubmission.test.ts:65 asserts that initProjectRepository runs before listing refs VERIFIED; draftSessionLifecycle.test.ts:107 and editorSessionLifecycle.test.ts:54 pin deleted code. Those assertions are deleted, not patched to match.
  3. Root checkout is shared. Current checkout runs git switch in the project root, which moves every other session working in that folder. That is the owner's chosen behaviour.
  4. Saved-root import is one-shot. A saved root on a drive that is unmounted at the first 1a start is skipped and the key is deleted; the skip is logged and the user re-adds it with Add project.
  5. PR 3 provider cwd changes. Claude stores transcripts under a directory derived from the cwd, so resuming a Claude session from a different worktree may not find its transcript. change_checkout is Codex-only for this reason today. PR 3 must prove resume after a switch for each provider before enabling it.
  6. Remote UI proof on the workbox. On the workbox, "This Mac" is the workbox itself; the remote case needs a saved SSH profile to a host running the remote backend. Set it up before UI proof, not during.
  7. Size of 1a. 1a deletes ~900 lines and vendors ~250 shadcn lines. Reviewers should diff the vendored folder separately.
