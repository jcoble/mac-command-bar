Owner answers (2026-10-15)

  1. One kind of session: yes. Rights come from the backend's stored facts (who started a session, which run named it, the owner's orchestrator mark), never from how the rail shows it.
  2. A hierarchy. Workers message only their own run and its lead; helpers only their parent and their own runs; top-level sessions reach each other only through the main orchestrator. Pause answers and gates stay owner-only. Enforced in the backend (Task 15).
  3. The owner marks the main orchestrator: yes.
  4. Limits: yes. No helpers starting helpers; at most 3 unfinished helpers and 3 unfinished runs per session.
  5. Helper permissions: a helper takes its parent's permission mode, never more.

Order: 14, 17, 16, 15, then 18 to 23.

Today's bug, fixed first (Task 14)

On Agent Workbox, two helpers started with start_session never reached the rail, opened as an empty transcript, and hung 40 minutes on a permission request nobody could see. One cause: the rail learns about a new session only from a rename signal the remote server never sends, and only looks in the local list. The fix adds a session the rail does not know as soon as its first event arrives, from whichever machine has it. Opening it then shows its transcript, and its permission request shows on its rail row.

Removed from the old plan

One authority for each job.

The owner's own chat and inbox carry the owner's authority; no message does. The engine runs checks and applies rules. Sender labels are written by Assembly. Every agent is an ordinary session the owner can open.

Not in this plan: the phone app (slice 5, separate design). It gets two hooks: the inbox operation and the message list operation.
