Backbone Plan — Session Store + Engine Lifecycle

2026-08-12 · evidence: memprobe18 · muxspike19 (live probe) · t3lifecycle19 recon (running, feeds Track B policy detail) · rules: one-way-only, KISS, YAGNI

The end state, in one paragraph

A session is a SQLite row. Engines exist only while a turn runs (plus a 30-second grace window — owner-decided). One shared adapter process per provider hosts many sessions (proven live by muxspike19 for both adapters). Restart or crash the app and every session, transcript, draft, and annotation restores from the database. The journal ring buffer, the localStorage owned-sessions store, and the per-session-process assumption are all deleted — no old paths remain.

Three tracks, maximum safe concurrency

Track A — SQLite store module DISPATCHING NOW
New Rust files only (store/ module: schema, queries, retention, importer core) + full test suite. Zero overlap with the manager — runs concurrently with everything. The spec'd four tables (sessions, events, drafts, annotations), WAL, one retention DELETE policy.
Track C — Multi-session ACP client DISPATCHING NOW
acp_client.rs + process.rs: per-sessionId state and update routing (today: one native_session_id, one prompt route per process — muxspike19 proved the adapters already multiplex). Own worktree, own cargo target — safe alongside A (2 concurrent cargo builds, within the limit).
Track B — Manager rewire AFTER A + C + recon
The convergence point, sequential because everything meets in manager.rs: store wired as the single truth (writes in the same transaction as state changes), one-time importer, shared-adapter pool per provider, and turn-scoped suspend (30s grace; exact policy semantics — lease vs grace edge cases, cancel/permission interplay — finalized from the t3lifecycle19 recon report). Old paths deleted in this same track.

Then the fan-out point — you called it

Track B is exactly where the backbone starts affecting the rest of the app. Once it lands, the follow-ups are disjoint frontend/feature surfaces — ideal for wide concurrent lanes, each in its own worktree:

Verification gates (each track, before merge)

  • Track A: store tests incl. crash-safety (kill -9 mid-write → WAL recovers), retention policy, importer round-trip.
  • Track C: the muxspike19 probe rerun through OUR client — two sessions, interleaved ALPHA/BRAVO, no cross-talk; full agent_conversation suite green.
  • Track B: restart mid-conversation → everything restores; turn ends → engine gone in ~30s → next message resumes transparently; grep receipts that journal persistence + localStorage store are deleted; contract sweep zero-diff; rebuild + app restart before claiming done.
  • All: RUSTFLAGS="-D warnings", RUST_TEST_THREADS=1, one cargo per worktree, AGENTS.md perf rules.

Risks, honestly

  • Claude memory under multiplex is modest (+394MB/session measured) — the win there is turn-scoped lifecycle, not sharing. Codex gets both (~165MB saved per extra session).
  • Resume latency per message after grace expiry: engine respawn ~1-3s before first token. Mitigation: 30s grace covers active back-and-forth; if it feels slow in practice, the constant is one line.
  • Importer correctness: one-shot migration verified against your real machine before old stores are deleted — the delete commit only lands after a live restore check.
  • Recon may contradict a Track B detail (e.g. approval-while-suspended edge): B hasn't started, so findings land in its spec, not in rework.
