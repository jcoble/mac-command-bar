Remote history stored locally

Requested behavior: local SQLite persists fetched and live remote history with the same event representation and SQL paging as local chats. Workbox remains authoritative. Only the displayed window is retained in frontend memory. No age or size eviction.

Implementation boundary

  • core/src/session_store.rs: use the existing sessions.db and event tables; mark cached rows in an indexed cached_remote_profile_id column on sessions; transactional batch event upsert and source-specific purge. Local session startup and counts exclude cache-marked rows. No separate database file.
  • agent_conversation/remote_history.rs (new): small Rust owner for cached session metadata, confirmed history bounds, prepared events and SQL reads. Tag every cache session by source and original ID; reject responses from before explicit purge.
  • agent_conversation/remote.rs: save live events before UI delivery/acknowledgment; cache snapshot and page reads; incremental snapshot requests; purge explicit disconnect/removal/uninstall. Transient socket reconnect does not purge.
  • agent_conversation/manager.rs: snapshot read can return only events newer than the client's confirmed sequence. No frontend rendering change.
  • agent_conversation/mod.rs: register the new module.
  • main-architecture-explained.html: update actual storage, lifecycle, protocol and file responsibility receipts in the implementation commit.

Estimate: 600–850 lines including focused logic/socket tests and documentation. This is the specifically requested cache, not a general cache framework. No new user setting, age timer, UI component or automatic bulk preload of every historical chat.

Verification

  • All streamed events persist from the start, including inactive-session events.
  • Repeated reads use SQLite; unchanged snapshot checks carry no transcript events.
  • Missing older/newer history is retrieved without gaps or duplicates; signed imported sequences remain supported.
  • Prepared Markdown survives disk round-trip; no repeat frontend Markdown conversion.
  • Explicit cleanup deletes only the relevant cache; late responses cannot restore it. Local drafts/history and other machines remain intact.
  • Native repeated long-history scrolling, switching, new message, disconnect/reconnect tests; request-count and natural app-group memory evidence.

Existing committed journal and oversized-response fixes remain part of the broader memory goal.
